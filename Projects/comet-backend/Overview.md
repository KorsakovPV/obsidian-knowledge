# Comet-backend

#project

Бэкенд сервиса **электронных коммерческих предложений** (внутреннее название — **ETK**,
«Сервис электронных коммерческих предложений»). Менеджеры формируют коммерческое
предложение клиенту, проводят его через согласование и превращают в заказы во внешней
системе обработки заказов.

## Доменная суть

- **Сделка (deal)** — коммерческое предложение клиенту. Может содержать несколько продуктов.
- **Оффер (offer)** — составная часть сделки: `1 оффер == 1 продукт == 1 бланк заказа`.
- Согласованная сделка превращается в несколько **заказов (orders)** во внешней системе ОП
  (Order Processing).

Подробнее о сущностях и их связях — в [[Domain Model]].

## Стек

- **Python 3.13**, **FastAPI**, **Uvicorn** (ASGI).
- **SQLAlchemy 2.0** (async, `asyncpg`) + **Alembic** для миграций.
- **PostgreSQL** как основная БД, **Redis** для кэша/токенов.
- **Pydantic v2** / `pydantic-settings` для схем и конфигурации.
- **Keycloak** — аутентификация (JWT, Bearer).
- **Sentry** — мониторинг ошибок.
- Интеграции по HTTP (`httpx`): классификатор, Customers, Order Processing, Bitrix24.
- Почта: **SMTP** (`aiosmtplib`) и **IMAP** (`aioimaplib`) — для процесса согласования по email.
- Хранение файлов: **S3** (`aioboto3`).
- Управление зависимостями — **Poetry**; деплой — Docker + Kubernetes, CI в GitLab.

## Как запустить

Код проекта: `/home/pavel/PycharmProjects/comet-backend`.

```bash
poetry install
cp .env.example .env          # заполнить креды БД, Keycloak, S3, SMTP/IMAP и т.д.
alembic upgrade head          # применить миграции
python app/main.py            # uvicorn на localhost:8022
```

- Swagger UI отдаётся на корне `/` (`docs_url='/'`).
- Все ручки под префиксом `/api` (далее `/v1`), см. [[API]].
- Проверки качества: `make check` (pre-commit: black, isort, flake8, mypy, bandit).
- Тесты: `pytest`. Интеграционные тесты согласования требуют PostgreSQL и помечены
  маркером `integration`; без базы — `pytest -m "not integration"`.

## Заметки на полях

- Часть ручек — временные/технические (`/deals/check_send_email`,
  `/deals/check_fetch_unseen_emails`), они закрыты `require_admin`.
  Это видно по коду и помечено в [[API]]. `start-implementation` заглушкой быть
  перестала: она создаёт заказы в ОП по офферам сделки.
- Legacy offer-level согласование снято целиком (Ticket 15): у `approval` больше нет
  `offer_id`, `approvers` и email-токенов, служебные таблицы cutover удалены.
- Чтение сделки теперь зависит от доступности Order Processing: статусы заказов
  читаются на лету. Деградация продумана (сохранённое значение + предохранитель),
  но это новая внешняя зависимость на пути отдачи — [[Offer Order Status]].
  Предохранитель с 2026-08-11 не заклинивает на потерянной пробе: отмена запроса
  (`CancelledError`) освобождает слот явно, зависшая проба истекает по дедлайну.
- Файл КП (2026-08-11) хранится на бэке: фронт загружает PDF в момент отправки на
  согласование, загрузка заменяет прежний файл (одно КП на сделку, последняя версия).
  Согласующий получает файл в письме каждой стадии (вложение), в задачах
  `GET /approval-stages/pending` (`kp_attachment`) и скачиванием через ручку вложений.
  По ревью того же дня: ручки вложений закрыты правами (`send_kp` / `view_deals`),
  перманентные ошибки чтения КП не зацикливают доставку писем, чистка старых версий
  идёт в порядке «запись → объект», замена/удаление файла при активном согласовании
  запрещены (409, под блокировкой сделки — она же сериализует конкурентные загрузки).
  Открытые решения за аналитиком: `kind`-колонка вложений и обязательность файла при
  отправке на согласование; потолок попыток outbox — [[Outbox Dead Letter]].
- Debug-послабление согласования (2026-08-05) перевязано на
  `redirects_email_to_initiator`: раньше оно смотрело на один `APP_DEBUG_EMAIL_REDIRECT`,
  который в прод-конфигмапе стоял `True`, и инициатор мог закрыть любую стадию своей
  сделки на боевом контуре. Детали — [[Approval Debug Mode]].
- Сбои ОП с 2026-08-11 отдаются наружу как `order_processing_upstream_error` с
  полным ответом ОП в `upstream.*`, а не как наша 400: сеть/5xx/429 → 502
  «инцидент ОП», 4xx → 500 «баг интеграции у нас». Инцидент внешнего сервиса
  виден фронту и в логах одной строкой. Повод — 500 от `GET /api/v2/staffers`
  стейджа ОП, из-за которого имплементация выглядела сломанной на стороне Кометы.
  Корень (по логам ОП): **рассинхрон контуров** — `comet-backend-test` создаёт
  договоры в customers-**t**, а op-**stage** проверяет их в customers-**dev** →
  404 → у ОП «Unknown error in get_staffers» → 500. Пока цепочка контуров не
  выровнена, имплементация несогласованных сделок на тест-стенде не работает
  ни для одной сделки; плюс отдельный баг ОП: 404 от customers отдаётся как 500.
- Customers отвечает 404 на выборку без совпадений — для поиска договоров это
  «ничего не найдено», а не сбой (`DealService._list_contracts`, 2026-08-05):
  без этого несуществующий договор отдавал наружу 404 customers вместо нашей 400,
  а клиент без единого договора не мог создать первую сделку —
  [[DFDEV-2257 Deal Contract Selection]].
