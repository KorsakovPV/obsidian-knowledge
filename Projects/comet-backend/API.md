# API

#project

Публичный HTTP-API [[Overview|comet-backend]]. Все ручки версионированы и собираются в
`app/api/v1/v1_router.py`. Общий префикс — **`/api/v1`**. Swagger UI — на корне `/`.

Аутентификация — **Bearer JWT** (Keycloak) для всех путей, кроме «skipped» (см.
[[Architecture]]). Ниже пути указаны относительно `/api/v1`.

Многие ручки дополнительно закрыты проверкой прав ЛКМ через
`Depends(require_permission(...))` — механизм описан в [[Architecture]] (раздел
«Права доступа»). В таблицах ниже требуемый пермиссен указан в колонке «Право».

## Approval stages — `/approval-stages`

| Метод | Путь | Назначение |
|-------|------|-----------|
| GET | `/approval-stages` | Все стадии текущего согласующего: и ждущие решения, и пройденные |
| GET | `/approval-stages/pending?limit=50&offset=0` | **Deprecated.** Только идущие стадии, без содержимого офферов |
| POST | `/approval-stages/{stage_id}/decision` | Решение `approve/reject`; требует `Idempotency-Key` |
| POST | `/approval-stages/{stage_id}/skip` | Пропустить необязательную стадию (`reason`), право `skip_kp_approval_stage` |
| POST | `/approval-stages/{stage_id}/reassign` | Переназначить единоличную стадию (`user_id`, `reason`), право `reassign_kp_approval_stage` |

Ручки не принимают email token или user id: actor берётся только из principal middleware.
Доступ и статус стадии проверяются повторно в locked workflow-транзакции; результат
команды по `Idempotency-Key` сохраняется в БД, повтор возвращает его без нового перехода.
Skip доступен только для optional stage, reassign — только для единоличной (для групповой
возвращается `reassign_not_supported_for_group_stage`).

### Список стадий согласующего (DFDEV-2274)

`GET /approval-stages` — без параметров, без пагинации, от новых к старым. Одна ручка на
обе страницы фронта (DFDEV-2275): «Согласование КП» и «Все КП».

Стадия попадает в список, если она **идёт и ждёт** пользователя, если её ему **присылали**
или если он её **решил**. По назначению отбирать нельзя: у групповых стадий
`assigned_user_id` пуст всегда, включая уже решённые, — назначенный проставляется только
для единоличных прав. Поэтому история читается из доставок уведомлений и событий стадии, и
стадия остаётся в ней после переназначения и после отзыва права.

`is_current` и статус процесса не фильтруются: правка сделки после решения заводит новую
версию, и прошлая — та, где решение и принято, — перестаёт быть текущей. Именно она и
составляет «Все КП». Вместо фильтра по статусу — `requested_at IS NOT NULL`, то есть
«стадию присылали»: ожидающие и отменённые до активации в списки не попадают.

**`action_required` отдельно от `status`.** Стадия остаётся идущей и после переназначения,
и после отзыва права, но решить её пользователь уже не может — ручка решения проверяет
назначение и текущее право заново. Фронт делит списки по `action_required`, а не по
статусу, иначе нарисует кнопку, дающую отказ.

Карточка собрана из зафиксированного предмета согласования: номер и название сделки,
клиент, офферы с особыми условиями и тарифами (цена, база скидки, источник базы, скидка).
Названия клиента, продукта и тарифа — живые метаданные, приходят из справочников и **могут
быть пустыми**: каждый справочник деградирует отдельно, идентификаторы в карточке остаются.
Номер и идентификатор сделки — единственное, что достраивается из живой строки при пустой
секции в старом снапшоте: они выданы при создании и не меняются.

Вложения КП в этом списке нет: поле в `/pending` бралось из живой сделки и в истории
показывало бы текущий файл вместо согласованного. Доступ согласующего к файлу — DFDEV-1672.

### Устаревшая `/approval-stages/pending`

Остаётся рабочей и неизменной до перехода фронта. Задача в ней содержит `kp_attachment`
(id, имя, MIME-тип, размер) — текущий файл КП сделки; `null` у сделок без файла. Сам файл
согласующий скачивает ручкой `GET /deals/{deal_id}/attachments/{attachment_id}/file`
(deal_id в задаче есть).

## Deals (сделки) — `/deals`

| Метод | Путь | Назначение |
|-------|------|-----------|
| POST   | `/deals` | Создать сделку (необязательный `contract_id`, см. ниже) |
| GET    | `/deals` | Список сделок (с фильтрами `DealFilters`) |
| GET    | `/deals/{deal_id}` | Получить сделку |
| PATCH  | `/deals/{deal_id}` | Обновить сделку (`contract_id` не принимается → 422) |
| DELETE | `/deals/{deal_id}` | Удалить сделку |
| POST   | `/deals/{deal_id}/start-implementation` | Создать заказы в ОП по офферам сделки (`change_deal_status`) |
| POST   | `/deals/{deal_id}/approval/request` | Отправить сделку на согласование (инициатор сохраняется в согласовании) |
| POST   | `/deals/{deal_id}/approval/revoke` | Отозвать согласование |
| GET    | `/deals/{deal_id}/approvals?limit=20&offset=0` | История версий согласования сделки (без token-полей) |
| POST   | `/deals/check_send_email` | ⚙️ Техническая: тест отправки письма |
| POST   | `/deals/check_fetch_unseen_emails` | ⚙️ Техническая: тест чтения писем |

`approval/revoke` с 24.08.2026 проверяет доступность действия на сервере (DFDEV-2264):
отзыв разрешён, только пока согласование идёт (`pending`/`blocked`) и только держателю
`send_kp`. В прочих статусах — **403** с тем же текстом, что и в `actions.revoke_approval`
сделки («не отправлена на согласование» / «согласование уже завершено» / «не требуется»).
Повторный вызов сразу после отзыва тоже 403: отзывать больше нечего. Сам набор
`actions` сделки пополнился ключом `revoke_approval` — это единственное действие, которое
активное согласование открывает, а не закрывает.

`start-implementation` доступна только для сделки с пройденным маршрутом согласования
(одобренной либо не требующей согласования). Заказы создаются по снимку версии, по
одному на оффер, с идемпотентным ключом; если часть заказов не создана — **422**
`deal_implementation_incomplete`, сделка не считается переданной. В теле — `failed_offers`
с причиной по каждому упавшему офферу (`offer_id`, `attempts` и блок `error`: какой сервис
отказал и что ответил), плюс устаревший `failed_offer_ids` только с идентификаторами.
Причины в одном ответе бывают разные — отказ ОП по цене и недоступность ОП соседствуют,
поэтому статус ответа един для любого набора, а разбираться нужно по каждому офферу
([[Видимая причина провала имплементации]]). Пустой маршрут — тоже пройденный: такие заказы уходят в ОП
согласованными, а не решаются им заново по каждому продукту
([[DFDEV-2044 Multi Product Approval]]). Сделка, которой маршрут положен, но не пройден,
получает 400 «сделка не отправлена на согласование»; оффер, по которому заказ уже создан,
пропускается и возвращается в отчёте как созданный ранее. После создания заказов состав
сделки редактировать нельзя — 409 `deal_already_implemented`.

Сбой на границе с ОП, **прерывающий запрос целиком**, отдаётся с кодом
`order_processing_upstream_error` и блоком `upstream`: сеть/5xx/429 → **502** «инцидент
ОП», 4xx → **500** «ОП отклонил запрос: ошибка интеграции на стороне Кометы» (не
ретраебельная). Так отвечает ручной `POST /orders/{offer_id}`, а на `start-implementation` —
только проверки до цикла по офферам (резолв стафферов, покрытие снимка, отсутствие
договора). Сбой отдельного оффера сюда не попадает: он поглощается циклом и становится
элементом `failed_offers`. Наши бизнес-ошибки (сделка без оферов, без договора) остаются
400; таймаут POST предсогласованного заказа не считается сбоем — его разбирает
идемпотентное GET-recovery, таймауты остальных вызовов ОП — обычная 502. Введено
2026-08-11 после инцидента, когда 500 от `GET /api/v2/staffers` ОП выглядел как 400 Кометы.

Форма блока одна для обоих случаев — `UpstreamErrorSchema` (`service`, `status`, `url`,
`body`), и собирает её один хелпер: в 502/500 она лежит в `upstream`, в 422 — в
`failed_offers[].error`. `service` различает отказ внешнего сервиса (`order-processing`) и
собственную проверку Кометы (`comet`, без статуса — например, цена ниже пола защищённого
тарифа). Строковое тело усечено до 2000 символов, разобранный JSON отдаётся структурой.

### Договор сделки

`contract_id` принимается при создании и после создания не меняется. Договор
пришёл — сделка коммерческая; не пришёл — тестовая, бэк сам подставляет тестовый
(`TST*`) договор клиента. Сделка отдаёт вычисляемый тип договора:
`contract_number`, `contract_type` (`test` / `inner` / `commercial`),
`contract_type_title` — и в карточке, и в списке. Подробно —
[[Deal Contract Selection]] и [[DFDEV-2257 Deal Contract Selection]].

## Вложения сделок — `/deals/{deal_id}/attachments`

| Метод | Путь | Назначение | Право |
|-------|------|-----------|-------|
| POST   | `/deals/{deal_id}/attachments` | Загрузить файл КП (заменяет прежний) | `send_kp` |
| GET    | `/deals/{deal_id}/attachments` | Список вложений | `view_deals` |
| GET    | `/deals/{deal_id}/attachments/{attachment_id}` | Метаданные вложения | `view_deals` |
| DELETE | `/deals/{deal_id}/attachments/{attachment_id}` | Удалить вложение | `send_kp` |
| GET    | `/deals/{deal_id}/attachments/{attachment_id}/file` | Скачать файл (S3) | `view_deals` |

Вложение сделки — это файл КП: он один на сделку, отдельного признака нет. Фронт
собирает PDF (данные — `OfferService.get_tariffs_for_pdf`) и загружает его в момент
отправки на согласование; повторная загрузка **заменяет** прежний файл (хранится
последняя версия, версионирование — отдельным тикетом). Лимит — 20 МБ
(`MAX_FILE_SIZE`), пустой файл отклоняется. Этот же файл уходит вложением в письме
каждой стадии согласования и отдаётся согласующему в `GET /approval-stages/pending`.

Права: загрузка и удаление — операции менеджера над отправляемым КП (`send_kp`, как
у самой отправки на согласование); чтение и скачивание — `view_deals`, оно есть у
всех ролей, включая согласующих (`product_owner`, `lawyer`), поэтому скачивание КП
из задачи согласования работает.

При активном согласовании (`pending`/`blocked`) POST и DELETE возвращают 409
`approval_subject_locked` — файл зафиксирован, как и сама сделка. После отзыва
согласования (draft-версия) замена снова доступна.

### Статусы в ответе оффера

Оффер отдаёт два независимых статуса, оба в общей форме `code` / `title` / `kind`:

- `status` — **КП-фаза**: `in_progress` / `formed` / `approval` / `approved` /
  `returned`. Вычисляется из состояния оффера и согласования сделки, не хранится.
  В фазе `approval` добавляется `stage_code` активной стадии — русских подписей стадий
  бэк не отдаёт, их рисует фронт.
- `order.status` — **статус БЗ в ITSM**: `code` (сырой `itsm_state`), `title` и `link`
  от ОП, `kind = external`, `synced_at`. Читается из ОП на каждый запрос сделки, а не
  сохраняется однократно при создании заказа.

Рядом в блоке заказа: `order.order_type` (`test` / `inner` / `commercial`, приходит из
ОП) и `order.kp_phase` — снимок КП-фазы на момент создания заказа, первая точка
мини-таймлайна.

При недоступном ОП карточка и список не падают: приходит последнее сохранённое
значение, признак — `synced_at`. Поля `order.order_status` и `order.synced_at`
помечены deprecated и дублируют `order.status.*` на переходный период.

Подробно, включая режимы чтения и предохранитель — [[Offer Order Status]].
Сводная справка для фронта — какие статусы уже отдаются и с какого шага жизни
сделки — [[Status Contract for Frontend]].

Тариф оффера обязан содержать `price` — цену продажи, от которой считается скидка и
строится маршрут согласования. Тариф без неё отклоняется с кодом
`offer_tariff_price_required`, тариф без цены в прайсе классификатора —
`offer_tariff_price_not_found` (оба 400).

`partner_client_price` — цена конечного потребителя. В расчёте скидки от прайса она не
участвует, но проверяется в воротах персональной цены: ворота открываются, только если и
цена продажи, и цена потребителя не ниже персональной цены клиента в своих шкалах. База
скидки отдаётся в `base_price` с источником в `base_price_source`
(`classifier` | `client_price`) — см. [[Discount Base and Personal Price]].

## Client prices (клиентские цены) — `/client-prices`

| Метод | Путь | Назначение |
|-------|------|-----------|
| POST | `/client-prices` | Создать клиентскую цену; право `approve_tariffs` |
| DELETE | `/client-prices/{price_id}` | Снять клиентскую цену; право `approve_tariffs` |
| GET  | `/client-prices/effective` | Действующая цена |
| GET  | `/client-prices/{price_id}` | Цена по id |
| GET  | `/client-prices/client/{client_id}/prices` | Цены клиента |

Заведение и снятие закрыты правом `approve_tariffs` (финансовый директор и администратор):
цена не ниже персональной снимает согласование скидки, поэтому без права менеджер мог бы
завести клиенту цену в рубль и провести КП мимо маршрута. Выдача и отзыв такого права —
решения одного класса, поэтому и право у них одно. Подробно — [[Discount Base and Personal Price]].

`valid_to` **необязателен**: пусто означает бессрочную цену. Бессрочной остаётся только
запись, заведённая вручную — у автоматической срок конечен (см. ниже).

**Ручное заведение не падает на пересечении с автоматической записью.** Переданный период
авторитетен и не обрезается: автозаписи под него подрезаются, поглощаются или разрезаются
надвое. Пересечение с другой **ручной** записью по-прежнему 409 — это конфликт намерений,
и решать его молча нельзя.

Удаление не сдвигает соседние периоды: в истории остаётся промежуток ровно там, где право
отозвали, и скидка в нём снова считается от прайса классификатора. Отдельная операция нужна
потому, что «персональной цены больше нет» иначе выразить нечем — ошибочно выданное право
пришлось бы прикрывать вымышленной ценой поверх него.

### Автозаполнение по созданному заказу

Персональная цена заводится сама при успешном создании заказа в ОП, если сошлось всё:
заказ создан этим вызовом (а не возвращён по ключу идемпотентности), версия согласования
несёт решение (`answered` + `approve`), и цена ниже прайса классификатора. Пустой маршрут
права не выдаёт: скидка в пределах беспорогового лимита проходит без согласующих.

Пишется цена конечного потребителя — та шкала, в которой прайс хранится. Срок действия
такого права конечен (`CLIENT_PRICE_AUTO_PRICE_TERM_DAYS`, по умолчанию год); покупка по
той же цене продлевает его, но никогда не укорачивает уже действующее.

Подробно — [[Автозаполнение персонального прайса при создании заказа]].

## Pre-tariffs (заявки на предтариф) — `/pre-tariffs`

| Метод | Путь | Назначение |
|-------|------|-----------|
| POST   | `/pre-tariffs` | Создать заявку |
| GET    | `/pre-tariffs` | Список заявок |
| GET    | `/pre-tariffs/{pre_tariff_id}` | Получить заявку с чатом, вложениями и историей |
| PATCH  | `/pre-tariffs/{pre_tariff_id}` | Обновить заявку |
| DELETE | `/pre-tariffs/{pre_tariff_id}` | Удалить заявку |

| POST   | `/pre-tariffs/{pre_tariff_id}/submit` | Отправить заявку на согласование (`draft → review`) |
| POST   | `/pre-tariffs/{pre_tariff_id}/withdraw` | Вернуть заявку в черновик (`review → draft`) |
| POST   | `/pre-tariffs/{pre_tariff_id}/approve` | Согласовать заявку (`review → approved`) |

**Права навешаны** (CM-2, 24.08.2026): чтение — `create_tariff` **или** `approve_tariffs`
(читают обе стороны), создание, правка, удаление и `submit`/`withdraw` — `create_tariff`,
`approve` — `approve_tariffs`. Теми же правами закрыты чат и вложения заявки. Автор
записывается из принципала: `created_by`/`updated_by` в запросах больше не принимаются.

**Заявка заводится вместе с черновиком тарифа** (CM-5, 25.08.2026): `POST /pre-tariffs`
принимает `tariff` — payload по контракту классификатора (ветка услуг объектами, элемент
тарификации, цены, даты, коды). Комета создаёт черновик, сохраняет ссылку на него и
денормализует из payload название и цены. `PATCH` в статусе `draft` с полем `tariff`
проксирует правку целиком; `approve` сначала публикует черновик и только потом переводит
заявку — отказ публикации оставляет её на согласовании. Отказы классификатора: **422**
`rejected` с его текстом, **409** `publish_conflict` (полный дубль) и `not_found`,
недоступность — **502**. Деталка отдаёт сам черновик в поле `tariff`, а если позиция в
классификаторе исчезла — `tariff_error: not_found_in_classifier`.

**Контракт заявки реализован** (CM-1, 24.08.2026) — CRUD те же, изменилось наполнение:

- Деталка (`GET /{id}`, ответы POST и PATCH) отдаёт `status`, `classifier_tariff_id`,
  `product_id`, `client_id`, `deal_id`, `title`, `description`, `price`, `cost_price`,
  `quantity_params` (`{min, max?, step?}`), `decided_by`/`decided_at`, плюс `comments`,
  `attachments` и `events` — журнал заявки (`actor`, `actor_role`, `action`,
  `old_status`, `new_status`, `created_at`). Создание сразу даёт событие `created`.
- Список (`GET /pre-tariffs`) отдаёт **другую схему**: те же поля заявки плюс
  `unread_count`, но без чата, вложений и журнала; сортировка — новые первыми.
  `unread_count` пока всегда `0` (заглушка до CM-3).
- Вход строг: `status`, `classifier_tariff_id`, `decided_by`/`decided_at` схемами не
  принимаются (ими управляют переходы), неизвестные поля → 422. Цены — не больше
  `numeric(10,2)`, `title` — до 255 символов, `quantity_params` валидируется по составу.
- `PATCH` частичный: непереданное поле не трогается, явный `null` **очищает**
  необязательное поле. `description`, `title` и `quantity_params` очистить нельзя —
  они есть у заявки всегда, `null` для них 422.

Правила переходов и доступа (все проверяются сервером):

- **Ведёт заявку автор**: правка только в `draft` (`submit` замораживает состав),
  `submit`/`withdraw` — тоже автор. Не автор получает **403**.
- **Решает согласующий**: `approve` доступен держателю `approve_tariffs`, авторства не
  требует, проставляет `decided_by`/`decided_at`. Статус `approved` терминален —
  обратных переходов нет.
- **Повтор перехода идемпотентен**: заявка уже в целевом статусе → **200** с текущим
  состоянием. Если статус успели изменить другим переходом — **409**
  `{"code": "invalid_status"}`.
- **Видимость**: держатель `approve_tariffs` видит все заявки, остальные — только свои;
  правило серверное и не зависит от фильтров запроса. Чужая заявка в деталке — 403.
- **Удаление**: автору в `draft`/`review`; в `approved` — 409 `invalid_status`; если
  `classifier_tariff_id` встречается в составе любого оффера — 409 `pre_tariff_in_use`.
  Статус проверяется тем же запросом, что удаляет. Вместе с заявкой удаляются её черновик в
  классификаторе и файлы вложений; недоступный классификатор откладывает удаление — **502**,
  заявка остаётся на месте (иначе черновик повис бы без заявки).
- Каждый переход пишет событие в журнал заявки (`events` в деталке).

**Коды ошибок ручек заявки** (в теле рядом с `detail`):

| Код | Статус | Когда |
|-----|--------|-------|
| `invalid_status` | 409 | статус заявки не тот, что нужен действию, либо его успели изменить |
| `pre_tariff_in_use` | 409 | позиция уже стоит в оффере — заявку не удалить |
| `publish_conflict` | 409 | классификатор отказал в публикации (полный дубль по коду и цене) |
| `draft_missing` | 409 | у заявки нет черновика либо он исчез из классификатора |
| `rejected` | 422 | классификатор не принял данные тарифа; текст — его собственный |
| `classifier_unavailable` | 502 | классификатор недоступен или ответил не по контракту |

403 отдают все ручки заявки, её чата и вложений: и при отсутствии прав, и при обращении к
чужой заявке.

Ещё не реализовано ([[Предтариф как черновик тарифа]]): флаг черновика в офферах и КП,
триггер маршрута и guard имплементации — CM-6.

### Состав оффера с пропавшими позициями

Тарифы оффера хранятся у нас, а их описание — в классификаторе. Если позиции там больше нет,
оффер **всё равно рендерится**: она пропускается, а в ответе появляются

- `tariff_warnings: [{pk, reason: "not_found_in_classifier"}]` — что именно не показано;
- `amounts_incomplete: true` — суммы посчитаны не по всему составу.

Критичные операции этим не довольствуются: **отправка сделки на согласование** отвечает
**422** `offer_tariffs_missing` с перечнем `offers: [{offer_id, tariff_ids}]` — согласующим
нельзя показывать состав, из которого молча выпала позиция. Полная недоступность
классификатора при рендере — **502**, а не 500.

## Справочники классификатора — `/tariff-classifier`

| Метод | Путь | Назначение |
|-------|------|-----------|
| GET | `/tariff-classifier/tree` | Всё для каскада формы черновика тарифа одним ответом |

Реализовано CM-4 (24.08.2026), право — `create_tariff`. В ответе `service_tree`
(линия бизнеса → линейка → услуга → элемент услуги, у каждого узла `pk`, `title`, `code`;
у услуги ещё `is_available`) и словари `units`, `charge_types`, `currencies`,
`update_frequencies`, `locations`.

Классификатор отдаёт эти уровни четырьмя плоскими списками со ссылками по
идентификаторам — дерево собирается на сервере, узлы с несуществующим родителем в выдачу
не попадают и логируются как рассинхрон справочников. Идентификатор нормализован: короткие
сериализаторы классификатора отдают `pk`, а локации — `id`.

Ответ кешируется в Redis на час целиком; недоступный Redis форму не ломает — справочники
перечитываются у классификатора, а пересборка идёт под локом, чтобы протухший кеш не отправил
все параллельные запросы в классификатор разом. Недоступность, отказ в правах и неожиданный
формат дают **502** с `code: classifier_unavailable`, а не 500; у 403 текст отдельный — про
права сервисной учётной записи.

### Комментарии пре-тарифов — `/pre-tariff-comments`

CRUD-набор: POST / GET (список) / GET `/{id}` / PATCH `/{id}` / DELETE `/{id}`, плюс
`POST /pre-tariff-comments/read` (тело: `pre_tariff_id`) — отметка «чат открыт»: двигает
отметку прочтения на текущий момент и возвращает обнулённый счётчик.

Счётчик `unread_count` приходит в списке заявок и в деталке. Он **личный**: отметка своя у
каждого читателя, свои сообщения непрочитанными не считаются, а чат без отметки непрочитан
целиком. Деталка счётчик показывает, но не обнуляет — прочитанным чат делает его открытие.
Лимит сообщения — 2000 символов. Все ручки чата закрыты правилом видимости заявки.

## ЛКМ: управление пользователями — `/lkm/users`

Ролевая модель ЛКМ (`app/api/v1/lkm/`). Guard'ы — по пермиссиям. Подробно — в
[[Architecture]] и исследовании [[LKM Role Model]].

| Метод | Путь | Назначение | Право |
|-------|------|-----------|-------|
| GET   | `/lkm/users` | Список видимых пользователей | любой из `add_users` / `change_user_roles` / `change_permissions` |
| GET   | `/lkm/users/search?q=` | Поиск в Keycloak по логину/ФИО (мин. 3 символа) | `add_users` |
| POST  | `/lkm/users` | Добавить пользователя из AD в ЛКМ | `add_users` |
| GET   | `/lkm/users/{user_id}` | Карточка пользователя + эффективные пермиссии | любой из `add_users` / `change_user_roles` / `change_permissions` |
| PATCH | `/lkm/users/{user_id}/role` | Сменить роль (не свою УЗ; сбрасывает персональные права) | `change_user_roles` |
| PATCH | `/lkm/users/{user_id}/email` | Задать канонический email доставки писем согласования (или очистить через `null`) | `add_users` |
| PATCH | `/lkm/users/{user_id}/permissions` | Заменить персональные пермиссии: `permission_codenames` — на все продукты, `scoped_permissions` (`codename` + `product_id`) — на конкретный продукт | `change_permissions` |

Обе правящие ручки (`/role` и `/permissions`) возвращают пользователя вместе с полем
`stage_transfer`: какие идущие стадии согласования переехали на нового держателя
единоличного права и какие перевести не удалось — повторный запрос доводит перенос до
конца. Единоличное право (`approve_kp_lawyer`, `approve_kp_sales_director`,
`approve_kp_finance_director`) при назначении **переносится**: у прежнего держателя оно
снимается. Отказы: снятие права у единственного держателя и смена его роли —
«назначьте другого держателя»; назначение такого права на продукт запрещено. Подробнее —
раздел «Единоличные права» в [[Architecture]].
