# DFDEV-2773 План реализации

#project

Источники: [DFDEV-2773](https://btask.beeline.ru/browse/DFDEV-2773), [парная фронтовая задача DFDEV-2829](https://btask.beeline.ru/browse/DFDEV-2829), [БТ 03.06](https://bwiki.beeline.ru/pages/viewpage.action?pageId=2650033656). Задача явно заменяет процентный ввод из §1 БТ рублёвыми ценами L1–L3. Правила для текста обоснования берём из §2 БТ.

## Согласованный результат

- Для не-SOR черновика можно сохранить пустую шкалу или 1–3 уровня. Отправка заявки на согласование и прямая публикация в классификаторе требуют полные L1–L3. `GPL ≥ L1 ≥ L2 ≥ L3 > 0`; равные соседние цены допустимы. Номера только 1, 2, 3, без повторов. При изменении GPL уровни не пересчитываются.
- GPL и минимальная отпускная цена `cost_price`: максимум `99 999 999,99`, до двух дробных знаков. Цена уровня: максимум восемь цифр до запятой и шесть после. Сохраняется числовое значение без округления; фиксированный масштаб БД может добавить незначащие нули при выдаче.
- Защита использует существующие `is_price_protected` и `TariffElement.cost_price`: это минимальная клиентская цена без НДС. При включённой защите она обязательна и положительна. При выключении введённые сумма и обоснование сохраняются; жёсткий минимум действует только при включённом флаге. Партнёрский минимум вычисляется из клиентского делением на `1,1` с действующим округлением классификатора и не хранится отдельно.
- Необязательное обоснование — до 255 символов. Допустимы русские и английские буквы, цифры, обычный пробел U+0020 и только `+ - _ , . ( ) ? ! " № # ; : % @`. Обычные пробелы по краям и подряд допускаются, значение не обрезается и не очищается автоматически; другие пробельные символы отклоняются.
- SOR остаётся вне новых правил; действующее обнуление GPL и `cost_price` сохраняется. Старые опубликованные тарифы и расчёт скидок оффера сохраняют действующее поведение.

## Контракт API

В `tariff` запросов `POST /api/v1/pre-tariffs` и `PATCH /api/v1/pre-tariffs/{id}` добавить `price_levels: [{level, price}]` и `price_protection_reason`.

| Поле | POST | PATCH |
| --- | --- | --- |
| `price_levels` | Нет поля или `[]` — пустая шкала; `null` — ошибка | Нет поля — сохранить; `[]` — очистить; `null` — ошибка |
| `element.cost_price` | Ключ обязателен. `null` или старый `0` — минимума нет при выключенной защите; положительное число — минимум | Если передан `tariff`, ключ обязателен: отсутствие — 422; `null` и `0` очищают, положительное число задаёт или сохраняет минимум. Если `tariff` не передан, цена не меняется |
| `price_protection_reason` | Нет поля или `null` — обоснования нет | Нет поля — сохранить; `null` — очистить |

Если `is_price_protected=true`, `cost_price=null` и `0` отклоняются. При `false` сохранённая положительная сумма не очищается лишь из-за выключения флага. Комета пересылает объект тарифа классификатору через PUT: учитывать `model_fields_set` и не терять различие между отсутствующим полем и явным очищением при сериализации.

## Порядок разработки

1. **Классификатор: данные и запись.** Использовать существующую `TariffPriceLevel(tariff_id, level, price)` с уникальностью `(tariff, level)` и `DecimalField(14,6)`; новые колонки L1/L2/L3 не нужны. Добавить к `Tariff` `price_protection_reason` и служебный `cost_price_present`. `TariffElement.cost_price` оставить числовым и ненуллабельным: отсутствие нового минимума хранить внутренним нулём с `cost_price_present=false`. Для новых SOR записывать `cost_price_present=true`, сохраняя старую числовую выдачу.
2. **Классификатор: миграция.** Сначала добавить nullable `cost_price_present` без значения по умолчанию. Новый код при `NULL` выводит присутствие из сырой цены, признака черновика и типа SOR; положительная сырая цена имеет приоритет и над устаревшим `false`, записанным смешанными версиями сервиса. Новые пути записи устанавливают признак. После вывода старых экземпляров сервиса выполнить идемпотентную команду `backfill_cost_price_present` пакетами по PK: положительная цена → `true`, ноль у не-SOR черновика → `false`, ноль у опубликованного тарифа или SOR → `true`. Проверить количества и выборку архивных/SOR записей; ограничение `NOT NULL` добавлять отдельной последующей миграцией после этой операции, не в первом выпуске.
3. **Классификатор: проверка и транзакция.** Расширить запись `DraftTariffSerializer` для уровней и обоснования. Проверять номера, уникальность, положительность, точность, GPL и порядок по итоговому состоянию после частичного изменения. Имеющаяся `validate_tariff_price_levels` работает с сортированными заполненными парами, в том числе L1+L3; передавать в `supplied_levels` все итоговые номера, чтобы изменение только GPL тоже перепроверяло старые уровни. Записывать тариф, его цену, признак наличия минимума, обоснование и набор уровней в одной транзакции. Создание включает связанные локации и тарифы; ошибку, превращённую во вьюхе в HTTP-ответ после записи, нужно откатить. Сохранять уровни и обоснование при публикации и архивировании; проверить журнал изменений, кэш и Excel.
4. **Классификатор: чтение.** Отдавать упорядоченные уровни, защиту, обоснование и `cost_price_present`. При отсутствии минимума в БД остаётся `0`, а на существующем проводе сохраняются числовые значения без изменения поведения конкретной ручки: текущий сериализатор тарифа подменяет нулевой `cost_price` расчётом `85% GPL`, старый список Кометы содержит локальный `0`; существующие поля партнёрского минимума тоже остаются числовыми. Эти числа не означают введённый минимум при `cost_price_present=false`. Новая Комета использует маркер, чтобы представить отсутствие минимума на экране предтарифа как пустое значение. Положительная сохранённая сумма при выключенной защите показывается справочно и не становится жёстким порогом.
5. **Комета: запись и переход.** Расширить `DraftTariffPayloadSchema`, проверить деньги и точность до вызова классификатора. При переходе `submit` под существующей блокировкой сначала проверить автора и статус DRAFT, затем прочитать сохранённый тариф. Для не-SOR потребовать полные корректные L1–L3; для SOR эту проверку пропустить. После проверки оставить условный контроль статуса в `pre_tariff_crud.transition`. Для неполной/неверной шкалы вернуть 409 в существующем формате `{detail, code}` с кодом `price_levels_incomplete` или `price_levels_invalid` и указанием поля/уровня в `detail`; без изменения статуса, события и outbox. Некорректное тело запроса остаётся 422. Тип SOR брать из сохранённого `element.charge_type.charge_type` по действующему значению `SOR`, согласованному с классификатором. Повторная отправка после отзыва проходит ту же проверку.
6. **Комета: время и чтение.** Обернуть весь вызов `DraftTariffService.get` внутри блокировки во внешний `asyncio.timeout(30)`. Обычный клиент допускает четыре попытки с тайм-аутом 30 секунд на каждую, но отмена внешнего контекста прерывает внутренние ретраи: общее время удержания блокировки ограничено 30 секундами, а у `submit` меньше времени на восстановление, чем у остальных чтений. На истечении времени возвращать ошибку недоступности классификатора и освобождать блокировку. Блокировка сейчас не ждёт: конкурирующая операция может получить `pre_tariff_busy`, а при заполнении пула — `pre_tariff_capacity_exceeded`. Деталка и согласование читают тариф из классификатора; `GET /pre-tariffs` для карточек и выбора в КП обогатить по ID через существующий `get_tariffs_by_ids` пакетами по 100. При недоступности классификатора оставить строки списка и пометить отсутствие финансовых данных `tariff_error`. Расчёт скидки и маршрут согласования КП не менять.
7. **Прямая публикация.** Проверка полной шкалы не-SOR находится в `publish_draft` внутри транзакции после существующих блокировок; до этапа 5 она выключена настройкой `ENFORCE_DRAFT_PRICE_LEVELS_ON_PUBLISH=false`. Повторная публикация уже опубликованного тарифа остаётся идемпотентной. Одинаковые правила проверяются тестами в обоих сервисах.

## Выпуск без разрыва старых клиентов

1. Классификатор: схема, чтение/запись новых полей, **без** запрета публикации. Старые запросы Кометы без новых полей работают; числовая выдача сохраняется. Этот этап должен работать на каждом контуре до выпуска Кометы.
2. Комета: приём полей и обогащённое чтение, **без** проверки шкалы на `submit`. Старый фронт продолжает отправлять `cost_price=0`; ответ для него пока остаётся числовым, дополненным `cost_price_present`.
3. Фронт: новая форма и отображение. Признак `cost_price_present` позволяет показать отсутствие цены как пустое поле при числовом ответе переходного периода.
4. Когда старые фронтовые экземпляры и кэшированные версии уйдут: включить в Комете `APP_ENFORCE_PRE_TARIFF_LEVELS_ON_SUBMIT=true` и `APP_PRE_TARIFF_NULL_COST_PRICE=true`. Первая настройка требует полную шкалу на `submit`, вторая возвращает `null` для отсутствующего минимума в выдаче предтарифа. По умолчанию обе выключены.
5. Когда старые экземпляры Кометы уйдут: проверить согласованные, но ещё не опубликованные не-SOR черновики без полной шкалы. Если они есть, отложить включение запрета до согласованного ручного исправления реальными ценами; значения не придумывать. Затем включить в классификаторе `ENFORCE_DRAFT_PRICE_LEVELS_ON_PUBLISH=true`. По умолчанию настройка выключена. Уже опубликованные за переходный период тарифы остаются по старому контракту.
6. После вывода старых экземпляров классификатора выполнить `pipenv run python backend/manage.py backfill_cost_price_present` и проверить результат. Ограничение `NOT NULL` для служебного признака — отдельная последующая миграция после проверки данных; в текущей реализации его нет.

## Проверка

- Классификатор: пустая/частичная/полная шкала, не соседние уровни, равные цены, повторы и лишние номера, GPL, предельные числа и шесть дробных знаков, ошибка после последней записи и откат, включение/выключение защиты, разрешённые/запрещённые символы и длина обоснования, SOR, старые нулевые тарифы, публикация/архив, кэш, журнал и Excel.
- Комета: старые POST/PATCH с `cost_price=0`, новый `null` по каждому полю, повторное открытие и правка, первичная/повторная отправка, приоритет ошибки статуса перед ошибкой шкалы, права автора, отсутствие события и outbox при 409, недоступность классификатора, 30-секундный предел, конкуренция и освобождение блокировки, совпадение карточки/деталки/выбора КП.
- Совместимость выпусков: старый Comet читает и публикует против этапа 1; старый фронт создаёт и отправляет предтариф против этапа 2; новый фронт понимает переходную числовую выдачу; после этапов 4–5 неполные шкалы отклоняются. Проверить отсутствие регрессии у старых опубликованных тарифов, SOR и скидок оффера.
- При реализации запустить существующие наборы `poetry run pytest` и `poetry run make check` в Комете, `pipenv run python backend/manage.py test` и `pipenv run python backend/manage.py qa` в классификаторе.

Атомарность охватывает одну БД классификатора. Комета сначала пишет в классификатор, затем обновляет локальную заявку; при сбое второй записи данные могут разойтись. В рамках этой задачи логировать ID заявки и тарифа, читать актуальные финансовые данные из классификатора и не обещать общей транзакции или автоматического исправления локальной копии.
