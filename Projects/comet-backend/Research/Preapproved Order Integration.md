# Интеграция с ОП: предсогласованные заказы

#research #project

> Зеркало `docs/preapproved_order_integration.md`. Сущность `OfferOrder` описана в
> [[Domain Model]], процесс согласования — в [[Architecture]], разбор дефекта
> «согласован только один заказ» — в [[DFDEV-2044 Multi Product Approval]].

Как согласованная в Комете сделка превращается в заказы Order Processing (ОП).
Заведено в DFDEV-1908, существенно переработано в DFDEV-2279 и DFDEV-2044 — ниже
описано текущее поведение, а не первоначальный замысел.

## Когда создаются заказы

Имплементация запускается ручкой `POST /deals/{deal_id}/start-implementation` и создаёт
по одному заказу на каждый оффер снимка версии согласования.

Пропускается версия, **прошедшая свой маршрут**:

- `answered` + `approve` — маршрут пройден решениями согласующих;
- `not_required` — маршрут пуст (скидка в пределах лимита, особых условий нет),
  согласовывать было нечего.

Пустой маршрут раньше уводил сделку на обычное создание заказов, где про согласование
решал сам ОП, отдельно по каждому продукту: продукт из его списка автосогласования
получал «Согласован», остальные — «Требует согласования». В сделке с несколькими
продуктами это выглядело как «согласован только один заказ» (DFDEV-2044). Отдельной ветки
с обычными заказами в имплементации больше нет.

Сделка без единой версии согласования выглядит как «согласовывать нечего», хотя маршрут ей
мог ни разу не строиться. Поэтому имплементация сама готовит версию тем же способом, что и
отправка на согласование: пустой маршрут — работаем, непустой — 400 «сделка не отправлена
на согласование». Подготовленный черновик при отказе сохраняется, иначе сделку нечем было
бы отправить на согласование.

## Что уходит в ОП

`POST /api/v2/internal/orders/preapproved/new`:

```json
{
  "external_approval_id": "<UUIDv5 от пары (approval_id, offer_id)>",
  "order": { "...": "поля заказа в формате OrderNewCreateSchemaIn" }
}
```

- **Ключ идемпотентности** — детерминированный UUIDv5 от строки `{approval_id}:{offer_id}`
  с фиксированным namespace. Менять формулу нельзя: другой ключ = дубли заказов в ОП.
- **Предмет заказа берётся из снимка версии**, а не из живых строк: в ОП должны уйти те
  данные, по которым принято решение. Из актуальной сделки берутся только операционные
  поля (договор, стафферы).
- **`tariffs_for_approve` — весь состав тарифов**, тот же список, что и `tariffs`. ОП не
  применяет к согласованным тарифам валидацию минимальной цены (кроме защищённых), иначе
  режет согласованную цену и имплементация падает (DFDEV-2279).
- **`special_conditions` кладётся, только когда заполнено.** В схеме ОП поле объявлено
  строкой со значением по умолчанию «Без особых условий»: отсутствие ключа он принимает и
  подставляет своё, а явный `null` отклоняет с 422.
- Типовые условия продукта не передаются: ОП сам печатает их в бланке, беря из
  классификатора. В `order.special_conditions` уходит только то, что дописал менеджер.
- `external_context` (approval id, версия, offer id) добавляется под флагом
  `ORDER_PROCESSING_SEND_EXTERNAL_CONTEXT` — только после согласования контракта с ОП.

Перед отправкой состав ещё раз проверяется на пол защищённых тарифов по актуальным данным
классификатора: минималка и признак защиты живут там и могут измениться после сохранения
оффера. Отказ приходит с минимальной ценой в ответе, а не общей ошибкой от ОП.

## Что делает ОП

Создаёт заказ и в той же транзакции — согласование со статусом `APPROVED` и источником
`external_service`. Поэтому заказ сразу «Согласован» и проходит гейт ITSM. Отправка БЗ в
ITSM — отдельное действие уже в ОП (`POST /api/v2/itsm_implement_order` и фоновая задача),
Комета его не инициирует.

## Идемпотентность

| Ситуация | Действие |
|---|---|
| ОП вернул `201` | Заказ создан, состояние сохраняется как `succeeded` |
| ОП вернул `200` | Повтор: заказ уже был, данные берутся из ответа |
| Таймаут / сетевая ошибка | `GET /api/v2/internal/orders/by-external-approval/{id}`; `200` — сохранить, `404` — повторить создание |

Состояние попытки хранится в `offer_implementations` в границе `(approval_id, offer_id)`:
статус, число попыток, последняя ошибка, хеш предмета, ключ идемпотентности.

Правила пропуска:

- оффер с успешной попыткой **в этой же версии** — заказ не пересоздаётся;
- оффер, по которому заказ создан **в любой прошлой версии**, тоже пропускается: заказ
  принадлежит офферу, а не версии. Иначе правка состава давала бы второй заказ на ту же
  услугу, а связь оффера с заказом (уникальная по офферу) перезаписалась бы и первый заказ
  потерялся бы для Кометы. Неуспешная запись текущей версии при этом закрывается ранее
  созданным заказом, чтобы база не расходилась с ответом;
- оффер, отсутствующий в снимке (пересборка не состоялась после его добавления),
  останавливает имплементацию: иначе он молча остался бы без заказа, а сделка отчиталась бы
  как переданная целиком.

Сбой одного оффера не отменяет остальные: ответ содержит отчёт по каждому, а сделка
считается переданной только при полном успехе. Частичный провал — **422**
`deal_implementation_incomplete` с причиной по каждому упавшему офферу
([[Видимая причина провала имплементации]]); до 2026-08-19 это был 409 с одним лишь
перечнем идентификаторов.


## Версии согласования и правки состава

- Версия, по которой уже созданы заказы, при пересборке **не переписывается на месте** —
  заводится новая. Ключ идемпотентности считается от версии, поэтому правка поверх
  отправленной версии сделала бы новый состав неотличимым от прежнего. Учитываются только
  успешные попытки: версию с одними неудачами нужно переиспользовать, иначе повтор ушёл бы
  в ОП с новым ключом и создал второй заказ.
- Состав сделки, переданной в ОП, **больше не редактируется**: страж предмета согласования
  отклоняет изменение сделки и офферов с кодом `deal_already_implemented`. Изменение услуги
  оформляется в ОП отдельным типом заказа, а не повторной отправкой сделки.

## Что сохраняется в Комете

`OfferOrderModel` (`app/models/offer_order.py`), одна строка на оффер:

```
offer_id      FK → offer.id (CASCADE), unique
order_id      UUID БЗ в ОП
order_number  номер БЗ
order_status  itsm_state на момент создания
kp_phase_code снимок КП-фазы оффера
kp_phase_at   время перехода в неё
```

Снимок КП-фазы — первая точка мини-таймлайна карточки оффера: фаза вычисляется из
состояния согласования, а оно уедет вперёд. Для одобренной сделки это «КП согласовано» с
временем решения; для сделки с пустым маршрутом — «КП сформировано» без времени, потому что
решения не было ни у кого (то же значение возвращает и живой расчёт фазы).

Актуальный статус заказа не хранится: он читается из ОП на каждый запрос сделки.

## Логирование

При каждом обращении к ОП пишутся `external_approval_id`, `offer_id`, `order_id`,
`order_number` и исход (`created` / `reused` / `failed`), а по завершении сделки — сводка
`total / succeeded / failed / reused`.
