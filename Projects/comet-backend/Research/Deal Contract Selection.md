# Deal Contract Selection

#research #deal #contracts

Связано: [[DFDEV-2257 Deal Contract Selection]], [[API]], [[Domain Model]],
[[Offer Actions Rules]].

Договор сделки: выбор при создании и вычисляемый тип договора (DFDEV-2257).
Постановка: БТ03 «Функционал управления сделками», раздел «Создание новой сделки».

## Что изменилось

Раньше менеджер искал клиента по ИНН, а договор подставлял бэк — молча и поздно, на
имплементации: `implement_deal` искал у родительского клиента продавца договор с
номером `TST*`, при отсутствии создавал новый и перетирал `deal.contract_id`.
Менеджер не управлял ни договором, ни, соответственно, типом сделки, а тип был
не виден в карточке до имплементации.

Теперь договор определяется при создании сделки:

1. **Договор пришёл** (`contract_id` в теле запроса) — сделка коммерческая. Договор
   валидируется и сохраняется как есть, TST-ветка не выполняется.
2. **Договор не пришёл** — сделка тестовая. Логика прежняя: у родительского клиента
   продавца ищется тестовый договор клиента, при отсутствии создаётся новый.
   Изменился только момент — при создании сделки, а не при имплементации.
3. **После создания договор не меняется** — по аналогии с контрагентом (БТ03,
   «Общие данные», требование 5).

Тестовый договор остаётся внутренней абстракцией: клиент о нём не знает, менеджер
его не выбирает.

## Тип договора

Тип нигде не хранится — отдельной колонки на сделке нет, тип вычисляется по номеру
договора (`app/helpers/contract_types.py`). Логика повторяет `ContractFullType` из
Order Processing (`app/services/contracts/contract_helpers.py`), чтобы подписи
совпадали в обоих сервисах:

| Условие по номеру | `contract_type` | `contract_type_title` |
|---|---|---|
| номер начинается с `TST` | `test` | Тестовый |
| номер `DF0001` | `inner` | Внутренний |
| остальное (и договор без номера) | `commercial` | Коммерческий |

Вторая ось ОП (`ContractClientType`: прямой / партнёрский / для внешних
пользователей API) в ЛКМ не используется.

### Про `INNER_DF_CONTRACT`

В ОП есть `INNER_DF_CONTRACT = ('DF0001', 'TST0563', 'DF1302')` (`app/constants.py`).
Внутренним при классификации считается только `DF0001`: расхождение почти мнимое —
`TST0563` в `ContractFullType` всё равно попадает в `test`, потому что префикс `TST`
проверяется первым, а сам кортеж используется только в ITSM-задачах ОП как защита
«от внутренних договоров не отвязываем услуги и пулы». Расходится один `DF1302`.
Если аналитика решит иначе, правка — кортеж `INNER_CONTRACT_NUMBERS`.

## API

### Список договоров для выбора

`GET /api/v1/customers/contracts?child_client_id=<клиент сделки>&seller=<продавец>`

- `seller` (`datafort` / `vimpelcom`) бэк разворачивает в `parent_client_id`
  продавца — фронту UUID родительских клиентов знать не нужно
  (`SELLER_PARENT_CLIENT_IDS` в `app/helpers/constants.py`);
- удалённые договоры не отдаются: `is_deleted=false` подставляется по умолчанию,
  вернуть их можно явным `is_deleted=true`;
- отдаются **все** типы договоров — фильтрацию и группировку делает фронт;
- каждый договор дополнен `contract_type` и `contract_type_title`;
- `seller` вместе с не совпадающим `parent_client_id` → 400.

Те же поля есть в `GET /api/v1/customers/contracts/{id}`.

### Создание сделки

`POST /api/v1/deals` принимает необязательный `contract_id`. Переданный договор
проверяется одним запросом в customers: он должен принадлежать клиенту сделки
(`child_client_id`), быть не удалён и относиться к родительскому клиенту продавца.
Наличие договора в ответе проверяется по id, поэтому результат не зависит от того,
поддерживает ли customers фильтр `id__in`. Ошибка — 400, «Договор не найден у
выбранного клиента или удалён».

### Изменение сделки

`PATCH /api/v1/deals/{id}` поля `contract_id` больше не принимает — при
`extra="forbid"` попытка передать его возвращает 422.

### Сделка в ответе

`DealSchema` отдаёт `contract_id`, `contract_number`, `contract_type`,
`contract_type_title` — и в карточке, и в списке. Номер договора в сделке не
хранится, поэтому договоры подтягиваются из customers **одним** запросом по `id__in`
на страницу списка (`DealService._load_deal_contracts`). Если customers недоступен,
сделки отдаются с пустыми полями типа, а ошибка пишется в лог — список не падает.

## Легаси-сделки

Сделки, созданные до этого изменения и не дошедшие до имплементации, лежат с
`contract_id IS NULL`. Для них в `DealService._ensure_legacy_deal_contract` осталась
временная страховка: договор проставляется на имплементации, как раньше, с WARNING
в логе. Разовый бэкфилл — `scripts/backfill_deal_contracts.py` (без флагов только
считает объём, с `--apply` проставляет договоры). После бэкфилла страховку и
внутреннюю схему `DealContractUpdateSchema` можно удалить.
