# DFDEV-2695 — предтариф без продукта в бумажном оффере

#project #ticket #pre-tariff

Задача: [DFDEV-2695](https://btask.beeline.ru/browse/DFDEV-2695).

Связанные материалы: [[Предтариф как черновик тарифа]],
[[Офферы бумажных продуктов — правила сборки и проверок]],
[[Черновик тарифа публикуется при отправке заказа]].

## Статус

Реализовано локально 29.09.2026. Для подтверждённого бумажного продукта общий
валидатор больше не связывает заявку с конкретным `product_id`; digital-проверка и
остальные инварианты сохранены. Изменение применяется при записи оффера, переносе
между сделками и перед публикацией тарифа/отправкой заказа в ОП.

## Проблема

Заявка на предтариф для бумажного продукта может быть создана без `product_id`, но
до реализации общий валидатор позиции оффера безусловно требовал равенства
`pre_tariff.product_id == offer.product_id`. Поэтому корректная заявка с
`product_id = null` отклоняется кодом `pre_tariff_product_mismatch`.

Эта проверка выполняется в трёх сценариях:

1. при создании или изменении состава тарифов оффера;
2. при переносе оффера с уже сохранённым предтарифом в другую сделку;
3. повторно перед публикацией чернового тарифа и отправкой заказа в Order Processing.

Если изменить только первый сценарий, оффер сохранится, но не пройдёт preflight
имплементации.

## Требуемое поведение

| Тип продукта оффера | `product_id` заявки | Результат проверки продукта |
| --- | --- | --- |
| Бумажный | `null` | разрешить |
| Бумажный | равен продукту оффера | разрешить |
| Бумажный | отличается от продукта оффера | разрешить: бумажный предтариф не привязан к продукту |
| Цифровой | равен продукту оффера | разрешить |
| Цифровой | `null` или отличается | отклонить с `pre_tariff_product_mismatch` |
| Тип продукта не подтверждён | любое | не ослаблять проверку, завершить запрос существующей ошибкой классификатора |

Независимо от типа продукта должны сохраниться проверки:

- заявка существует;
- `classifier_tariff_id` заявки равен `pk` позиции оффера;
- текущий пользователь вправе использовать заявку;
- количество входит в `min`/`max` и соответствует `step`;
- перед имплементацией заявка согласована, черновик тарифа существует и пригоден к
  публикации;
- для цифрового продукта остаются проверки `group_code` и принадлежности группы дереву.

## Проектное решение

Сделать режим проверки продукта явным обязательным параметром общего валидатора,
например `product_is_paper: bool`, без значения по умолчанию. Проверку равенства
`product_id` пропускать только при `product_is_paper is True`.

Режим нельзя принимать от HTTP-клиента или выводить из `group_code`: его нужно брать
только из уже загруженных доверенных метаданных классификатора. Обязательный параметр
заставит каждый новый call site осознанно выбрать политику и не позволит случайно
ослабить цифровой сценарий.

## План реализации

### 1. Разделить общие инварианты и paper-only исключение

Файл: `app/services/pre_tariff_binding.py`.

1. Добавить в `validate_pre_tariff_position` обязательный keyword-only параметр
   `product_is_paper`.
2. Оставить порядок общих проверок: существование заявки → совпадение тарифа →
   проверка продукта для digital → ограничения количества.
3. Для подтверждённого бумажного продукта не сравнивать `pre_tariff.product_id` с
   `product_id`.
4. Для любого небумажного режима сохранить текущую ошибку
   `pre_tariff_product_mismatch` и её публичный код.

### 2. Передавать тип продукта при записи оффера

Файл: `app/services/offer.py`.

1. Добавить обязательный `product_is_paper` в `_get_pre_tariff_positions` и передать
   его в общий валидатор.
2. В `_normalize_tariff_selection` использовать уже загруженное
   `ProductMetadata.is_paper`; дополнительного запроса к классификатору на обычном пути
   не требуется.
3. Не менять последующую развилку тарифов:
   - paper продолжает проверять обычные тарифы по плоскому каталогу;
   - digital продолжает проверять `group_code` и пару тариф/группа по дереву;
   - параметры количества предтарифа продолжают браться из заявки.
4. В ветке переноса оффера между сделками без поля `tariffs` загрузить и распарсить
   метаданные текущего продукта до повторной проверки сохранённых предтарифов, затем
   передать подтверждённый `is_paper`. Ошибка или некорректная форма ответа
   классификатора должны закрывать операцию, а не включать paper-исключение по
   умолчанию.
5. Сохранить действующую проверку владельца/права согласующего при обычной записи и
   действующее управление `check_pre_tariff_ownership` при внутреннем переносе.

### 3. Передавать тип продукта в preflight имплементации

Файл: `app/services/offer_implementation_service.py`.

1. Добавить обязательный `product_is_paper` в `_prepare_offer_pre_tariffs`.
2. В `_preflight_pre_tariff_publication` передавать признак из уже рассчитанной
   `_ProductClassification`: `classification.mode == _ProductMode.PAPER`.
3. Не делать повторный запрос типа продукта и не доверять снимку approval: текущий
   preflight уже классифицирует живой продукт и fail-closed обрабатывает отсутствие
   классификации.
4. Не менять порядок побочных эффектов: все проверки выполняются до публикации
   черновика; публикация и фиксация `published_at` происходят до вызова Order
   Processing; служебный `pre_tariff_id` не уходит во внешний payload.

### 4. Сохранить публичный контракт ошибок

Файл: `app/api/docs/responses.py`.

Код `pre_tariff_product_mismatch` не удалять: он остаётся частью цифрового сценария.
При необходимости уточнить только текст документации, что несовпадение продукта
проверяется для digital; состав HTTP-ответа и коды статусов не менять.

### 5. Добавить регрессионные тесты

Новый файл: `tests/services/test_pre_tariff_binding.py`.

- paper + заявка без продукта проходит;
- paper + legacy-заявка с другим продуктом проходит;
- digital + заявка без продукта получает `pre_tariff_product_mismatch`;
- digital + другой продукт получает тот же код;
- для paper по-прежнему возвращаются точные ошибки отсутствующей заявки,
  несовпадающего тарифа и нарушений `min`/`max`/`step`.

Файл: `tests/services/test_offer.py`.

- нормализация paper-оффера принимает productless-предтариф и сохраняет его параметры
  количества;
- digital-оффер с productless-предтарифом отклоняется даже при валидной группе дерева;
- перенос paper-оффера с уже сохранённым productless-предтарифом без повторной передачи
  `tariffs` проходит проверку по live-метаданным;
- недоступный или некорректный тип продукта при таком переносе не превращается в
  разрешение paper-исключения.

Файл: `tests/services/test_offer_implementation_service.py`.

- согласованный productless-предтариф бумажного оффера проходит полный preflight:
  черновой тариф публикуется, заявка отмечается опубликованной, затем вызывается Order
  Processing;
- в payload ОП отсутствует `pre_tariff_id`, а группа бумажной позиции остаётся
  канонической нулевой группой;
- искусственно сохранённый digital productless-предтариф отклоняется до публикации и до
  вызова ОП;
- неправильный тариф и невалидное количество по-прежнему останавливают preflight до
  побочных эффектов.

Файл `tests/api/docs/test_responses.py` менять только если уточняется описание ошибки;
проверку наличия `pre_tariff_product_mismatch` сохранить.

## Проверка

После реализации выполнить последовательно:

```bash
poetry run pytest tests/services/test_pre_tariff_binding.py tests/services/test_offer.py \
  tests/services/test_offer_implementation_service.py tests/api/docs/test_responses.py -q
poetry run pytest -q
poetry run make check
```

Ручной контрактный сценарий на тестовом стенде:

1. создать заявку на предтариф без продукта с ограничениями количества;
2. согласовать её финансовым директором;
3. добавить тариф заявки в оффер подтверждённого бумажного продукта;
4. убедиться, что создание/изменение оффера не возвращает
   `pre_tariff_product_mismatch`;
5. провести сделку по маршруту и отправить в работу;
6. проверить, что черновик опубликован как тариф, заказ создан в ОП, количество и цена
   совпадают со снимком согласования;
7. отдельно проверить отказ для количества вне диапазона и для несовпадающего
   `classifier_tariff_id`;
8. повторить productless-сценарий с цифровым продуктом и убедиться, что он по-прежнему
   отклоняется.

## Миграции и совместимость

Миграция БД не нужна: `pre_tariff.product_id` уже nullable, новые поля и ограничения
схемы не вводятся. Формат API и сохранённых JSON-снимков не меняется. Изменение
расширяет допустимое поведение только для продукта, который классификатор достоверно
пометил как бумажный.

## Риски и меры

- **Ослабление digital-проверки.** Закрывается обязательным параметром без default и
  негативными тестами обоих digital-вариантов.
- **Расхождение записи и имплементации.** Оба пути используют один валидатор и один
  смысл признака paper, полученный из классификатора.
- **Побочные эффекты до обнаружения ошибки.** Негативные тесты фиксируют отсутствие
  публикации и вызова ОП при ошибке тарифа/количества/product binding.
- **Legacy-записи с чужим `product_id`.** Для подтверждённого paper они намеренно
  разрешаются: по требованиям бумажный предтариф не связан с конкретным продуктом.
- **Недоступность классификатора.** Операция остаётся fail-closed; `null`, отсутствие
  поля или некорректный ответ не трактуются как бумажный продукт.

## Граница задачи

Не входят в DFDEV-2695: изменение модели создания предтарифа, новая миграция,
ослабление правил цифровых продуктов (отдельная DFDEV-2556), изменение маршрута
согласования, логики публикации или внешнего контракта Order Processing.
