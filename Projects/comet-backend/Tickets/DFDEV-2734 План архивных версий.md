# DFDEV-2734 План архивных версий

#project

Задача: https://btask.beeline.ru/browse/DFDEV-2734. Реализация разрешена пользователем 2026-10-13 после обновления документации. Объём тикета: только `comet-backend`; frontend, ОП и классификатор не редактируются. Контракт классификатора: https://gitlab.datafort.ru/dev/service-catalog/-/merge_requests/142. Контракт ОП: https://gitlab.datafort.ru/dev/order-processing/-/merge_requests/1828. Ниже сохранён согласованный план; фактически реализованные ручки и поля описаны в [[API]], а детали потока — в [[Architecture]].

## Согласованное поведение

- Новую продажу разрешать только если `is_active=true` и `archived_at=null`. Отсутствие обязательного поля, конфликт значений, 404 и сбой классификатора блокируют операции, которым нужна проверка продукта. Локальный fallback не добавлять. Физическое удаление версии считаем невозможным по контракту классификатора.
- Старый архивный оффер доступен для чтения, включая историю и вложения; обычное редактирование, удаление, перенос, новое согласование и новый заказ запрещены. Внешняя архивация автоматически не отзывает уже идущее согласование.
- Смена версии сохраняет `offer_id` и `product_line_id`. Историю прежнего состава сохранять и для черновика. Менеджер заново выбирает тарифы, цены и технические параметры. Два оффера одной линейки только ради истории не создавать.
- Для ожидающего согласования сначала требуется ручной отзыв. Уже одобренное, но ни разу не отправлявшееся в ОП согласование пометить superseded и согласовать новый состав заново. После фактически начатого POST смену версии этим действием не разрешать.
- Полностью архивную линейку оставлять в каталоге видимой, но отключённой.
- При сбое классификатора новый POST не делать. Допускается только чтение ОП по `external_approval_id` для сверки ранее начатой отправки. Часовая задержка свежести кэша продукта в ОП после архивации — известный риск за рамками этой реализации; менять кэш без отдельного решения бизнеса не нужно.

## 1. Контракт и порядок выпуска

1. До включения фактической архивации выпустить совместимые со старым контрактом проверки Comet для PATCH, нового согласования и pre-POST. Старый классификатор не архивирует версии, поэтому отсутствие новых полей на этой стадии допустимо только как временная совместимость.
2. Выпустить MR 142 классификатора. Проверить, что старый `product_id` читается, ответ содержит `product_line_id`, `is_active` и обязательный nullable `archived_at`.
3. Перед MR 1828 ОП дождаться истечения старого Redis product cache не меньше часа после переключения классификатора либо адресно удалить старые записи и проверить новый ответ. Новая схема ОП требует полей, которых нет в старом ответе.
4. Выпустить MR 1828 ОП, полную строгую версию comet-backend и затем frontend. До завершения последовательности фактическую архивацию не включать, в том числе для других клиентов ОП.

## 2. Backend: схемы, каталог и запреты

- Добавить обязательный `is_active` в `ProductMetadata`, сделать его строгим во всех продуктовых схемах; `product_line_id` сделать обязательным, `archived_at` — обязательным nullable. Убрать временные fallback-значения. Общий predicate `is_active is True and archived_at is None` использовать в выборе продукта, create, всех вариантах PATCH, смене версии, старте согласования и перед POST. Историческое чтение старого ID допускает архивный продукт.
- В меню выбирать текущую версию линии; если вся линейка архивна, показывать последнюю архивную с причиной недоступности. При ошибке классификатора не менять DB/S3.
- Guard архивного оффера ставить в сервисном слое до ветвления PATCH по `tariffs`: проверить `None` (отсутствие поля и `null` кодом неразличимы), `[]`, непустой список, перенос через `deal_id`; отдельно закрыть upload/delete вложений, удаление одного оффера, удаление офферов сделки и каскадное удаление сделки с архивным оффером. Явная смена версии — единственное исключение.
- После `FAILED` preflight с `post_started_at=NULL` разрешить настройку новой версии. При частичном успехе сделки разрешить менять только неотправленный offer ID. Для этого пересмотреть `OfferService.ensure_action_allowed`, `deal_has_orders`, `ApprovalSubjectGuard`, `_update_locked`/rebuild и отдельный deal-wide gate `OfferAttachmentService._lock_offer_deal_for_change`. Состав уже отправленных офферов и общие поля сделки, влияющие на их заказы, остаются закрытыми. Те же разрешённые действия должен показывать frontend.

## 3. Backend: смена версии и история

- Добавить `change_version`, `finalize`, history-модель/миграцию и сохраняемый `version_change_pending`. Целевая версия должна быть активной, неархивной и той же линии. В одной блокировке offer/deal проверить согласование и записи отправки: запрет при pending/blocked approval, `post_started_at IS NOT NULL` для данного оффера или найденном заказе. Простая claim-запись или достоверный отказ до HTTP POST смену не блокирует.
- Транзакционно сохранить старые `product_id`, тарифы и цены, технические параметры, особые условия, ID и метаданные вложений, ссылку на согласование — в том числе у draft. Историю не удалять по TTL. Старые вложения убрать из активного состава, сохранить файлы и историческое скачивание с проверкой прав.
- Под `pre_tariff_lock` сохранить старые привязки в истории и убрать из активного состава. Цифровой предтариф со старым `product_id` не переносить; для бумажного продукта учесть разрешённую привязку без `product_id`. Уже состоявшуюся публикацию тарифа в классификаторе не откатывать. Для новой версии менеджер подбирает предтарифы, которые проходят обычную проверку и публикацию.
- Поменять `offer.product_id`, очистить поля прежней версии и поставить `version_change_pending`. Пока флаг установлен, разрешить заполнение нового состава и загрузку новых вложений, но закрыть согласование и отправку заказа даже при маршруте `NOT_REQUIRED`. `finalize` проверяет полноту состава, тип продукта и eligibility, затем снимает флаг. Новый snapshot/route строить при явном новом запросе согласования.

## 4. Согласование и отправка в ОП

- При каждом draft/rebuild вычислять eligibility для всех офферов, включая не имеющие `special_conditions`. Недоступность сохранять как причину в draft, не откатывая редактирование активного соседа или ручной отзыв. Отзыв по-прежнему создаёт current draft. Отдельный guard блокирует запуск нового согласования при недоступной версии.
- В `create_for_deal` сохранить текущий timeout → GET → возможный retry механизм, расширяя один общий recovery helper. При повторном запуске для начатой, но неподтверждённой отправки сначала выполнить GET ОП по детерминированному `external_approval_id`, до классификации, claim и preflight. Найденный заказ записать как success; если GET не ответил, оставить исход неопределённым и не делать POST. Неоднозначный 5xx тоже требует GET до повторной отправки.
- После GET=404 продолжить подготовку и перед каждым новым POST, включая retry, повторно проверить по классификатору `product_id` из актуального approved snapshot. Существующий subject-match проверяет совпадение ID, но не архивность.
- Разделить нынешний общий preflight-барьер `post_started_at` по офферам: для каждого ставить маркер после его финальной eligibility-проверки, непосредственно перед HTTP POST; сохранить блокировки и проверку неизменности snapshot. Ошибка до этого шага оставляет маркер пустым. После установки маркера и обрыва процесса исход считать неопределённым до read-only сверки с ОП.
- Уже успешные заказы не менять. Payload брать из текущего одобренного snapshot.

## 5. Зависимости вне объёма этой реализации

- API backend должен отдать поля версии, архивности, причины блокировки и `version_change_pending`, необходимые клиенту. Реализация интерфейса frontend — отдельная задача.
- Контракт ОП сверяется с MR 1828; исходный код ОП в этом тикете не меняется. Риск часового кэша после новой архивации остаётся отдельно задокументированным.

## 6. Проверки перед выпуском

- Comet: матрица `missing/null/false/archived`, полностью архивная линейка, все PATCH/DELETE/attachments, история draft/approved и скачивание, предтариф старой и новой версии, ручной revoke с current draft, `NOT_REQUIRED` при pending, отказ до POST с разрешённой сменой, частичный успех, архивирование между approval и POST, сбой классификатора, GET recovery `200/404/ошибка`, повторная проверка перед retry.
- Frontend и ОП проверяются как внешние зависимости, без правок в их репозиториях.
- На момент планирования неизменённый comet-backend: `poetry run pytest -q` дал `3 failed, 1480 passed` (все три в `tests/services/test_deal_clients.py`); `poetry run make check` — все проверки Passed. При реализации выполнить оба прогона вновь и отдельно разобрать эти базовые падения.
