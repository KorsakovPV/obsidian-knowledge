# Unblock Blocked Approval

#project #ticket #approval

Связано: [[Architecture]], [[LKM Role Model]], [[Sequential KP Approval]],
[[Offer Actions Rules]].

Дать выход из состояния `blocked` без пересборки маршрута: сейчас согласование,
заблокированное отсутствием согласующего, не оживает после выдачи права.

## Проблема

Кейс с тестирования 2026-08-11 (Артём Паршутин): маршрут дошёл до стадии «Юрист» →
`BLOCKED: Не найден согласующий с правом approve_kp_lawyer`. После этого нужному
пользователю выдали право — но согласование осталось заблокированным навсегда.

Две составляющие:

1. **Права единоличных стадий не входят в роли** (это by design, БТ02): `approve_kp_lawyer`,
   `approve_kp_sales_director`, `approve_kp_finance_director` выдаются только
   персонально (`PATCH /lkm/users/{id}/permissions`). Назначение роли «юрист» права
   не даёт — обладателей ноль → активация стадии блокирует процесс. Дополнительная
   ловушка: смена роли **сбрасывает** персональные права.
2. **Из `blocked` нет публичного выхода.** В workflow есть готовый
   `ApprovalWorkflowService.retry_activation` (событие `activation_retried`,
   `app/services/approval_workflow.py`), но публичной ручки нет — отложена «до
   утверждения permission-контракта». Автоматического ре-скана «появился обладатель
   права» тоже нет.

**Обход сейчас:** выдать право → `POST /deals/{id}/approval/revoke` → отправить
заново. Цена — маршрут проходится с первой стадии (новая версия согласования).

## Варианты решения

### Вариант A (рекомендуемый): «толкнуть» той же ручкой отправки на согласование

`POST /deals/{deal_id}/approval/request` получает семантику «запустить или толкнуть»:

- draft / нет активного согласования → как сейчас, пересборка и старт;
- **blocked → `retry_activation`**: маршрут НЕ пересобирается, пройденные стадии
  сохраняются, оживает только застрявшая waiting-стадия; если согласующий всё ещё
  не найден — процесс штатно остаётся blocked;
- pending → прежний 409 «уже запущено».

Плюсы: не нужен новый permission-контракт (право то же `SEND_KP`, у
менеджера-инициатора), не нужна новая кнопка на фронте, поведение предсказуемо
(без фоновой магии).

Нюансы реализации:

1. **Action resolver**: `request_approval` сейчас недоступен при активном
   согласовании — разрешить его в состоянии blocked (и вернуть кнопку на фронте).
2. **Конфликт с локом файла КП**: замена вложения запрещена при `pending`/`blocked`
   (409 `approval_subject_locked`). Фронту правило: при blocked **не загружать
   файл**, только дёргать request — иначе 409 на загрузке до толчка.
3. **Идемпотентность**: повторный толчок без выданного права снова возвращает
   blocked; событие `activation_retried` на каждый явный толчок — приемлемый аудит.

### Вариант B: отдельная публичная ручка retry

`POST /deals/{deal_id}/approval/retry-activation` поверх готового метода. Требует
решения по правам (инициатор? `change_permissions`? админ?) — то самое, из-за чего
ручка и была отложена. Оставить как админский запасной выход, если A окажется мало.

### Вариант C: авто-ретрай при появлении права

Хук в точках, где право может появиться (`PATCH /lkm/users/{id}/permissions`,
`PATCH .../role`, `POST /lkm/users`): найти blocked-согласования с
`blocked_permission` из выданного набора и вызвать `retry_activation`. Лучший UX
(«выдал право — ожило само»), но: ретрай пачки согласований, `scope_product_ids`
у владельца продукта (право с чужим scope не оживит стадию — холостой ретрай),
ошибки селектора должны штатно возвращать blocked, а не 500. После варианта A
скорее всего не нужен.

## Критерии приёмки (для варианта A)

- Blocked-согласование после выдачи права оживает повторной отправкой на
  согласование с той же стадии; пройденные стадии не повторяются.
- Толчок без выданного права оставляет blocked без ошибки 5xx.
- Pending-согласование по-прежнему отвечает 409.
- Действие `request_approval` доступно (resolver + фронт) в состоянии blocked.
- Событие `activation_retried` пишется в историю стадий.
