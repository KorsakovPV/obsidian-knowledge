# DFDEV-2044 Multi Product Approval

Дефект: в сделке с несколькими продуктами после согласования и имплементации в ОП
появлялось несколько заказов, но согласованным был **только один**.

## Причина

Количество продуктов ни при чём — совпадение в том, что при одном продукте дефект
незаметен. Имплементация ветвилась по агрегатному статусу сделки: предсогласованные
заказы создавались только для `approved`, всё остальное шло обычным путём создания
заказов. А отправка в имплементацию разрешена ещё и для `not_required` — маршрут пуст,
скидка в пределах лимита и особых условий нет, согласовывать нечего.

По обычному пути про согласование решает **сам ОП, отдельно по каждому заказу**: продукт
из его списка автосогласования (`AUTO_APPROVE_PRODUCTS_IDS` — YellowBe, Cloud Interconnect,
Доступ в сеть Интернет, Cloud SD-WAN, Cloud CDN) получает «Согласован», остальные —
«Требует согласования». Отсюда «несколько заказов, согласован ровно один».

## Решение

Принято считать «в Комете согласование не требовалось» равным «заказ согласован» для ОП —
та же модель доверия, что уже зафиксирована для предсогласованных составов, просто решение
принимает правило маршрута, а не человек.

- Гейт имплементации пропускает версию, **прошедшую свой маршрут**, включая пустой;
  ветка с обычными заказами из имплементации убрана.
- Сделка без единой версии согласования больше не проезжает мимо согласования: версия
  готовится на месте, пустой маршрут — работаем, непустой — отказ.
- Заодно закрыт куст регрессий, найденных ревью: неизменяемость версии с созданными
  заказами, пропуск оффера с уже созданным заказом, запрет правки состава после передачи
  в работу, проверка покрытия snapshot живыми офферами, свежий ответ ручки.

Механика описана в [[Architecture]] (раздел «Согласование»), контракт интеграции —
в [[Preapproved Order Integration]] (заметка устарела относительно кода, см. ниже).

## Статус на 14.08.2026

Код готов и запушен в ветку `DFDEV-2044`; полный набор тестов зелёный. Приёмка на стенде
не пройдена по внешним причинам: на stage в ITSM отсутствовало соглашение с номером
договора (`not found agreement` в логах воркера), на тестовом контуре не работает
`order-processing-worker`, поэтому задача создания БЗ в ITSM не выполняется вовсе. Оба
препятствия к этому тикету отношения не имеют — заказы в ОП создаются согласованными.

## Осталось за рамками

- Кнопка редактирования сделки не знает про запрет правки после имплементации: отказ
  приходит с сервера, а не гасит действие заранее. Нужен признак «по сделке есть заказы»
  в контексте действий, с загрузкой пачкой для списка сделок.
- Отказ «нужно согласование» не пересчитывает маршрут, если версия `not_required` уже
  лежит: изменение правил маршрута на сервере без правки сделки не будет учтено.
- Ключ идемпотентности считается от версии согласования, а не от состава оффера. Сейчас
  это компенсировано пропуском уже созданных заказов и запретом правки, но правильная
  модель — ключ от состава: тогда изменённый оффер доезжает, а неизменённый не дублируется.
  Меняет формулу ключа, поэтому требует разбора уже созданных заказов.
