# DFDEV-2555 — маршрут согласования по уровням цен тарифов

#project #ticket #approval #pricing

Связано: [[Architecture]], [[API]], [[Domain Model]],
[[Discount Base and Personal Price]], [[Sequential KP Approval]].

## Статус

Планирование. Код DFDEV-2555 в Comet ещё не реализован. Целевой контракт и rollout
полностью согласованы 24.09.2026; открытых вопросов для начала реализации нет.

Полный журнал обсуждённых вопросов и ответов ведётся в
[[Discount Base and Personal Price#Тикет DFDEV-2555]].

## Задача

Заменить общие процентные пороги маршрута согласования на индивидуальные уровни цен
тарифа из service-catalog. Одновременно дать фронту отдельную версию тарифной ручки,
которая возвращает те же данные, что текущая, плюс `price_levels`.

## Что есть сейчас

### Каталог

- `GET /api/v1/tariffs` принимает `client_id`, фильтры, пагинацию и отдаёт опубликованные
  тарифы с действующей персональной ценой клиента.
- Comet рассчитывает `default_price`, `partner_price`, минимальные цены и `custom_price`,
  но текущие схемы отбрасывают `price_levels` из ответа service-catalog.
- Весь публичный API Comet сейчас собран только под `/api/v1`; инфраструктуры `/api/v2`
  ещё нет.

### Цены оффера

Фронт передаёт в тарифе:

- `price` — цену продажи; схема допускает `null`, но сервис фактически требует значение;
- `partner_client_price` — опциональную цену конечного потребителя.

Если `partner_client_price` не передана, сервер выводит её из `price`: для DataFort цены
совпадают, для ВымпелКом действует `partner_client_price = price * 1.1`.

В `offer.tariffs` (JSONB) сохраняются `price`, `partner_client_price`, `base_price`,
`base_price_source` и `discount_percent`. GPL и L1–L3 отдельно пока не сохраняются.

### Согласование

Текущий `ApprovalRouteBuilder` выбирает максимальную процентную скидку сделки:

| Скидка | Скидочные стадии |
|---|---|
| `<= 10%` | нет |
| `(10%; 15%]` | Pre-sale |
| `(15%; 20%]` | Pre-sale → руководитель Pre-sale |
| `> 20%` | Pre-sale → руководитель Pre-sale → коммерческий → финансовый директор |

Builder синхронный и выполняется под блокировкой строки сделки. Он не должен ходить во
внешние сервисы. `subject_snapshot` и `route_context` сохраняются в версии согласования.

### Контракт service-catalog

Service-catalog уже возвращает у тарифа абсолютные денежные цены уровней, а не проценты
скидки:

```json
"price_levels": [
  {"level": 1, "price": "900.000000"},
  {"level": 2, "price": "800.000000"},
  {"level": 3, "price": "700.000000"}
]
```

Список упорядочен по `level`; для тарифа без настроек upstream возвращает `[]`.
На уровне модели service-catalog номер и цена положительные, номер уникален внутри тарифа.
При этом upstream технически допускает неполный набор и номера кроме 1–3, поэтому Comet
должен отдельно проверять согласованный бизнес-контракт.

## Целевой бизнес-контракт

### Сравниваемая цена

GPL и L1–L3 находятся в шкале цены конечного потребителя. Для любого организатора продаж
с ними сравнивается `partner_client_price`, а не `price`:

- DataFort: при отсутствии явного значения `partner_client_price = price`;
- ВымпелКом: при отсутствии явного значения `partner_client_price = price * 1.1`;
- если фронт передал `partner_client_price` явно, используется это значение без обратного
  вывода из `price`;
- GPL и L1–L3 для ВымпелКом не делятся на `1.1`: партнёрская цена продажи `price` не
  участвует в выборе уровня;
- `price` остаётся ценой продажи для заказа и текущего legacy-расчёта скидки, пока
  DFDEV-2555 не реализован.

Таким образом, один и тот же денежный смысл используется в персональных воротах и шкале
уровней: сколько фактически платит конечный потребитель.

### Валидность шкалы

- Должны присутствовать ровно три записи с номерами `1`, `2`, `3`.
- Цены разных уровней могут совпадать.
- Валидный порядок: `GPL >= L1 >= L2 >= L3 > 0`.
- Пустой или неполный набор, повтор номера, дополнительный номер, нулевая цена, уровень
  выше GPL или рост цены с номером уровня считаются невалидными.
- Невалидный набор блокирует отправку всей сделки; fallback на старый снимок не применяется.

### Диапазоны

| `partner_client_price` | Результат |
|---|---|
| `partner_client_price >= GPL` | согласование скидки не требуется |
| `GPL > partner_client_price >= L1` | уровень 1 |
| `L1 > partner_client_price >= L2` | уровень 2 |
| `L2 > partner_client_price >= L3` | уровень 3 |
| `partner_client_price < L3` | продажа блокируется |

Равенство соседних границ отключает пустой диапазон: `GPL = L1` — L1 недоступен,
`L1 = L2` — L2 недоступен, `L2 = L3` — L3 недоступен. Контракт
`GPL = L1 = L2 = L3 > 0` валиден и означает, что скидка для тарифа не предусмотрена.

### Ввод цены и стадии согласования

«Завести скидку» в интерфейсе ОП означает указать цену тарифа в КП. Отдельной сущности
скидки нет. На бэкенде уровень скидки и право пользователя сохранить цену определяются по
итоговому `partner_client_price`. Строка «Принятие решения» в матрице определяет, кто
вправе сохранить такую цену в КП, но не добавляет этого пользователя в маршрут
согласования собственного решения.

| Уровень | Кто вправе указать цену в КП | Стадии согласования цены |
|---|---|---|
| без скидки (`partner_client_price >= GPL`) | действующие права создания/редактирования КП | нет |
| L1 | Pre-sale; также руководитель Pre-sale | руководитель Pre-sale |
| L2 | руководитель Pre-sale | коммерческий директор |
| L3 | руководитель Pre-sale | коммерческий → финансовый директор |

Обычный Pre-sale может добавить тариф и сохранить скидочную цену только в диапазоне L1:
`GPL > partner_client_price >= L1`. Для цены из диапазона L2 или L3 в редактирование КП
должен зайти руководитель Pre-sale. Цена ниже L3 блокируется независимо от роли.

Ограничение должно проверяться на бэкенде при создании и изменении оффера; блокировка поля
на фронте — только UX. Руководитель Pre-sale имеет право сохранить и цену L1, то есть права
иерархичны.

Часть маршрута, вызванная особыми условиями, не меняется: оффер с непустыми
`special_conditions` по-прежнему добавляет владельца продукта и юриста. Эти стадии
объединяются с ценовыми стадиями в общем каноническом порядке и не заменяются ими.

Если в сделке несколько тарифов, выбирается максимальный требуемый уровень; ценовые
маршруты отдельных тарифов не объединяются.

### Персональная цена

Сохраняется текущее правило ворот: `partner_client_price` не ниже действующей персональной
цены клиента не требует согласования скидки; значение ниже персональной цены возвращается
в шкалу GPL/L1–L3, где снова сравнивается именно `partner_client_price`.

Пример: `GPL = 1000`, `L1 = 900`, `L2 = 800`, `L3 = 700`, персональная цена — `850`.
`partner_client_price = 850` не требует согласования. `partner_client_price = 840`
попадает в L2, `750` — в L3, `699` блокирует продажу. Этот пример нужно продублировать в
docstring новой функции расчёта ценового уровня, когда функция появится в коде.

### Актуальность и история

- Перед каждым новым построением или пересчётом маршрута уровни заново читаются из
  service-catalog.
- Использованные GPL, L1–L3, сравниваемая цена и рассчитанный уровень сохраняются в
  immutable snapshot версии согласования.
- Уже запущенные на момент релиза согласования не пересчитываются.
- Черновик, созданный до релиза, при отправке после релиза использует новую логику.
- Недоступность service-catalog или невалидная шкала блокирует операцию без fallback.

## Зафиксированные решения бизнеса

### Шкала сравнения — решено 24.09.2026

Для прямых и партнёрских продаж GPL и L1–L3 сравниваются с ценой конечного потребителя —
`partner_client_price`. `price` в выборе уровня не участвует. Это осознанно сохраняет
явно переданную фронтом цену потребителя, даже если она не равна расчётному
`price * 1.1` для ВымпелКом.

### Ввод скидки и согласование — решено 24.09.2026

- Pre-sale принимает ценовое решение фактом ввода цены уровня L1 в КП; отдельной стадии
  Pre-sale для подтверждения собственной цены нет.
- Руководитель Pre-sale может вводить цены L1–L3. Для L2/L3 обычный Pre-sale цену
  сохранить не может.
- Ценовой маршрут начинается со следующего согласующего: L1 — руководитель Pre-sale,
  L2 — коммерческий директор, L3 — коммерческий и затем финансовый директор.
- Особые условия сохраняют текущий независимый маршрут: владелец продукта + юрист.

### Переключение модели скидок — решено 24.09.2026

- Модель переключается целиком настройкой `APPROVAL_WORKFLOW_DISCOUNT_MODEL` со
  значениями `legacy_percent` и `price_levels`.
- Значение по умолчанию — `legacy_percent`.
- На тестовом стенде включается `price_levels`; на stage и production остаётся
  `legacy_percent` до отдельного решения о продвижении новой модели.
- Переключатель одновременно управляет расчётом маршрута, загрузкой GPL/L1–L3 и
  ограничениями ролей на ввод цены. Частичное включение новой модели запрещено.
- Уже запущенные согласования продолжаются по сохранённым stages и `route_context`.
- При ошибке service-catalog новая модель завершается fail-closed; автоматического
  fallback на процентную модель в рамках отдельного запроса нет.

### Дополнительные решения — решено 24.09.2026

- Предтариф сохраняет отдельное обязательное согласование финансовым директором. Если
  финансовый директор уже добавлен ценовым уровнем L3, в маршруте остаётся одна стадия.
- Невалидная шкала хотя бы одного тарифа блокирует всю сделку; максимум среди остальных
  тарифов не рассчитывается.
- Перед отправкой сделки вместе с GPL/L1–L3 повторно загружается актуальная персональная
  цена клиента.
- Администраторы и технические роли не обходят диапазоны L1–L3. Исключение возможно
  только через отдельное permission, которого в рамках DFDEV-2555 не добавляется.
- Публичный `GET /api/v2/tariffs` сохраняет permissions, параметры, фильтрацию, пагинацию
  и ошибки v1 и добавляет `price_levels`.
- Пустая, неполная или нарушающая бизнес-правила шкала возвращает доменную ошибку
  `409 tariff_price_levels_invalid`; недоступность, timeout, 5xx или структурно битый
  ответ service-catalog возвращают `502 classifier_unavailable`.
- Автоматических retry при обращении к service-catalog пока нет. После первой сетевой
  ошибки, timeout или 5xx Comet возвращает `502 classifier_unavailable` с пользовательским
  сообщением «Не удалось получить актуальные цены тарифов. Попробуйте ещё раз позднее»;
  повтор операции инициирует пользователь.

## План реализации

### 1. Ввести переключатель модели скидок

- Добавить enum `DiscountModel` со значениями `legacy_percent` и `price_levels`.
- Добавить в `ApprovalWorkflowSettings` настройку `discount_model`, читаемую из
  `APPROVAL_WORKFLOW_DISCOUNT_MODEL`, с безопасным default `legacy_percent`.
- Выбирать модель в одном месте до загрузки pricing context и построения маршрута; не
  разбрасывать проверки флага по формулам, API и builder-ам.
- В режиме `legacy_percent` использовать действующий расчёт 10/15/20, не загружать
  GPL/L1–L3 и не применять новый role guard на ввод цены.
- В режиме `price_levels` загружать GPL/L1–L3, применять новый role guard и полностью
  исключить процентные пороги из выбора ценового маршрута.
- Сохранять `discount_model` и версию builder-а в `route_context`, а pricing snapshot —
  только для `price_levels`.
- Не менять активные согласования при переключении. Если сохранённая модель текущего
  `DRAFT`/`NOT_REQUIRED` отличается от выбранной, создавать новую approval-версию, а не
  переписывать маршрут существующей версии.
- Не выполнять автоматический fallback `price_levels → legacy_percent` при ошибке
  service-catalog: смена модели допускается только явной настройкой окружения.

### 2. Ввести тип уровня цены

- Добавить общую Pydantic-схему `TariffPriceLevel(level, price)`.
- Расширить внутренний `ClassifierTariff` полем `price_levels`.
- Не добавлять уровни в клиентские схемы создания/обновления оффера: фронт не должен
  присылать или подменять серверную шкалу.

### 3. Добавить каталог v2

- Создать `app/api/v2/v2_router.py`, подключить его к `/api` рядом с v1.
- Добавить `GET /api/v2/tariffs` с тем же query-контрактом, правами, фильтрацией,
  пагинацией и персонализацией, что у `GET /api/v1/tariffs`.
- Выделить отдельную response-схему v2: все поля v1 плюс `price_levels`.
- Переиспользовать `CatalogService`; v1 не менять.
- Различать структурно битый ответ upstream (`502 classifier_unavailable`) и структурно
  валидный, но неполный или неупорядоченный бизнес-набор (`409
  tariff_price_levels_invalid`). Невалидная шкала не возвращается как успешный ответ.

### 4. Добавить чистый расчёт уровня

- Реализовать одну pure-функцию, принимающую GPL, три уровня и `partner_client_price`.
- В ней же проверять номера, положительность, порядок и равные границы.
- Возвращать `None`, L1, L2 или L3; цену ниже L3 и невалидный контракт оформлять разными
  доменными ошибками.
- Поместить подтверждённый числовой пример персональной цены в docstring этой функции.

### 5. Разделить право ввода цены и согласование

- При create/update оффера вычислять уровень каждой изменяемой цены до записи.
- Для скидочного диапазона L1 разрешать запись Pre-sale и руководителю Pre-sale.
- Для диапазонов L2/L3 разрешать запись только руководителю Pre-sale.
- Цену ниже L3 блокировать для всех ролей; цену без скидки не превращать в уровень.
- Проверять право на сервере по эффективной роли/permission вызывающего, а не доверять
  скрытому или заблокированному полю фронта.
- Не давать администраторам и техническим ролям неявный bypass. В рамках тикета
  исключение не вводится; в будущем оно возможно только отдельным permission.
- Возвращать отдельную доменную ошибку с допустимым для пользователя диапазоном и
  требуемой ролью; точный HTTP-код и текст зафиксировать в API-контракте.
- Не добавлять автора цены в approval route: его действие уже является принятием
  ценового решения.

### 6. Загружать pricing context до DB-lock

Внешний HTTP нельзя переносить внутрь `_rebuild_locked`. Нужен двухфазный поток:

1. Прочитать состав сделки и собрать уникальные tariff ids.
2. Одним или chunked-запросом получить тарифы, уровни и актуальные персональные цены из
   service-catalog.
3. Провалидировать шкалы и сформировать серверный `ApprovalPricingContext`.
4. Войти в транзакцию, заблокировать сделку и убедиться, что pricing-input не изменился:
   те же offer ids, tariff ids и сравниваемые цены.
5. При расхождении вернуть workflow-conflict для безопасного повтора, не строить маршрут
   по данным другого состава.
6. Передать готовый context синхронному builder без сетевых вызовов.

Для create/update уже используется fingerprint сделки вокруг `_locked_offer_mutation`;
для `prepare_for_start` нужна аналогичная проверка состава тарифов, а не только product ids.

### 7. Перестроить скидочную часть builder

- Убрать выбор стадий по `10/15/20` для новых rebuild.
- По каждому тарифу применить персональные ворота и рассчитать требуемый уровень.
- Выбрать максимальный уровень сделки и построить соответствующую цепочку.
- Не включать в цепочку того, кто ввёл цену: L1 → руководитель Pre-sale, L2 → коммерческий
  директор, L3 → коммерческий и финансовый директора.
- Особые условия обрабатывать отдельно и объединять с ценовым маршрутом без изменения
  действующего набора `PRODUCT_OWNER + LAWYER`.
- Для каждого предтарифа сохранять обязательную стадию финансового директора; при L3
  дедуплицировать её с финансовым директором ценового маршрута.
- Повысить `BUILDER_VERSION` и записывать версию правил в `route_context`.

### 8. Сохранить объяснимый snapshot

Добавить в `subject_snapshot` отдельный серверный блок, например:

```json
"pricing": {
  "schema_version": 1,
  "tariffs": [
    {
      "offer_id": "...",
      "tariff_id": 42,
      "gpl": "1000.00",
      "levels": {"1": "900.00", "2": "800.00", "3": "700.00"},
      "comparison_price_kind": "consumer_price",
      "comparison_price": "840.00",
      "personal_price_gate": false,
      "required_level": 2
    }
  ],
  "required_level": 2
}
```

Snapshot должен различать отсутствие нового блока у legacy-версии, рассчитанное
`required_level = null` и ошибку расчёта. Ошибка не должна сохранять частичный snapshot.

### 9. Сохранить legacy-процессы

- Не выполнять backfill и массовую пересборку активных approvals.
- `pending`/`blocked` продолжают работать по сохранённым stages и snapshot.
- При следующем разрешённом rebuild черновик получает новый pricing snapshot и builder.
- Проверить `hash_subject_like_stored`, чтобы появление блока pricing не инвалидировало
  уже запущенные legacy-согласования.

### 10. Ошибки и наблюдаемость

- Timeout, сеть, 5xx и битая форма service-catalog возвращают
  `502 classifier_unavailable`.
- Пустая, неполная или нарушающая порядок бизнес-шкала возвращает
  `409 tariff_price_levels_invalid`; цена ниже L3 остаётся отдельной доменной причиной
  блокировки.
- Логировать deal id, offer id, tariff id и код причины без полного клиентского payload.
- Добавить метрики блокировок по причинам: unavailable, malformed, missing levels,
  invalid order, below L3.
- Не выполнять автоматические retry. Добавить алерт на всплеск fail-closed отказов до
  включения логики; повтор операции остаётся ручным действием пользователя.

## Тесты

### Unit

- Конфигурация принимает только `legacy_percent`/`price_levels`; default —
  `legacy_percent`.
- `legacy_percent` использует текущие границы 10/15/20, не запрашивает уровни и не
  применяет новый role guard.
- `price_levels` не использует процентные пороги, загружает уровни и применяет новый
  role guard.
- Все точные границы: GPL, L1, L2, L3 и значения на копейку выше/ниже.
- Равенства `GPL=L1`, `L1=L2`, `L2=L3`, все четыре цены равны.
- Нулевые/отрицательные значения, нарушение порядка, отсутствующий, лишний или повторный
  номер уровня.
- Персональная цена: выше, равна и ниже; явно заданная consumer price.
- DataFort и ВымпелКом: уровни сравниваются с `partner_client_price`; отдельно проверить
  вычисленную и явно переданную цену потребителя, не равную `price * 1.1`.
- Права ввода цены: Pre-sale может сохранить границы GPL/L1 и не может L2/L3;
  руководитель Pre-sale может сохранить L1/L2/L3; цена ниже L3 блокируется всем.
- Администратор и техническая роль без отдельного permission не обходят ограничения
  диапазона.
- Несколько тарифов: L1+L3 → L3; один невалидный тариф блокирует всю сделку.
- Точное соответствие маршрутов: L1 → руководитель Pre-sale, L2 → коммерческий директор,
  L3 → коммерческий → финансовый; автор цены в стадии не добавляется.
- Особые условия при любом ценовом уровне сохраняют `PRODUCT_OWNER + LAWYER`, стадии
  дедуплицируются и остаются в каноническом порядке.
- Предтариф сохраняет обязательного финансового директора; комбинация предтарифа с L3
  создаёт одну, а не две стадии финансового директора.

### API и integration

- Каждый новый маршрут сохраняет фактически выбранный `discount_model` в
  `route_context`.
- Смена модели не изменяет активное согласование; для draft с другой сохранённой моделью
  создаётся новая approval-версия.
- Ошибка service-catalog в режиме `price_levels` не запускает процентную модель; в
  `legacy_percent` обращения за GPL/L1–L3 нет.
- v1 не изменился; v2 совпадает с ним кроме `price_levels`.
- Пагинация, фильтры, `pks`, `client_id`, permissions и персональная цена в v2.
- Перед отправкой сделки персональная цена повторно загружается вместе с уровнями; её
  изменение учитывается в расчёте и snapshot.
- Timeout/5xx/malformed дают `502 classifier_unavailable`; пустая, неполная или
  неупорядоченная шкала даёт `409 tariff_price_levels_invalid`.
- При `502 classifier_unavailable` автоматического retry нет; ответ содержит понятный
  пользователю совет повторить действие позднее.
- Create/update оффера отклоняет цену вне диапазона роли до записи и не позволяет обойти
  guard прямым API-запросом.
- HTTP-fetch происходит до захвата deal-lock; изменение состава между fetch и lock даёт
  conflict, а не snapshot чужого состава.
- Rebuild сохраняет pricing snapshot и не выполняет сеть из builder.
- Активный legacy approval не меняется; старый draft при отправке переходит на новую логику.
- История и `hash_subject_like_stored` читают старые snapshots.

## Rollout

1. Выпустить обе модели в одном артефакте с default
   `APPROVAL_WORKFLOW_DISCOUNT_MODEL=legacy_percent`.
2. Настроить окружения:

   | Окружение | `APPROVAL_WORKFLOW_DISCOUNT_MODEL` | Поведение |
   |---|---|---|
   | test | `price_levels` | новая модель GPL/L1–L3 |
   | stage | `legacy_percent` | действующая модель 10/15/20 |
   | production | `legacy_percent` | действующая модель 10/15/20 |

3. На test проверить загрузку уровней, role guard, маршруты L1–L3, особые условия,
   предтарифы, snapshot и отсутствие fallback на старую модель.
4. Собирать метрики рассчитанных уровней и блокировок по причинам: unavailable,
   malformed, missing levels, invalid order, below L3 и forbidden price level.
5. Stage и production не переводить на `price_levels` без отдельного решения и
   обновления конфигурации окружения.
6. Переключение требует согласованного рестарта экземпляров приложения; использовать
   rollout без длительной одновременной работы pod-ов с разными значениями настройки.
7. Не пересобирать активные approvals. Rollback на `legacy_percent` влияет только на
   новые или явно пересобираемые версии и не является fallback отдельного запроса.
