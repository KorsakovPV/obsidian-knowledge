План реализации схемы из [[Предтариф как черновик тарифа]]. Тикеты небольшие, в порядке
реализации, с деталями до файлов — по описанию можно приступать сразу.

(**DFDEV-2282**). Дорожки стартуют параллельно; зависимости указаны в каждом тикете и
сведены в таблицу в конце.

## Дорожка CM — comet-backend

### CM-1. Модель заявки на предтариф — СДЕЛАНО 24.08.2026

**Что сделать.** В `app/models/pre_tariff.py` расширить `PreTariffModel`: `status` (str,
default `draft`; значения `draft`/`review`/`approved`), `classifier_tariff_id` (int, null),
`product_id` (int, null), `client_id`, `deal_id` (UUID, null, без FK-каскада), денормализация
`title` (str), `price`, `cost_price` (Numeric, null), `quantity_params` (JSONB:
`{min, max, step}`, default `{"min": 1}` — ограничения количества v1, см. риск 5),
`decided_by` (str, null), `decided_at` (datetime, null). Новая таблица `pre_tariff_event`:
`pre_tariff_id` (FK CASCADE), `actor`, `actor_role`, `action`, `old_status`, `new_status`,
`created_at` — журнал по образцу `approval_stage_events`. Alembic-миграция (существующие
строки → `draft`, поля nullable). Обновить `app/schemas/pre_tariff.py`: поля + events в
деталке; список — с `status`, `title`, `price`, счётчиком непрочитанных (заглушка до CM-3).

**Критерии.** Миграция обратима; существующие CRUD-ручки работают и отдают новые поля;
события отдаются в `GET /api/v1/pre-tariffs/{id}`.

**Как сделано.** Миграция `c6d7e8f9a0b1` (проверена up → down → up на чистой базе), поля и
журнал — как в тикете. Отступления и решения, принятые по ходу:

- `pre_tariff_status_valid` (check-constraint) и `pre_tariff_classifier_tariff_id_key`
  (partial unique index) — сверх тикета: один черновик классификатора не должен
  согласовываться двумя заявками.
- В журнале нет `sequence`: события одной транзакции упорядочены тай-брейком по `id`
  (uuid6 монотонен), потому что `created_at` в Postgres — время старта транзакции.
- Создание заявки пишет событие `created`: иначе история начинается с первого перехода.
- Список заявок вынесен в отдельную схему (`unread_count`, без чата/вложений/журнала) и
  больше не догружает связи; `unread_count` — ноль до CM-3.
- `PATCH` научен очищать необязательные поля явным `null`; `description`, `title` и
  `quantity_params` очистить нельзя — для них `null` это 422.
- Ручки по-прежнему без permission guards — это CM-2, и до него список видят все.

Уборка соседнего кода чата и вложений, найденная ревью CM-1, вынесена в
[[Уборка кода комментариев и вложений предтарифа]].

### CM-2. Переходы статусов, права, guard удаления — СДЕЛАНО 24.08.2026

Зависит от CM-1.

**Что сделать.** Ручки в `app/api/v1/pre_tariffs/pre_tariff_router.py` + логика в
`services/pre_tariff.py`: `POST /{id}/submit` (`draft → review`, только автор с
`create_tariff`), `POST /{id}/withdraw` (`review → draft`, автор), `POST /{id}/approve`
(`review → approved`, право `approve_tariffs`; финдир не может править поля заявки ни в одном
статусе). Перехода из `approved` нет (решение 3): статус терминальный. Конфликт состояния
(статус уже изменён) → 409, интерфейс перезапрашивает; повтор того же перехода —
идемпотентный 200. Каждый переход пишет `pre_tariff_event`. **Закрыть все ручки предтарифа
правами** (снять TODO, см. [[BT02 Role Model Gaps]]): CRUD — `create_tariff`, approve —
`approve_tariffs`; видимость списка финдиру — все заявки, менеджеру — свои (правило
серверное). `DELETE`: разрешён автору в `draft`/`review`, запрещён в `approved` и всегда
запрещён, если `classifier_tariff_id` встречается в `offer.tariffs` (JSONB-поиск по pk) — с
внятной ошибкой.

**Критерии.** Матрица роль × статус выполняется сервером с уточнением «в `approved` переходов
нет»; 409 и идемпотентность покрыты тестами; журнал пишется; guard удаления работает.

**Как сделано.** Ручки `submit` / `withdraw` / `approve`, политика — в сервисе, переход и
событие — одной транзакцией под `FOR UPDATE`. Решения по ходу:

- Автор берётся из принципала: `created_by`/`updated_by` убраны из входных схем. Без этого
  «только автор» и видимость списка опирались бы на присланное клиентом поле.
- Правка полей разрешена только в `draft` — отправка на согласование замораживает состав
  (решение из ресёрча); в `review` и `approved` — 409 `invalid_status`.
- Права: чтение — `create_tariff` **или** `approve_tariffs` (финдир не держит `create_tariff`
  во всех ролях, а читать заявки обязан), запись и `submit`/`withdraw` — `create_tariff`,
  `approve` — `approve_tariffs`. Теми же правами закрыты чат и вложения: без этого заявка
  закрыта, а переписка по ней открыта всем. Закрывает тикет 5 из [[BT02 Role Model Gaps]].
- Конфликты отдаёт `PreTariffConflictError` → 409 с `code`: `invalid_status` и
  `pre_tariff_in_use`; повтор перехода — 200 с текущим состоянием.
- Удаление проверяет статус тем же запросом, что удаляет: между отдельной проверкой и
  удалением заявку успевают согласовать.
- Использование позиции в офферах ищется JSONB-containment по `pk` (обе формы — число и
  строка, на случай старых записей).

### CM-5. Прокси: создание, правка, публикация черновика

Зависит от CL-3, CL-4, CM-2.

**Что сделать.** В `ClassifierService` — write-методы: `create_draft_tariff(payload)`,
`update_draft_tariff(pk, payload)` (вьюха CL-3), `publish_draft(pk)` (CL-4). Связать с
жизненным циклом заявки: `POST /api/v1/pre-tariffs` принимает payload тарифа (pydantic-схема,
зеркалящая контракт `POST /api/tariffs/`; серверная валидация обязательности всех полей —
заявка «одним описанием» не создаётся), создаёт черновик в классификаторе, пишет
`classifier_tariff_id` и денормализацию; `PATCH` в статусе `draft` проксирует правку;
`approve` вызывает `publish_draft` — 400 (полный дубль) прокидывается финдиру как ошибка
действия (заявка остаётся в `review`). Ошибка сети/таймаут при создании: заявка не создаётся,
ошибка менеджеру; recovery-дублей не требуется (черновики без защиты от дублей — повторное
создание даёт новый черновик, старый менеджер удаляет). 404 по `classifier_tariff_id` при
чтении — пометка ошибки целостности в деталке, не 500.

**Критерии.** Полный цикл `create → edit → submit → approve` проходит и публикует тариф;
конфликт публикации виден финдиру текстом.

**Критерии.** Критерий 10 раздела 9 ТЗ; счётчики синхронны между плашкой, карточкой и деталкой.

### FR-6. Флаг черновика в оффере и КП, сквозная приёмка

Зависит от FR-1, бэк — CM-6.

**Что сделать.** Пробросить `is_draft_tariff` в карточки состава оффера и КП (бейдж из словаря
`entities/pre-tariff`, тот же компонент, что в списке заявок); пояснение у флага — «в оффере и
КП позиция помечена флагом до апрува». Обработать блокировку имплементации (guard CM-6):
сообщение с перечнем позиций, ждущих апрува. Прогнать сквозные сценарии приёмки раздела 9 ТЗ
на реальном бэке; `npm run build` + `npm run lint` без ошибок и предупреждений (критерий 12).

**Критерии.** Черновик визуально отличим в оффере и КП до апрува и становится обычной позицией
после; сквозной сценарий «создать → обсудить → согласовать → продать» проходит.
