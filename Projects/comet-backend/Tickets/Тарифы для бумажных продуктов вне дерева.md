# Тарифы для бумажных продуктов вне дерева

#project #ticket

Статус: **реализовано, проверки и три независимых ревью пройдены**.

Следующий этап: [[Офферы бумажных продуктов — правила сборки и проверок]] —
план nullable `group_code`, paper-ветки без дерева и контракта отправки в Order Processing.

## Цель

Дать менеджеру плоский поиск по тарифам классификатора для бумажного
продукта без оцифрованного состава. Комета не реализует поиск сама: она
проксирует уже готовую плоскую выдачу service-catalog.

Ручной выбор допустим только для подтверждённого бумажного продукта. Если
классификатор не подтвердил `is_paper=true`, продукт считается цифровым и ручная
позиция не сохраняется.

## Зафиксированный HTTP-контракт

### K-1. `GET /api/v1/services`

- Комета запрашивает `/api/service/` классификатора с `is_available=true`.
- Ответ: `{"count": N, "result": [{"pk": 154, "title": "Cloud Compute"}]}`.
- Ручка доступна с `Permission.VIEW_KP` или `Permission.CREATE_KP`, потому что
  справочник используется и при чтении, и при редактировании состава КП.
- Недоступность или невалидный ответ классификатора: `502 classifier_unavailable`.

### K-2. `GET /api/v1/tariffs`

Вход:

- `client_id: UUID` — обязателен; персональная цена не может вычисляться без клиента;
- `concat_codes: list[str] | null`;
- `services_names: list[str] | null`;
- `services_pks: list[int] | null`;
- `tariffs_names: list[str] | null`;
- `pks: list[int] | null` — добавлено к образцу ОП для дозагрузки уже выбранных позиций;
- `page: int = 1`, минимум 1;
- `page_size: int = 100`, диапазон 1–1000.

Фильтры транслируются в готовые фильтры `/api/listapi/query_tariff/`:
`concat_code__in`, `service__service__title`, `service__service__id__in`, `title__icontains`,
`id__in`, `page`, `page_size`. Семантика поиска остаётся на стороне классификатора.

Ответ: `{"count": N, "result": [...]}`. Элемент выдачи содержит:

- `pk`, `concat_code`, `tariff_title`, `service_service_title`, `tariff_service_title`;
- `tariff_element_title`, `tariff_element_unit_unit`, `tariff_element_charge_type`, `currency`;
- `archived_at`;
- `params: {min, max, step}` — для ручной позиции `min=1`, `max=9999`, `step=null` для
  `usage based`, иначе `step=1`;
- `default_price = element.price`;
- `min_default_price = element.cost_price`;
- `partner_price = round(default_price / 1.1)`;
- `min_partner_price = round(min_default_price / 1.1)`;
- `custom_price` — текущая действующая персональная цена для `client_id`, иначе `null`.

Денежные поля возвращаются строками с двумя знаками после запятой; округление
`ROUND_HALF_UP`, как в классификаторе.

Обычная выдача не фильтрует `archived_at` локально: иначе `count` и размер страницы
разойдутся с нативной пагинацией. Фронт показывает архивную строку как недоступную
для выбора; сервер повторяет эту проверку при сохранении.

В обычном поиске черновики скрывает service-catalog. При `pks` классификатор намеренно
возвращает и черновики, поэтому режим делается отдельно:

1. `pks` дедуплицируются с сохранением порядка запроса.
2. Комета читает их батчами по 100.
3. Строки `is_draft_tariff=true` исключаются.
4. `count` считается после дедупликации и фильтра черновиков, затем применяются `page`
   и `page_size`.

## Выбор тарифа и защита бумажного сценария

На `POST /offers` и `PATCH /offers/{offer_id}` сервер не доверяет переданному `group_code`:

1. Для строгого `is_paper=true` любой `group_code` (`null`, `0.0.0.0.0` или валидная
   ненулевая строка) допустим без проверки дерева, но сам `pk` обязан быть опубликованным
   неархивным тарифом плоского каталога.
2. Для цифрового продукта строится карта `(tariff pk, group_code) -> group params` и
   требуется точное совпадение ненулевой пары; `null`, zero и чужая пара отклоняются.
3. Недоступность классификатора, отсутствие продукта или невалидный ответ не подтверждают
   бумажность: `null`/zero отклоняются как ручной выбор, а ненулевая группа получает
   `classifier_unavailable`, потому что принадлежность дереву проверить невозможно.

`null` и legacy-код `0.0.0.0.0` проходят request → JSONB оффера → `OfferReadSchema` →
snapshot без подмены. Только adapter отправки подтверждённого бумажного оффера в ОП
канонизирует все варианты группы в `0.0.0.0.0` одновременно в `tariffs` и
`tariffs_for_approve`.

## K-3/K-4. Выдача оффера

В `TariffSchemaOfferOut` для всех, а не только бумажных офферов, добавляются:

- `params`;
- `default_price`, `min_default_price`, `partner_price`, `min_partner_price`;
- `custom_price`.

Для цифрового тарифа `params` берутся из конкретной связи `(product_id, group_code, pk)` в дереве:
это вложенные `inner/commercial/test`, а не универсальные 1–9999. Для всех позиций
подтверждённого бумажного оффера используются плоские параметры каталога — в том числе
для legacy-позиций с ненулевой группой и ранее сохранёнными tree-`params`.

Новые позиции пишут сервером выведенные `params` в `OfferTariffStoredSchema`. Старые JSONB без этого
поля обогащаются при чтении из дерева. Если дерево недоступно, `params=null`: сервер не
подменяет неизвестное ограничение универсальным.

Персональные цены загружаются bulk-запросом по всем `pk` сделки для `deal.client_id` и
передаются в трансформацию офферов. В списке тарифов поиска bulk ограничен `pk` текущей
страницы.

В `OfferReadSchema` добавляется `product_is_paper: bool`. Название и признак бумажности берутся
одним чтением продукта. Если классификатор недоступен, ответ деградирует в `product_name=null`,
`product_is_paper=false`.

## K-6. Вложения оффера

Добавляется `offer_attachment`:

- `offer_id`, `file_name`, `storage_key`, `content_type`, `size`, `sha256`, `uploaded_by`;
- `created_at`, `updated_at`, `deleted_at`;
- FK `offer_id -> offer.id ON DELETE CASCADE`, индекс по `offer_id`, unique `storage_key`;
- Alembic-миграция от текущей головы `f9a0b1c2d3e4`.

Публичные ручки повторяют контракт вложений предтарифа:

- `POST /api/v1/offers/{offer_id}/attachments`;
- `GET /api/v1/offers/{offer_id}/attachments`;
- `GET /api/v1/offers/{offer_id}/attachments/{attachment_id}`;
- `GET /api/v1/offers/{offer_id}/attachments/{attachment_id}/file`;
- `DELETE /api/v1/offers/{offer_id}/attachments/{attachment_id}`.

Загрузка и удаление требуют `Permission.CREATE_KP`, чтение — `Permission.VIEW_KP`. Лимит файла берётся
из общего `MAX_FILE_SIZE`. S3-ключ: `offer/{offer_id}/{uuid}_{file_name}`. В `OfferReadSchema.attachments`
возвращаются только активные вложения с presigned `download_url`.

Обязательный active-only инвариант `deleted_at IS NULL` применяется в четырёх местах:

- relationship/eager load для обычной выдачи оффера;
- list/get/download CRUD;
- проверка наличия скана;
- сборка нового snapshot.

Историческое чтение по дескриптору snapshot может обращаться к soft-deleted строке, но обычные
ручки оффера её не видят.

Файл сначала загружается в S3, затем в одной DB-транзакции создаётся строка и пересобирается
согласование. При ошибке DB новый S3-объект компенсирующе удаляется. `DELETE` помечает
строку `deleted_at`, но не удаляет S3-объект: он может быть доказательством старой версии согласования.
Политика GC/retention для таких объектов выносится в отдельную операционную задачу; до неё объекты
не удаляются.

## K-7. Скан и согласование

Бумажный оффер без хотя бы одного активного вложения считается оффером без скана.

- `DealActionContext` получает `missing_paper_scan_offer_ids`.
- `deal.actions.request_approval` и `deal.actions.send_to_implementation` неактивны, если список не пуст.
- Authoritative-проверка есть и в `POST .../approval/request`, и в прямой имплементации `not_required`.
- Отказ: `409 Conflict`,
  `{"detail": "...", "code": "paper_offer_scan_missing", "offer_ids": ["..."]}`.
- При неподтверждённом типе продукта `product_is_paper=false`, поэтому скан не требуется; это тот же
  консервативный default, который запрещает ручной тариф.

## Атомарность и snapshot

Скан — часть предмета согласования. Snapshot каждого оффера хранит отсортированные дескрипторы
активных вложений: `id`, `storage_key`, `sha256`, `size`, `file_name`. Изменение вложений меняет
`subject_hash`.

Все загрузки для lifecycle snapshot, workflow stale-check и implementation subject-check добавляют eager load
активных вложений. `OfferImplementationService.SUBJECT_OFFER_FIELDS` включает канонические дескрипторы
вложений.

Старые snapshot нельзя инвалидировать одним деплоем: `hash_subject_like_stored` определяет отсутствие
ключа `attachments` в сохранённом оффере и считает live-хеш без этого ключа, как уже сделано для
`created_at`. Отдельный тест покрывает pending/approved snapshot старого формата.

Мутации вложений, офферов и самой сделки выполняются так:

1. Сетевые чтения продукта, тарифа и персональной цены идут до DB-лока.
2. Целевые сделки блокируются `Deal FOR UPDATE` в стабильном порядке; при переносе оффера — обе.
3. После лока оффер и сделка перечитываются; `product_id`, `client_id`, `seller` и другие входы enrichment
   сверяются с предварительно прочитанными; при расхождении операция повторяется вне транзакции.
4. В той же `AsyncSession` проверяются active approval и любая строка implementation attempt.
5. CRUD-мутация и `approval_lifecycle.rebuild_in_session` выполняются в той же транзакции.

Старт согласования делает финальную проверку active attachments уже после захвата того же
`Deal FOR UPDATE`, непосредственно перед `prepare/start`. Это закрывает гонку `scan check -> concurrent delete -> start`.

Имплементация делится на claim и execution:

1. До `_resolve_staffers` и любого HTTP одна транзакция берёт `Deal FOR UPDATE`.
2. В этой транзакции eager-load даёт current approval, offers и active attachments; проверяются snapshot,
   сканы и fingerprint вложений.
3. Для всех ещё не `succeeded` офферов snapshot в той же сессии создаются/захватываются
   `offer_implementations(status=pending)` с прежним детерминированным `external_approval_id`.
4. Только после commit и освобождения лока идут staffers/ОП. Мутация вложений после claim видит attempt
   и отклоняется.
5. Retry идемпотентно захватывает ту же failed/pending-строку, не меняя `external_approval_id`.

## Проверки

Обязательные новые тесты:

- API-параметры, обязательный `client_id`, трансляция фильтров, pagination и 502;
- формулы цен, `custom_price` только нужного клиента, `params` tree/manual/legacy;
- `pks` не возвращает черновики и даёт стабильный `count/result`;
- tree pair, paper zero, digital zero, fake nonzero group, draft/archive, classifier unavailable;
- явный round-trip `0.0.0.0.0` через request/read/snapshot/ОП;
- CRUD/API/S3-компенсация/soft-delete/cascade/права для вложений;
- soft-deleted скан не участвует в read, guard и snapshot;
- pending/implemented блокируют мутацию вложения;
- старый snapshot без `attachments` не инвалидируется;
- action и обе authoritative-ветки отклоняют бумажный оффер без скана;
- concurrency: `attachment delete <-> approval start`, `attachment mutation <-> implementation claim`,
  `offer snapshot mutation <-> approval start`.

poetry run make check

## Независимое ревью реализации

Финальный код проверили три разные AI-модели с разными фокусами:

- API-контракт и обратная совместимость;
- вложения, snapshot, транзакции и конкурентные сценарии;
- paper-only guard, цены, `params`, скан и отправка в ОП.

После исправления найденных замечаний все три финальных вердикта:
`CRITICAL: NONE`, `MAJOR: NONE`.

По результатам ревью дополнительно закрыты:

- утечка presigned URL вложения через `GET /deals/{id}` без `VIEW_KP`;
- гонки мутаций оффера/сделки со стартом согласования и implementation claim;
- отмена активного согласования при PATCH только неснапшотного `updated_by`;
- устаревшее ожидание частичного отчёта при глобальном расхождении live subject и snapshot.
