# Outbox Dead Letter

#project #ticket #approval #outbox

Связано: [[Architecture]], [[Approval Debug Mode]], [[Sequential KP Approval]].

Завести потолок попыток и dead-letter-состояние для transactional outbox
уведомлений согласования (`ApprovalNotificationWorker`,
`app/services/approval_notification_worker.py`).

## Проблема

У outbox нет предела попыток: ретраится вечно всё, что не `SENT` и не `CANCELED`.
Экспоненциальный backoff капится только по задержке —
`outbox_retry_base_seconds * 2^min(attempts-1, 8)` ≈ 4,3 часа при базе 60 с
(`app/core/config.py`, `ApprovalWorkflowSettings`; `max_attempts=5` в конфиге —
это настройка S3-клиента, к outbox отношения не имеет). Доставка с перманентной
ошибкой крутится бесконечно, и узнать о ней можно только из warning-логов.

Всплыло на ревью MR про файл КП (2026-08-11, DFDEV-1672): часть перманентных
сценариев тогда же закрыта точечно — битый `deal_id` в снимке уведомления и
`S3ObjectNotFoundError` (запись о КП без объекта в S3) больше не ретраятся,
письмо уходит без вложения с error-логом. Но класс проблемы остался.

## Известные перманентные сценарии, которые всё ещё зациклятся

- **Письмо больше лимита SMTP-релея**: КП до 20 МБ (`MAX_FILE_SIZE`) + base64
  ≈ 27 МБ — многие релеи режут на ~25 МБ. Отказ приходит как `EmailSendError`
  и неотличим от транзиентного сбоя SMTP.
- Стабильно отвергаемый получатель (несуществующий ящик, политики релея) —
  тоже `EmailSendError` на каждой попытке.
- Любая будущая ошибка, не разобранная по типу: дефолтный путь — вечный retry.

## Предложение

1. `outbox_max_attempts` в `ApprovalWorkflowSettings` (например, 10 — с текущим
   backoff это ~1,5 суток попыток).
2. Новый терминальный статус доставки `dead` (или переиспользовать `CANCELED`
   с отдельным `last_error`) — по исчерпании попыток доставка закрывается,
   пишется error-лог; сейчас статусы: `pending/sent/failed/canceled`
   (`ApprovalNotificationDeliveryStatus`).
3. По возможности классифицировать `EmailSendError`: SMTP-коды 5xx
   (permanent) → dead сразу, 4xx (transient) → retry. `aiosmtplib` отдаёт код в
   исключении — сейчас он теряется при заворачивании в `EmailSendError`.
4. Видимость: dead-доставки должны быть заметны не только в логах —
   минимум метрика/алерт, максимум ручка/выборка для поддержки. Сюда же —
   алерт на уже существующие error-логи worker-а о письме, ушедшем **без
   вложения КП** (`KP attachment skipped: object is missing in S3` и
   `malformed deal_id in snapshot`): сейчас согласующий в таком случае молча
   работает без файла, и это видно только в логах (замечание из повторного
   ревью DFDEV-1672).
5. Решить продуктово, что значит dead-доставка для стадии согласования:
   согласующий письмо не получил, но стадия остаётся pending — задача видна в
   ЛКМ (`GET /approval-stages/pending`), поэтому процесс не мёртв, но SLA-таймер
   стадии идёт. Возможно, стоит уведомлять инициатора.

## Критерии приёмки

- Доставка с перманентной ошибкой прекращает ретраиться не позже чем через
  `outbox_max_attempts` попыток и получает терминальный статус.
- Терминальное состояние отличимо от `canceled` штатных сценариев
  (debug-дедупликация, redacted token).
- Транзиентные сбои SMTP/S3 по-прежнему ретраятся до потолка.
- Тесты: исчерпание попыток, классификация 4xx/5xx (если делается), редакция
  encrypted_token после закрытия всех доставок notification не ломается.
