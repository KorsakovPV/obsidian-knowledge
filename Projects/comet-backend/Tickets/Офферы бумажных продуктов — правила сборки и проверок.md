# Офферы бумажных продуктов — правила сборки и проверок

#project #ticket

Статус: **реализовано**.

Связанные заметки: [[Тарифы для бумажных продуктов вне дерева]],
[[Preapproved Order Integration]].

## Цель

Разрешить собрать, показать в КП и передать в Order Processing оффер бумажного
продукта с любыми выбираемыми тарифами каталога, даже если этих тарифов нет в
дереве продукта. Для обычного продукта сохранить точную проверку пары
`(tariff pk, group_code)` по дереву.

## Реализовано

- `TariffsSchema.group_code` принимает отсутствующее значение и явный `null`; строка
  по-прежнему проверяется маской из пяти числовых сегментов.
- PATCH сохраняет вложенный `group_code: null` в JSONB, не меняя прежнюю top-level
  семантику `exclude_none`.
- Для подтверждённого paper-продукта выбранные тарифы проверяются по плоскому
  каталогу без привязки к дереву. Для digital требуется точная пара
  `(tariff pk, group_code)` из дерева.
- Недоступность классификатора не разрешает ручной тариф: `null` и legacy zero
  отклоняются как digital, а ненулевая группа не принимается без подтверждённой пары.
- При чтении paper-оффера параметры всех тарифов вычисляются из плоского каталога;
  хранимый JSONB и approval snapshot при этом не мутируют.
- Перед отправкой в Order Processing любой paper-код группы канонизируется в
  `0.0.0.0.0` в `tariffs` и `tariffs_for_approve`. Digital-код передаётся без
  изменения только после повторной проверки точной пары.
- Публичный legacy endpoint `POST /api/v1/orders/{offer_id}` и его незащищённый
  сервисный путь удалены. Единственная точка запуска — canonical
  `POST /api/v1/deals/{deal_id}/start-implementation`.
- Параллельные запуски одной сделки сериализованы transaction-scoped PostgreSQL
  advisory lock. Lock использует отдельное соединение `NullPool`, поэтому длительный
  вызов ОП не занимает основной пул CRUD-сессий. Число lock-соединений на процесс
  ограничено `DB_IMPLEMENTATION_LOCK_POOL_SIZE`; перегрузка завершается управляемым
  503, а конкурентный запрос по той же сделке получает 409
  `deal_implementation_in_progress`.
- В Order Processing добавлен межсервисный contract-test бумажного заказа с тарифом
  вне дерева через реальные валидаторы и сохранение заказа.

## Зафиксированный контракт

### Вход Кометы

`group_code` у позиции оффера становится `str | null` с default `null`:

```json
{
  "pk": 929,
  "quantity": 1,
  "price": "100.00",
  "group_code": null
}
```

Ключ можно не передать или передать с `null`. Если передана строка, существующая
маска `^\d+\.\d+\.\d+\.\d+\.\d+$` сохраняется.

### Правила выбора

| Тип продукта | `group_code` | Проверка |
|---|---|---|
| `is_paper is True` | `null`, `0.0.0.0.0` или валидная строка | Тариф должен существовать в плоском каталоге; принадлежность дереву не проверяется |
| цифровой | валидный ненулевой код | Точная пара `(pk, group_code)` должна быть в дереве продукта |
| цифровой | `null` или `0.0.0.0.0` | Отказ: ручное добавление запрещено |
| тип продукта не подтверждён | `null` или `0.0.0.0.0` | Отказ как для цифрового продукта |

«Любой тариф каталога» означает любой доступный для выбора опубликованный и
неархивный тариф. Черновик, архивная позиция, отсутствующий или невалидный ответ
классификатора не становятся допустимыми из-за бумажности продукта.

Для нового запроса Комета не подставляет `0.0.0.0.0` внутри своего домена:
`null` проходит request → JSONB → `OfferReadSchema` → approval snapshot. Только
интеграционный adapter канонизирует группу под контракт ОП. Существующие позиции с
`0.0.0.0.0` продолжают читаться, обновляться и передаваться без миграции данных.

### Недоступность классификатора

- Бумажность подтверждается только строгим `is_paper is True`.
- Если продукт получить не удалось, позиция без группы или с legacy-кодом
  `0.0.0.0.0` отклоняется как ручная для цифрового продукта.
- Для ненулевой группы недоступность дерева остаётся `502 classifier_unavailable`:
  сервер не может ни подтвердить, ни опровергнуть принадлежность тарифа обычному
  продукту и не должен превращать инфраструктурный сбой в ложную бизнес-ошибку.

### Параметры тарифа

- Для новой или повторно сохранённой позиции бумажного продукта `params` выводятся
  из плоского тарифа каталога по тем же
  правилам, что для ручной позиции: `min=1`, `max=9999`, `step=null` для
  `usage based`, иначе `step=1`.
- Для цифрового продукта `params` по-прежнему берутся из конкретной группы дерева.
- Присланные клиентом `params` не считаются авторитетными и перезаписываются сервером.
- При чтении подтверждённого paper-оффера flat-`params` вычисляются для **всех**
  позиций, включая legacy с ненулевой группой и уже сохранёнными tree-`params`.
  Это enrichment ответа без тихой перезаписи JSONB и approval snapshot; при следующем сохранении
  тарифов те же flat-`params` станут хранимыми.

### Контракт с Order Processing

Pydantic-схема Order Processing принимает nullable-значение, но runtime — нет.
Поэтому adapter получает проверенный режим продукта, вычисленный до claim:

- для подтверждённого paper в **обоих** списках, `tariffs` и `tariffs_for_approve`,
  любой исходный `group_code` (`null`, zero или nonzero) становится `0.0.0.0.0`;
- для подтверждённого digital каждая пара `(pk, group_code)` повторно проверена по дереву;
  точный ненулевой tree-код передаётся без изменения, `null`, zero и чужая пара отклоняются;
- недоступность классификатора не превращает ранее paper nonzero в доверенный digital:
  manual null/zero запрещается как для digital, а nonzero не уходит в ОП без доказанной tree-пары.

Цена и остальные поля формируются прежним путём из одобренного snapshot. Проверки
subject hash, защищённой минимальной цены и идемпотентный implementation claim не
ослабляются для бумажного продукта.

## Реализованный план

1. **Сделать группу nullable на всех границах Кометы.**
   Изменить `TariffsSchema.group_code` на `str | None = None`; через наследование
   обновятся `OfferTariffStoredSchema`, `TariffSchemaOfferOut` и order-схемы.
   Проверить, что валидатор маски применяется только к строке.
2. **Не потерять `null` при PATCH.**
   Изменить `OfferCrud._build_update_data`: сохранить существующую top-level
   семантику `exclude_none`, но сериализовать переданный список `tariffs` отдельно
   с `group_code=None`. Закрепить одинаковое JSONB-представление для omitted и
   explicit null внутри позиции.
3. **Разделить классификацию продукта и проверку дерева.**
   В `OfferService._normalize_tariff_selection` сначала получить строгий
   `is_paper`, затем выбрать paper/digital стратегию. Не использовать наличие
   `group_code` как единственный признак бумажной ветки.
4. **Реализовать paper-стратегию.**
   Батчем загрузить все выбранные `pk` через существующий метод плоского каталога,
   потребовать опубликованность и отсутствие архива, вывести серверные `params`.
   Дерево продукта и пары групп для подтверждённого бумажного продукта не проверять.
5. **Сохранить digital-стратегию.**
   Для каждого тарифа потребовать ненулевой `group_code` и точное совпадение
   `(pk, group_code)` в дереве. `null`, legacy zero и чужая ненулевая группа
   отклоняются до записи.
6. **Сохранить fail-closed поведение.**
   Разделить ошибки чтения продукта так, чтобы ручная позиция при неизвестном типе
   получила запрет, а штатная цифровая проверка при недоступном дереве — честный 502.
7. **Протянуть nullable-группу через чтение и КП.**
   Передать `product_is_paper` в enrichment и для подтверждённого paper всегда выводить
   flat-`params` из плоского тарифа, даже если в legacy JSONB уже есть tree-`params`.
   Не мутировать JSONB/snapshot при чтении. Для digital сохранить stored-`params` и tree fallback
   только при их отсутствии. Значение группы в API-выдаче не подменяется.
8. **Зафиксировать outbound adapter.**
   Заменить булевую `_classify_paper_offers` на результат с тремя состояниями:
   `confirmed_paper`, `confirmed_digital`, `unavailable`. Весь запуск одной сделки,
   включая классификацию, повторную сверку живых тарифов, snapshot/hash, claim и отправку
   в ОП, выполнять под deal-level advisory lock. Для lock использовать отдельный
   `NullPool`, не занимая основной пул вложенных CRUD-сессий, и process-wide
   ограничитель числа активных lock-соединений. `unavailable` для manual null/zero даёт бизнес-запрет,
   а для nonzero — `502 classifier_unavailable`; в обоих случаях до claim/HTTP.
   Протянуть проверенный режим в `_implement_offer`/фактический `_build_payload`.
   Для paper канонизировать **все** группы в `0.0.0.0.0` до создания обоих списков;
   для digital передать только уже проверенный ненулевой tree-код. Закрепить в Comet полный
   payload, включая paper null/zero/nonzero, digital и одинаковый код в обоих списках.
   Создавать новые словари позиций: shallow-copy `snapshot_offer` не должен позволить
   канонизации in-place изменить approval snapshot.
9. **Закрыть legacy-обход имплементации.**
   Удалить публичный `POST /api/v1/orders/{offer_id}` и прямой `OrderService.create`:
   заказ должен создаваться только через
   `POST /api/v1/deals/{deal_id}/start-implementation`, где уже есть проверка
   approval snapshot, скана, subject hash, protected price и идемпотентный claim.
   Согласовать удаление с парным фронтовым тикетом и обновить API-документацию. Вместе
   удалить осиротевшие `OrderProcessing.create`, `OrderCreateSchema`, `OrderOutSchema`, docs/tag
   и их тесты; схемы staffers оставить, они используются canonical flow.
10. **Добавить межсервисный contract-test.**
    В `order-processing` добавить тест `PreapprovedOrderService.create_preapproved_order`
    с paper-продуктом и тарифом вне дерева: одинаковый canonical zero в `tariffs` и
    `tariffs_for_approve`, реальные `NewOrderHandler`, `TariffsValidator` и
    `TechParametersValidator`, сохранение и возврат заказа. Прод-код ОП не менять.
11. **Регрессия обычных продуктов.**
   Не менять скидочный маршрут, snapshot/hash, protected-price guard, атомарные
   блокировки оффера и implementation claim.
12. **Сериализовать параллельный запуск.**
   Конкурирующий `start-implementation` для того же `deal_id` завершать 409
   `deal_implementation_in_progress` до implementation claim и HTTP-запроса в ОП.
   Route-level action guard до входа в сервис может обратиться к классификатору. После завершения или
   аварии процесса transaction-scoped lock освобождается БД; незавершённая запись
   `pending` повторно использует прежний детерминированный `external_approval_id`.

## Проверки

Обязательные сценарии:

- схема принимает отсутствующий и явный `null`, но отклоняет строку неверной маски;
- OpenAPI не включает `group_code` в `required`, допускает `null`, а строковая ветка сохраняет pattern;
- paper + `group_code=null` + тариф вне дерева создаётся и возвращается с `null`;
- paper + валидная ненулевая группа вне дерева также принимается без tree-check;
- paper сохраняет legacy `0.0.0.0.0` без подмены;
- paper отклоняет отсутствующий, draft и archived тариф каталога;
- digital принимает прежнюю точную tree-пару;
- digital отклоняет `null`, `0.0.0.0.0` и чужую ненулевую пару;
- неизвестный тип продукта запрещает ручную позицию;
- недоступное дерево для штатной digital-позиции даёт 502;
- `params` paper/digital берутся из правильного источника;
- legacy paper + nonzero group получает flat enrichment и при missing, и при stored tree-`params`;
- PDF/OfferRead не падают на `group_code=null`;
- snapshot сохраняет `null`, subject hash стабилен;
- PATCH с omitted/explicit null сохраняет ключ `group_code` в JSONB и snapshot;
- payload ОП канонизирует paper null/zero/nonzero в `group_code: "0.0.0.0.0"`
  одновременно в `tariffs` и `tariffs_for_approve`;
- после `_build_payload` и retry исходные null/nonzero в `subject_snapshot` не изменились in-place;
- digital payload сохраняет tree-код и fail-closed отклоняет null/zero;
- confirmed digital повторно требует exact `(pk, group_code)` из дерева до claim/HTTP;
- если ранее paper-оффер с nonzero больше не подтверждён как paper, чужая digital-пара
  отклоняется, а недоступное дерево даёт 502; claim и HTTP не выполняются;
- contract-test ОП проходит цепочку `PreapprovedOrderService → NewOrderHandler →
  TariffsValidator → TechParametersValidator` и возвращает сохранённый paper-заказ;
- legacy `/orders/{offer_id}` больше не позволяет обойти canonical implementation flow;
- существующие paper-офферы с нулевым кодом продолжают работать.

## Границы

- Плоские proxy-ручки каталога повторно не проектируются.
- Модель и API вложений оффера (K-6), обязательность скана (K-7) и фронтенд не
  меняются в этом тикете.
- Production-код Order Processing не меняется: Comet adapter использует уже
  поддерживаемый canonical zero code. В Order Processing добавляется только
  межсервисный regression-test. Расхождение nullable-схемы и runtime ОП следует
  завести отдельным дефектом владельцам Order Processing.

## Независимое ревью плана

План прошёл четыре итерации у трёх независимых AI-ревьюеров:

- **Euclid — API/contract:** Pydantic, OpenAPI, PATCH/JSONB и удаление legacy API;
- **Anscombe — end-to-end:** snapshot, scan, claim, outbound payload и runtime Order Processing;
- **Popper — business guard:** paper/digital-матрица, fail-closed, legacy params и регрессия.

## Независимое ревью реализации

Реализация прошла повторяющиеся ревью тех же трёх независимых AI-рецензентов до
нулевого остатка critical/major:

| Рецензент | Фокус | Финальный результат | Проверки рецензента |
|---|---|---|---|
| Euclid | API, схемы, JSONB, ошибки и capacity | `CRITICAL: NONE`, `MAJOR: NONE`, `MINOR: NONE` | 200 unit/API tests + black/isort/flake8/mypy |
| Popper | paper/digital/fail-closed, retry и конкурентность | `CRITICAL: NONE`, `MAJOR: NONE`, `MINOR: NONE` | 184 unit/API tests + полный `make check` |
| Anscombe | DB concurrency, retry, K-6/K-7 регрессия | `CRITICAL: NONE`, `MAJOR: NONE`, `MINOR: NONE` | 13 DB integration + 18 целевых tests |

На промежуточных раундах были найдены и устранены мажорные дефекты:

- повтор уже успешного оффера зависел от классификатора и мог перестать быть
  идемпотентным при его недоступности;
- параллельные запуски могли одновременно отправить одинаковый заказ в ОП;
- lease/TTL-вариант блокировки допускал takeover ещё работающего запроса без fencing;
- advisory lock в основном DB-пуле создавал взаимное исчерпание при вложенных сессиях;
- неограниченный `NullPool` переносил риск на общий `max_connections` PostgreSQL.

Финальное решение: transaction-scoped advisory lock на отдельном `NullPool`,
process-wide bounded semaphore с настраиваемой ёмкостью, 409 для той же сделки и
fail-fast 503 при исчерпании слотов.

На промежуточных раундах были найдены и устранены:

- `MAJOR`: PATCH удаляет nested `group_code=None` из-за `exclude_none=True`;
- `CRITICAL`: runtime Order Processing падает на `group_code=null`, несмотря на
  nullable Pydantic-схему;
- `CRITICAL`: legacy `/orders/{offer_id}` обходит approval snapshot и claim;
- `MAJOR`: не был определён flat fallback для legacy paper + nonzero group;
- `MAJOR`: outbound канонизировал только `null`, но не paper nonzero;
- `MAJOR`: проверка runtime ОП была не назначена конкретному межсервисному тесту;
- `MAJOR`: при outage ранее paper nonzero мог пройти как digital без exact tree-check.
