# Черновик тарифа публикуется при отправке заказа

#project #ticket #pre-tariff #order-processing

Реализация переноса публикации предтарифа с решения финдиректора на отправку оффера в
Order Processing. Связанный общий ресерч — [[Предтариф как черновик тарифа]], устройство
отправки заказов — [[Preapproved Order Integration]].

## Итоговое поведение

- `POST /pre-tariffs/{id}/approve` только фиксирует решение и переводит заявку
  `review → approved`; тариф в классификаторе остаётся черновиком.
- Позиция оффера хранит `pre_tariff_id` рядом с настоящим `pk` тарифа. Комета проверяет
  соответствие заявки тарифу и продукту, а также `min` / `max` / `step` количества.
- Наличие `pre_tariff_id` добавляет в маршрут сделки обязательную стадию
  `FINANCE_DIRECTOR` и триггер `custom_tariff`; в `route_context` сохраняются UUID заявок
  и офферов.
- Перед каждым `POST` заказа Комета перечитывает `is_draft_tariff` по точному `pk`.
  Неодобренная заявка или непройденная стадия финдиректора останавливает оффер до
  публикации и до вызова OP.
- Черновики исключены из общего дерева продуктов классификатора. Комета дополнительно
  отбрасывает их при разборе дерева, поэтому черновик без `pre_tariff_id` нельзя добавить
  в цифровой оффер. Для бумажных позиций перед OP выполняется точечная проверка каждого
  тарифа; найденный непривязанный черновик также блокирует отправку.
- После всех preflight-проверок черновики публикуются, результат проверяется на тот же
  `pk` и `is_draft_tariff=false`, сохраняется `published_at`, сбрасываются кэши дерева и
  продукта, затем немедленно выполняется `POST` в OP.
- `pre_tariff_id` — внутренний маркер Кометы: в payload OP он не передаётся.

## Повторная отправка

Классификатор остаётся источником истины по факту публикации.

| Состояние при попытке | Действие |
| --- | --- |
| `is_draft_tariff=true`, заявка и маршрут согласованы | Опубликовать, записать marker, вызвать OP |
| `is_draft_tariff=false`, предыдущий вызов OP упал | Не публиковать повторно, восстановить marker при необходимости, повторить OP с прежним idempotency key |
| Публикация прошла, запись marker не прошла | OP не вызывать; следующая попытка увидит опубликованный тариф, запишет marker и продолжит |
| OP упал после публикации | Тариф остаётся опубликованным; следующая попытка не создаёт второй тариф |
| Заявка не `approved` или нет завершённой стадии финдиректора | Публикацию и OP не вызывать |

`published_at` отделён от статуса заявки. Миграция заполняет его для исторических
`approved`-заявок с `classifier_tariff_id`, потому что до этого изменения такие заявки
уже публиковались во время approve.

## Защита от гонок

Создание/обновление оффера с `pre_tariff_id` и изменение/удаление той же заявки берут
общую PostgreSQL advisory-блокировку по UUID заявки. Это закрывает окно между проверкой
«позиция ещё не используется» и сохранением оффера. UUID сериализуется в JSONB строкой;
локальный lock-marker в OP не уходит.

Привязать заявку к офферу может только её автор либо пользователь с
`approve_tariffs`; известного UUID чужой заявки недостаточно.

В `service-catalog` публикация, изменение/удаление черновика и создание обычного тарифа
используют общий transaction-scoped advisory lock пространства версий. После него
публикация блокирует группу одинакового составного кода в порядке `pk`, проверяет дубль
и назначает `price_code`. Поэтому параллельные write-операции не отменяют публикацию, не
создают одинаковые версии и не берут строковые блокировки во взаимно обратном порядке.

## Межсервисный контракт

`service-catalog` гарантирует идемпотентный
`POST /api/draft_tariffs/{pk}/publish/`: повтор для уже опубликованного активного тарифа
возвращает `200`. Полный дубль отвечает `400` со стабильным машинным кодом
`published_duplicate`; Комета переводит только этот код в `publish_conflict`, остальные
`400` остаются общим `rejected`.

## Основные изменения

- Comet: `app/services/offer.py`, `offer_implementation_service.py`,
  `approval_route_builder.py`, `pre_tariff.py`, `pre_tariff_binding.py`,
  `pre_tariff_lock.py`; схемы тарифов и миграция `b1c2d3e4f5a6`.
- Service catalog: публикация возвращает структурированный код конфликта, не теряя его в
  общем преобразователе ошибок; черновики исключены из дерева продуктов, а ключ Redis
  этого дерева переведён на `Product:v2:{id}`, чтобы старый бессрочный кэш не пережил
  деплой нового фильтра.

Миграция БД обязательна до запуска новой версии Comet.

Порядок rolling deploy: сначала полностью обновить `service-catalog` и вывести из трафика
pod'ы, читающие legacy-ключ `Product {id}`, затем выкатывать Comet. Даже в смешанном окне
Comet работает fail-closed по `is_draft_tariff`, поэтому черновик в OP не отправляется;
порядок нужен для однозначного контракта самого `/api/products/`.
