# KP File Versioning

#project #ticket #kp #s3

Связано: [[Architecture]], [[Domain Model]], [[API]], [[Outbox Dead Letter]].

Полноценное версионирование файла КП — отдельный тикет, вынесенный из постановки
«файл КП на бэке» (DFDEV-1672, 2026-08-11): «пока храним и отдаём последнюю версию
файла; при повторной отправке на согласование файл заменяется».

## Зачем

Сейчас согласующий всегда видит **последнюю** версию файла (осознанный компромисс,
задокументирован в коде). Версионирование нужно, чтобы:

- знать, **какая версия файла ушла в какую версию согласования**, и отдать
  согласованный PDF задним числом (споры, аудит);
- показать историю КП сделки;
- убрать инвариант «текущее КП = последнее вложение», на котором сейчас держатся
  три места кода (см. [[Domain Model]]).

## Важные вводные (проверено 2026-08-11)

- **Bucket versioning в MinIO включён** (вводная от Павла): физически ни один
  загруженный файл не теряется уже сейчас. Ретроактивно ничего не пропало.
- Каждая загрузка пишет объект под **уникальным ключом**
  `deal/{deal_id}/{uuid4()}_{имя}` — «замена» на уровне S3 это новый объект плюс
  удаление старого. При включённом версионировании `delete_object` без `VersionId`
  ставит delete-маркер, старый объект остаётся noncurrent-версией.
- **Но приложение теряет адрес**: при замене удаляется строка `deal_attachment`,
  вместе с ней — `storage_key`. Старые файлы достижимы только форензикой
  (`list-object-versions` по префиксу `deal/{deal_id}/`, чтение с `VersionId` —
  ручная админская операция). Кода работы с версиями S3 (`VersionId`,
  `list_object_versions`) в `S3Service` нет.

## Предлагаемый план (дешёвый путь)

Ключевая идея: версионированию нужна не сохранность байтов (она уже есть), а
**связь версии файла с версией согласования** — а она живёт в БД, которую мы чистим.
Поэтому API версий S3 не нужен вовсе:

1. **Перестать удалять строки БД**: вместо удаления помечать прежнее вложение
   superseded (`superseded_at` или `is_current`); объекты в S3 не трогать — ключи
   уникальны, им ничто не мешает жить рядом. Чистку S3-объектов убрать.
2. «Текущее КП» — единственная строка `WHERE superseded_at IS NULL` (заменяет
   инвариант «последнее вложение», тай-брейки становятся не нужны).
3. **Фиксировать `attachment_id` в версии approval** при старте согласования
   (рядом с `subject_snapshot` или отдельным полем) — письма и задачи согласующего
   смогут читать зафиксированную версию, а не живую (закрывает компромисс
   «стадии видят последнюю версию»).
4. Скачивание версии — обычный `get_object` по сохранённому `storage_key`
   строки-версии; ручка вида `GET /deals/{id}/attachments?include_superseded=true`
   или история в отдельном endpoint.
5. Решить про lifecycle: noncurrent-версии и delete-маркеры в бакете копятся с
   каждой заменой уже сегодня — нужна политика хранения (или отказ от версионности
   бакета, когда строки БД перестанут удаляться и защита от удаления станет не нужна).

## Связанные решения, которые упростятся

- `kind`-колонка вложений (второй тип файла) — если делать, то одной миграцией с
  версионированием.
- Обязательность файла при отправке на согласование (открытый вопрос аналитику) —
  с фиксацией `attachment_id` в approval проверка станет естественной частью старта.

## Критерии приёмки (черновик)

- По завершённому согласованию можно получить именно тот PDF, который видели
  согласующие этой версии.
- Замена файла не удаляет ни строк БД, ни объектов S3.
- Письмо стадии и `kp_attachment` в pending читают версию, зафиксированную в
  approval, а не последнюю загруженную.
- Существующие сделки с одним файлом работают без миграции данных S3.
