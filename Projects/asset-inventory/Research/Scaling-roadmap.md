# Asset Inventory — дорожная карта масштабирования

Цель: держать **кратный** рост нагрузки (сообщений/с от коллекторов и заказов).
Документ описывает весь путь фазами. Принцип сквозной: **сначала безопасность,
потом производительность** — нельзя добавлять параллелизм поверх непокрытых гонок.

Под-документы:
- `docs/scaling-phase-1.md` — детальный технический план Фазы 1.
- `docs/scaling-phase-1-rfc.md` — защитная памятка под одобрение Фазы 1.
- `docs/scaling-phase-2.md` — детальный технический план Фазы 2 (партиции + поды).
- `docs/scaling-phase-3.md` — детальный технический план Фазы 3 (декомпозиция + БД).

> Вне рассмотрения по решению команды: `resource_projection_sync`.

## Где мы сейчас (факты по `git_tag 3.55`)

- Главный сервис — **синглтон by design**: `replicas: 1`, `strategy: Recreate`, все 10
  Kafka-сабскрайберов `max_workers=1`, одна группа `ai-consumer-group`. Отчёты уже вынесены
  в отдельный worker.
- **Жёсткий потолок №1 — 1 партиция на statistic-топик** (в логах только `*-0`). Лишние
  поды простаивают: Kafka отдаёт партицию ровно одному консьюмеру в группе.
- Цена сообщения ~0.1–0.25 c → потолок **~5–8 сообщений/с на топик** при текущей схеме.
- **Корректность горячего пути уже в основном закрыта** (см. CLAUDE.md «Known race
  conditions»): `ON CONFLICT` в upsert'ах; `pg_advisory_xact_lock(order_resource_id)` +
  read-modify-write в одной транзакции для аллокаций (межподово безопасно).
- Остаточные зазоры: ревайвор не берёт advisory-лок; нет event-time guard.
- БД: Postgres HA + Pgpool, пул `20+20`/под, append-only история аллокаций растёт
  неограниченно.

## Карта зависимостей фаз

```
Phase 0 (безопасность/видимость)  ── ОБЯЗАТЕЛЬНО до Phase 2 (можно параллельно с Phase 1)
        │
Phase 1 (корректность)  ── ГЕЙТ: без неё Phase 2 портит данные
        │
Phase 1.5 (опц. fail-safe: unique index)  ── после дедупа; не требует Phase 2
        │
Phase 2 (параллелизм: партиции + поды)  ── снимает потолок №1
        │
Phase 3 (декомпозиция + БД-масштаб)  ── частично можно начинать после Phase 1
```

Ключ: **Phase 1 даёт безопасность без прироста, Phase 2 — прирост поверх безопасности.**
Перепрыгивать через Phase 1 нельзя.

## Phase 0 — безопасность и видимость (ОБЯЗАТЕЛЬНО до Phase 2)

Дешёвые шаги без смены архитектуры. Не «по мере рук»: `statement_timeout`, partial composite
индекс под `get_active_for_order_resources`, метрики lag/pool/lock-wait и решение по
commit-семантике должны быть **до** активного масштабирования — иначе масштабируем вслепую и
с риском потери сообщений.

1. **`statement_timeout` на стороне приложения/БД.** Сегодняшний инцидент (seq scan 73 c,
   подвесивший Kafka) не положил бы сервис, если бы тяжёлый запрос убивался на лимите.
2. **Индексы:**
   - `lost_resource(pool_name/tenant_name/fingerprint)` — уже сделано (миграция
     `a1b2c3d4e5f6`).
   - partial composite на активные аллокации:
     `(order_resource_id, instance_name, instance_id, start_date DESC) WHERE end_date IS NULL`
     — под hot-query `get_active_for_order_resources`.
3. **Вынести хардкод в конфиг и считать как глобальный бюджет, а не per-pod:**
   `max_workers` (по топикам), `pool_size/max_overflow/pool_timeout`,
   `_MAX_CONCURRENT_WRITE_PHASES` (=10), revival semaphore (=3). При N подах бюджет =
   `N × (pool_size + max_overflow)` должен укладываться в лимит Postgres/pgpool.
4. **Наблюдаемость → Prometheus:** консьюмер-лаг по топику/партиции, гистограммы времени
   обработки по фазам (уже логируются), время ожидания соединения из пула, lock wait,
   deadlocks, slow SQL (уже есть `slow_sqlalchemy_query`).
5. **Commit-семантика (реальная дыра надёжности).** Сейчас сабскрайберы стоят с
   `auto_commit=True`, а хендлеры ловят исключение и **не пробрасывают** его
   (`except Exception: logger.exception(...)`). Значит offset коммитится **даже при сбое
   обработки** → сообщение теряется. При `statement_timeout` (п.1) это усугубляется: убитый
   по таймауту запрос → сообщение «обработано» и потеряно. Нужна политика: коммит **после**
   успешной транзакции, retry с backoff, затем DLQ. Это предусловие любого масштабирования —
   при росте подов/лага потери станут заметнее.
6. **Classificator как узкое место.** Обработка заказа делает до 4 **последовательных** GET к
   Classificator на cache-miss (видно в логах). При кратном росте даже при хорошем hit-rate
   всплески cache-miss дадут latency-спайки. Меры: распараллелить вызовы (`asyncio.gather`),
   предзаполнять hot-mappings на старте, circuit breaker + fallback, локальный in-memory кэш
   с фоновым refresh поверх Redis.

Результат: видим узкие места по метрикам, инциденты не каскадят, сообщения не теряются,
ручки готовы к тюнингу.

## Phase 1 — корректность (ГЕЙТ для масштабирования)

Закрывает ровно два оставшихся зазора. Оба — **no-op на текущем синглтоне**, шипятся
заранее. Детали и фрагменты кода — в `docs/scaling-phase-1.md`.

1. **Ревайвор через тот же advisory-лок,** что и живой путь (общий helper, идентичный ключ
   `hashtext(str(order_resource_id))`). Закрывает гонку ревайвор↔живой хендлер по одному
   `order_resource_id`.
2. **Event-time guard в `_sync_allocations`:** не применять обновление **для ключа аллокации**
   (per-key, не на всё сообщение), чьё входящее событийное время (`time_end or collect_time`)
   `<=` записанного `last_collected_at`. Делает реплей идемпотентным и защищает от out-of-order,
   который неизбежен после репартиционирования / `max_workers>1`.

Fail-safe (**Phase 1.5**, рекомендуется; отдельным PR): partial **unique** index на активную
аллокацию — превращает пропущенный лок в явную ошибку, а не в тихий дубль. Единственное
предусловие — дедуп-прогон; advisory-лок уже снимает контеншн, поэтому ждать Phase 2 не нужно.
Подробности и разрешённый спор по таймингу — в `docs/scaling-phase-1.md`.

После Phase 1 `replicas > 1` безопасен **по корректности** даже при 1 партиции (throughput при
этом не растёт — Kafka отдаёт партицию одному консьюмеру; прирост даёт только Phase 2).

## Phase 2 — параллелизм (снять потолок №1)

1. **Репартиционировать statistic-топики по стабильному ключу сущности.** Ключ = тот же
   идентификатор, по которому идёт order_lookup (pool_name / tenant / fingerprint — зависит
   от обязательного инварианта порядка, см. открытые вопросы). Тогда сообщения одной
   сущности строго упорядочены и идут на один консьюмер, а **разные сущности — параллельно**.
   Бонус: контеншн advisory-лока сводится с кластерного к in-process.
2. **Консьюмеры = партициям**, автоскейл через **KEDA/HPA по консьюмер-лагу** (не по CPU).
3. **Бюджет соединений** под pgpool: выбрать transaction-pooling и разрулить несовместимость
   **asyncpg prepared statements** с пулером; пересчитать пулы под целевое число подов.
4. **Опционально `max_workers > 1` в поде** — теперь безопасно (event-time guard + advisory
   lock), **с оговоркой**: при равном `collect_time` нужен tie-breaker, иначе держать
   `max_workers=1` на партицию (см. phase-2 §7). Помогает на IO-bound участках; CPU-bound
   матчинг параллелится только подами.

Результат: пропускная способность растёт **почти линейно с числом партиций/подов — до
следующего бутылочного горлышка** (Postgres/pgpool, classifier на cache-miss, hot keys,
advisory-lock contention, rebalance, pool wait).

## Phase 3 — декомпозиция и масштаб БД

Изоляция blast-radius и независимое масштабирование. Часть можно начинать сразу после
Phase 1 (разделение деплоев не требует Phase 2).

1. **Разнести деплои по ролям из одного codebase:** orders / statistics-per-source /
   `statistic-recovery` / **revivor-worker** / reports (уже вынесены). Медленный источник
   больше не отъедает event loop / пул у остальных и не вызывает общий rebalance.
2. **Ревайвор — в свой деплой, событийный:** через топик (`statistic-recovery` или отдельный
   `lost-resource-revival` — см. phase-3 §2), дебаунс по identifier, троттлинг, собственный пул
   БД. Физически не может подвесить live ingestion (прямой урок инцидента).
3. **Убрать `_AsyncSharedExclusiveLock` и паузу-консьюмеров** — после Phase 1 (ревайвор под
   локом) и выноса ревайвора этот in-process механизм избыточен для корректности и сам был
   источником инцидентов.
4. **БД:**
   - read-реплики **только для read-only** (отчёты, recovery/revivor-сканы, API). ⚠️ Горячий
     путь ingestion (`order_lookup`/гидрация) остаётся на **primary** — иначе lag реплики →
     ложные `lost_resource` (см. phase-3 §4.1);
   - **тайм-партиционирование** `*_allocate_resource` + ретеншн/архивация (append-only растёт
     вечно);
   - тюнинг autovacuum под высокий write.

## Открытые вопросы (нужны решения команды)

1. **Инвариант порядка** — по инстансу (VM), по пулу/тенанту или по заказу? Определяет ключ
   партиционирования (Phase 2) и финальную форму event-time guard (Phase 1).
2. **Ключевой инвариант для Phase 2:** один `order_resource_id` всегда обрабатывается под
   **одним** partition key (т.е. `pool_name`/`tenant`/`fingerprint` ресурса стабилен и не
   мигрирует между значениями ключа). Только при нём контеншн advisory-лока сводится с
   кластерного к in-process. Нужно подтвердить по данным; если ресурс может менять ключ —
   ordering и лок разъезжаются (тогда пересматриваем ключ). **Важно:** ключ должен
   соответствовать инварианту порядка изменения **физической сущности**, а не просто совпадать
   с удобным `order_lookup`. Если один VM/ресурс может переехать между заказами или
   перематчиться иначе после обновления заказа — неверный ключ даст out-of-order на уровне
   бизнес-сущности, даже если технически партиции «упорядочены».
3. **Tie-breaker для event-time guard:** возможны ли два сообщения с одинаковым `collect_time`
   и разными данными? При `max_workers>1` это даёт недетерминированный last-write-wins. Если
   да — guard должен учитывать вторичный ключ (`collect_time` + Kafka offset/`sequence`), либо
   держим строгую сериализацию на партицию (`max_workers=1` на партицию). Зависит от формата
   сообщений коллекторов.
4. **Сколько партиций сейчас** на statistic-топиках и кто владелец (мы / команда
   коллекторов) — насколько свободно их менять.
5. **Целевой ×рост и профиль нагрузки** — во сколько раз по сообщениям/с; что дороже на
   горячем пути: `order_lookup` (сейчас дёшев) или классификатор по HTTP на cache-miss.
6. unique-index — **решено: Phase 1.5** (fail-safe, после дедуп-прогона; advisory-лок снимает
   контеншн, Phase 2 не нужен). Остаётся согласовать только объём дедуп-прогона.

  мержа Phase 1.
