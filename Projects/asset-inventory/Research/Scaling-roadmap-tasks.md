# Asset Inventory — декомпозиция тикетов на оптимизацию

Бэклог к `docs/scaling-roadmap.md` (+ phase-1/2/3 и rfc). Сгруппировано по фазам.
Размер: **S** ≈ ≤1 день, **M** ≈ 2–4 дня, **L** ≈ неделя+ / отдельный мини-проект.
Тип: **decision** (спайк/решение), **impl** (код/инфра), **migration** (БД).

Порядок фаз: **0 (обязательно до 2) → 1 (гейт) → 1.5 (опц. fail-safe) → 2 → 3**.
Phase 0 можно вести параллельно с Phase 1.

## Phase 0 — безопасность и видимость (обязательно до Phase 2)

### AI-SCALE-P0-1 — `statement_timeout` на запросах (S, impl)
- **Что:** ограничить время SQL-запроса на уровне движка/сессии (и/или БД-роли).
- **Зачем:** инцидент с seq scan 73 c подвесил Kafka; таймаут не даёт одному запросу ронять сервис.
- **Acceptance:** долгий запрос прерывается по лимиту с понятной ошибкой; значение в конфиге; покрыт тестом/ручной проверкой.
- **Зависит от:** AI-SCALE-P0-5 (иначе таймаут = тихая потеря сообщения).

### AI-SCALE-P0-2 — partial composite index на активные аллокации (S, migration)
- **Что:** `CREATE INDEX CONCURRENTLY ... (order_resource_id, instance_name, instance_id, start_date DESC) WHERE end_date IS NULL` на **всех** `*_allocate_resource` + общей `allocate_resource`.
- **Зачем:** hot-query `get_active_for_order_resources` (`app/cruds/allocate_resource.py`); текущий индекс только по `order_resource_id` слабее.
- **Acceptance:** `EXPLAIN` показывает index scan вместо seq scan; миграция concurrently; есть downgrade.

### AI-SCALE-P0-3 — вынести хардкод-ручки в конфиг (S/M, impl)
- **Что:** `max_workers` (по топикам), `pool_size/max_overflow/pool_timeout` (`app/db/db.py:30`), `_MAX_CONCURRENT_WRITE_PHASES` (`optimized_base_resource.py:38` — ⚠️ сначала AI-SCALE-P0-7, ручка может быть удалена), revival semaphore (`lost_resource_revivor.py:67`).
- **Зачем:** считать как **глобальный бюджет** (`N подов × пул`), а не per-pod; тюнить без релиза.
- **Acceptance:** все значения читаются из env с дефолтами = текущим; документирован расчёт бюджета соединений.

### AI-SCALE-P0-7 — судьба `_write_phase_semaphore`: удалить или перенести (S, decision+impl)
- **Что:** решить, что делать с `_MAX_CONCURRENT_WRITE_PHASES = 10` (`optimized_base_resource.py:37-38`; захваты — `:255`, `:530`, `:590`). Два варианта:
  - **A (предложение):** удалить все три захвата, константу и геттер. Admission control ввести осознанно в рамках P2-8, когда появится реальная конкурентность.
  - **B:** оставить как страховку, но тогда обязательно перенести `async with _get_write_phase_semaphore()` **выше** `_session_scope`, привязать значение к `pool_size` и добавить лог времени ожидания.
- **Зачем:** по логам прода (namespace `asset-inventory`, git_tag 4.15, 24 ч) семафор не связывает и связать не может:
  - write-фаза `total`: med **14 мс**, p90 96 мс, p99 137 мс, max 415 мс;
  - частота: 171 645/сутки, пик **521/мин = 8.7/с** → средняя конкурентность в секции **0.32** (по p99-длительности — 1.2) при лимите 10;
  - физический потолок конкурентов = число активных stat-топиков × `max_workers=1` ≈ 4–5;
  - `acquire` сессии во всех фазах: med/p90/p99 = **0.000 с** (max 2 мс), за 7 суток **0** упоминаний `QueuePool`/`TimeoutError`/`deadlock` → пул не является узким местом.

  Неконтендящийся `asyncio.Semaphore` возвращается без `await`, поэтому сегодня он не стоит ничего — но в `:845` он берётся под удерживаемым advisory-локом `allocation-recovery:{source}:{order_id}` (его же берёт `historical_allocation_rebuilder.py:91`). Это **латентная инверсия**: при `max_workers > 1` ожидание локального семафора начнёт удерживать лок в БД и соединение из пула.
- **Важно не путать роли:** advisory lock — *корректность* (взаимное исключение read-modify-write, кросс-подово); семафор — *admission control* (сколько корутин одновременно идут в БД). Второе при `max_workers > 1` нужно, иначе очередь переедет из процесса в Postgres, где ждут уже с занятым соединением.
- **Не относится к** `_revival_semaphore` (`lost_resource_revivor.py:65,67`): он взят **до** открытия сессии, порядок верный, остаётся как backpressure на fire-and-forget задачах. По логам не оценивается — за 7 суток на проде 0 запусков ревайвера при 666 сообщениях в топике заказов (~4/час); валидировать только реплеем (P2-7).
- **Хронология (проверено 2026-07-30, git + логи):** `_revival_semaphore` добавлен `c5b8fba` (DFDEV-1356) **2026-02-16** — через неделю после волны 16276 `QueuePool` timeout на тесте, то есть по конкретному инциденту и в fire-and-forget пути. `_MAX_CONCURRENT_WRITE_PHASES` добавлен `fb6d89c` **2026-05-12**, инцидента за спиной нет. Довод «write-phase семафор откалиброван под реальный лимит соединений» не подтверждается — это усиливает вариант A. Детали инцидентов — в AI-SCALE-P0-9.
- **Ещё один аргумент к A:** при `max_workers=1` на **всех** десяти сабскрайберах (`main.py:253,287,322,357,401,436,471,506,541,563`) потолок конкурентности = число одновременно активных stat-топиков (4–5), до лимита 10 не добраться. Из трёх точек захвата две (`:260`, `:535`) сегодня вообще не исполняются — они за флагом `APP_ENABLE_LOST_RESOURCES=False` (`:258`, `:533`), причём `:535` вызывается **под удерживаемым** recovery-локом (`:849`), т.е. включение lost-ресурсов оживит инверсию. Живая только `:595`, и она не контендится.
- **Acceptance:** решение зафиксировано (A или B); при A — код удалён, поведение не изменилось, `P0-3` больше не тащит эту ручку в конфиг; при B — захват выше `_session_scope`, значение из конфига, ожидание логируется и видно в P0-4.
- **Зависит от:** — (самостоятелен). **Связан с:** AI-SCALE-P0-3 (конфиг-ручки), AI-SCALE-P0-4 (метрика ожидания), AI-SCALE-P2-8 (`max_workers > 1` — момент, когда дроссель становится нужен).

### AI-SCALE-P0-4 — метрики в Prometheus (M, impl)
- **Что:** consumer-lag по топику/партиции, гистограммы времени обработки по фазам (уже логируются), pool wait, lock wait, deadlocks, slow SQL (`slow_sqlalchemy_query`).
- **Зачем:** без метрик масштабируем вслепую; нужны для KEDA (P2-4) и тюнинга.
- **Acceptance:** метрики экспортируются и видны в дашборде; алерты на лаг и pool saturation.

### AI-SCALE-P0-5 — commit-семантика: не терять сообщения (M, impl)
- **Что:** уйти от «`auto_commit=True` + проглоченное исключение». Коммит **после** успешной транзакции; retry с backoff; затем DLQ.
- **Зачем:** сейчас offset коммитится даже при сбое/таймауте → сообщение теряется (`main.py` statistic handlers). При росте лага/подов потери заметнее.
- **Acceptance:** сбой обработки → offset не закоммичен → ретрай; после N ретраев → DLQ; тест на DB-ошибку и на timeout.
- **Зависит от:** ничего; **блокирует безопасность P0-1**.

### AI-SCALE-P0-6 — разгрузить Classificator (M, impl)
- **Что:** распараллелить вызовы (`asyncio.gather`), предзаполнять hot-mappings на старте, circuit breaker + fallback, локальный in-memory кэш с фоновым refresh поверх Redis.
- **Зачем:** до 4 последовательных GET на cache-miss (видно в логах заказа) → latency-спайки при росте.
- **Acceptance:** на обработке заказа вызовы классификатора идут параллельно; cache-miss не блокирует > заданного таймаута; есть fallback.

### AI-SCALE-P0-8 — подтвердить, что advisory-локи идут на primary через pgpool (S, verify)
- **Статус: риск, скорее всего, УЖЕ ЗАКРЫТ конфигом.** Изначально тикет ставился как impl (добавить хинт `/*NO LOAD BALANCE*/`), но фактический конфиг это опроверг — осталась верификация на проде.
- **Что:** (а) снять конфиг прод-pgpool и убедиться, что он совпадает с тестовым; (б) подтвердить на проде, что лок физически берётся на primary; (в) зафиксировать конфиг и вывод в `docs/scaling-phase-2.md`. Хинт в код добавлять **только если (б) не подтвердится**.
- **Исходная гипотеза (не подтвердилась):** `SELECT pg_advisory_xact_lock(...)` синтаксически является `SELECT`, а `pg_advisory_*` не входит в дефолтный `black_function_list` (`currval,lastval,nextval,setval`) → лок может уехать на standby, пока записи идут на primary, и кросс-подовое взаимное исключение из CLAUDE.md станет фиктивным без ошибок в логах.
- **Почему не подтвердилась (факт с тест-стенда, pgpool-II 4.6, 2026-07-30):**
  - в pgpool 4.2+ `black_function_list` / `white_function_list` **переименованы** в `write_function_list` / `read_only_function_list`; довод про дефолт старого параметра к 4.6 неприменим;
  - в конфиге **оба списка пустые**, а в этом случае pgpool проверяет `provolatile` функции и volatile-функцию считает **пишущей** → отправляет на primary. `pg_advisory_xact_lock` объявлен VOLATILE;
  - `disable_load_balance_on_write = 'transaction'` — раз лок берётся первым стейтментом транзакции, все последующие чтения в ней тоже идут на primary, т.е. `get_last` защищён и от stale read;
  - `statement_level_load_balance = 'off'`.
- **Прод-конфиг снят 2026-07-30 и идентичен тестовому** по всем значимым параметрам: `num_init_children = 64`, `max_pool = 4`, `reserved_connections = 1`, `client_idle_limit = 1800`, `load_balance_mode = on`, `disable_load_balance_on_write = 'transaction'`, `statement_level_load_balance = 'off'`, оба function-списка закомментированы (пустые). `backend_hostname0/1` подтверждают две ноды. Значит рассуждение про `provolatile` применимо и к проду — **риск закрыт конфигом на обоих стендах**, остаётся только эмпирическая проверка.
- **Топология (проверено 2026-07-30):** prod (`ns asset-inventory`) — **2** ноды Postgres (`...postgresql-0`, `-1`) за pgpool → балансировка активна. test (`ns asset-inventory-test`) — **1** нода → тестовый стенд этот баг физически не воспроизводит, верификация только на проде.
- **Как подтвердить (б):** держа advisory-лок в открытой транзакции через pgpool, посмотреть `select * from pg_locks where locktype = 'advisory'` **двумя прямыми** подключениями — к primary и к standby. Лок должен быть виден только на primary. Альтернатива — временно `log_per_node_statement = on` и посмотреть, на какой node_id уходит запрос.
- **Если (б) не подтвердится:** хинт `/*NO LOAD BALANCE*/` перед локом в `optimized_base_resource.py:711` и `allocation_recovery_lock.py:16`. Предпочтителен конфигу, потому что `write_function_list` / `disable_load_balance_on_write` живут в values чужого чарта и могут быть потеряны при обновлении; хинт — no-op при прямом подключении.
- **Acceptance:** конфиг прод-pgpool снят и совпадение с тестовым подтверждено или зафиксированы расхождения; на проде показано, что advisory-лок виден в `pg_locks` только на primary; вывод выписан в доку. При расхождении — хинт в коде.
- **Зависит от:** — (самостоятелен). **Связан с:** AI-SCALE-P1-1, AI-SCALE-P0-9. **Блокирует:** AI-SCALE-P2-4 (защита Phase 2 должна быть подтверждённой, а не предполагаемой).
- **Зависит от:** — (самостоятелен). **Связан с:** AI-SCALE-P1-1 (если helper уже вынесен, хинт добавляется в одном месте), AI-SCALE-P0-9. **Блокирует:** AI-SCALE-P2-4.

### AI-SCALE-P0-9 — двусторонний бюджет соединений + asyncpg prepared statements (S/M, impl)
- **Что:** (а) `connect_args={"statement_cache_size": 0}` в `create_async_engine` (`app/db/db.py:26`); (б) снять фактические `num_init_children`, `max_pool`, `reserved_connections` с прод-pgpool и `max_connections`, `superuser_reserved_connections` с прод-Postgres; (в) пересчитать `pool_size` / `max_overflow` под **оба** неравенства ниже; (г) зафиксировать формулу и снятые значения в `docs/scaling-phase-2.md`.
- **Формула (двусторонняя — это главное):** у pgpool два лимита, и они смотрят в противоположные стороны.
  ```
  клиентская сторона:  Σ_деплоев (replicas × (pool_size + max_overflow)) ≤ num_init_children − reserved_connections
  backend-сторона:     num_init_children × max_pool                      ≤ max_connections − superuser_reserved − служебные
  ```
  **Считать надо по всем деплоям, а не по репликам одного.** Из одного образа поднимается несколько точек входа с разными `args` (`asset-inventory`, `-api`, `-worker`, `allocation-recovery-worker`), и каждая импортирует `app/db/db.py`, где `engine` создаётся **на уровне модуля** — значит у каждого пода свой пул на `20+20`. В `ns asset-inventory-test` таких подов **4**, в `ns asset-inventory` — **3** (api-пода нет). Прежняя формула считала только `replicas` основного деплоя и занижала потребление в 3–4 раза.
  `reserved` = `superuser_reserved_connections` + постоянные клиенты `repmgr` и `sr_check_user` (видны в логах Postgres непрерывно) + health-check'и pgpool + запас на alembic при старте.
  Первое неравенство — это «у pgpool коннектов меньше, чем у базы». Второе — обратное: `num_init_children × max_pool` backend-соединений против `max_connections`, то есть **pgpool способен не защитить Postgres от исчерпания, а привести к нему** (документация pgpool прямо требует `max_connections ≥ num_init_children × max_pool`). Нарушать нельзя ни одно; исторически нарушались оба, но на разных стендах.
- **Фактические значения (тест, pgpool-II 4.6, снято 2026-07-30 из `/opt/bitnami/pgpool/conf/pgpool.conf`):** `num_init_children = 64`, `max_pool = 4`, `reserved_connections = 1`, `child_life_time = 300`, `connection_life_time = 0`, `client_idle_limit = 1800`, `connection_cache = on`. Дефолты чарта, на которые я опирался раньше (32 / 15 / 0), **не подтвердились** — считать только по снятым значениям. ⏳ Прод-конфиг и `max_connections` ещё не сняты.
  **Всё снято 2026-07-30, prod и test совпадают:** pgpool — 64 / 4 / 1 / 1800; Postgres — `max_connections = 400`, `superuser_reserved_connections = 3`.
  ```
  клиентская сторона, test (4 пода):  4 × 40 = 160  >  64 − 1 = 63    ✗ нарушено СЕЙЧАС (в 2.5 раза)
  клиентская сторона, prod (3 пода):  3 × 40 = 120  >  63             ✗ нарушено СЕЙЧАС (в 1.9 раза)
  backend-сторона, оба стенда:        64 × 4 = 256  ≤  400 − 3 = 397  ✓ сходится с запасом
  ```
  Итог: **узкое место — только клиентская сторона pgpool.** Backend-сторона (`max_connections`) имеет полуторакратный запас, то есть амплификация `num_init_children × max_pool` сегодня безопасна на обоих стендах. Дефицит соединений упирается исключительно в `num_init_children = 64`, и поднимать его есть куда.
  Практические выводы:
  - **Клиентское неравенство нарушено на обоих стендах уже сегодня** — просто пулы не выбираются целиком: SQLAlchemy открывает соединения лениво, а транзакции короткие (медиана write-фазы 24 мс). При возврате долгих сессий (backfill, rebuild, регресс в коде) это снова упрётся в потолок, как в январе.
  - ⚠️ **Январь этими числами объяснять нельзя.** Значения не дефолтные, потому что devops донастраивал и Postgres, и pgpool — то есть снятый конфиг это, скорее всего, уже *результат* реакции на инцидент, а не его причина. Какими были `num_init_children` / `max_pool` / `max_connections` в январе, мы не знаем. Дешевле спросить devops, что и когда меняли, чем реконструировать по логам.
  - Запас есть только в backend-стороне, и он большой (`max_connections = 400`, а не дефолтные 100). Значит амплификация `num_init_children × max_pool` на тесте безопасна.
  - Для Phase 2: при `num_init_children = 64` бюджет на **все** поды вместе — 63 соединения. Пул `5+5` даёт 6 подов, `3+3` — 10 подов. Либо поднимать `num_init_children` (запас по `max_connections` позволяет: 400 − 3 − служебные).
  - ⚠️ **Прод-цифры не сняты**, и январские 1054 `FATAL` на прод-Postgres пока не объяснены: если у прода тоже `max_connections = 400` и `64 × 4 = 256`, backend-неравенство не нарушается и причина в чём-то другом (иные values, другие клиенты, миграции). Не закрывать тикет до снятия прод-конфига.
- **Побочная находка — `client_idle_limit = 1800`:** pgpool рвёт клиентское соединение после 30 мин простоя, причём (по комментарию в самом конфиге) **даже внутри открытой транзакции**. Долгоживущие соединения SQLAlchemy периодически убиваются — этим объясняется постоянный churn в логах прода (~3300 `new connection received` за 3 ч). Сегодня безвредно, потому что `pool_pre_ping=True` ловит это на checkout, а транзакции короткие (медиана write-фазы 24 мс). Станет источником обрывов, когда появятся долгие транзакции — backfill, `historical_allocation_rebuilder`, миграции. Учесть при P2-7 и P3-3.
- **Зачем — подтверждено по логам (Kibana `logs-*`, ретенция с 2025-09, проверено 2026-07-30):**
  - **test:** pgpool `ERROR: Sorry, too many clients already` — **819** событий (янв 2026 — 720, фев — 99), на Postgres теста при этом **0**. Здесь лимитером была клиентская сторона, `num_init_children`.
  - **prod:** Postgres `FATAL: sorry, too many clients already` — **1054** события, все в янв 2026 (пик 2026-01-21 15:49), на pgpool прода — всего 2. Здесь уперлись в `max_connections`, то есть в backend-сторону.
  - **приложение:** `QueuePool` timeout — **16276** событий, только на тесте, недели 2026-02-02 и 2026-02-09; на проде **0** за всю ретенцию.
  - С фев 2026 событий нет ни на одном стенде; сейчас session acquire = 0 мс на медиане и p99 на обоих стендах, `QueuePool` = 0. То есть это **не живая проблема, а guardrail перед Phase 2**.
  - Хронология правок: `pool_size=20/max_overflow=20` появились коммитом `ef41ec6` **2026-01-22** — на следующий день после прод-инцидента. Первый семафор (`_revival_semaphore`, `c5b8fba` DFDEV-1356) — **2026-02-16**, через неделю после волны `QueuePool` на тесте, в fire-and-forget пути ревайвора. `_MAX_CONCURRENT_WRITE_PHASES` — только `fb6d89c` **2026-05-12**, без инцидента за спиной (важно для AI-SCALE-P0-7: аргумент «семафор откалиброван под реальный лимит» не подтверждается).
- **Как проявляется исчерпание клиентской стороны:** при `reserved_connections = 0` лишний коннект не получает `too many clients already`, а **виснет в TCP backlog** — снаружи это случайные таймауты, а не явная ошибка. На тесте фактически стоит `reserved_connections = 1`, то есть отказ явный (`ERROR: Sorry, too many clients already` — именно эти 819 событий и видны в логах янв–фев). Проверить, что на проде тоже `> 0`, и не опускать до нуля при тюнинге.
- **Про (а):** asyncpg использует именованные prepared statements (`__asyncpg_stmt_N__`) и кэш на 100 записей; при переиспользовании backend-коннекта pgpool между клиентскими сессиями это даёт `prepared statement ... already exists` / `cached plan must not change result type`. За всю ретенцию таких ошибок в логах **не найдено** — то есть риск латентный (проявится при N подах / transaction-pooling), а не текущий.
- **Acceptance:** оба неравенства сходятся для целевого числа подов на снятых (а не дефолтных) значениях; `reserved_connections > 0`, чтобы отказ был явным; за нагрузочный прогон 0 ошибок prepared statements, 0 `QueuePool`, 0 `too many clients`; значения пула читаются из конфига; лимиты либо подняты в values чарта, либо задокументированы как ограничение на `replicas`.
- **Зависит от:** AI-SCALE-P0-3 (пул в конфиг). **Связан с:** AI-SCALE-P0-7, AI-SCALE-P0-8, AI-SCALE-P2-6. **Дедуп:** покрывает asyncpg/бюджетную часть AI-SCALE-P2-6.
- **⚠️ Отдельная зацепка для AI-SCALE-P0-5:** в январе на проде было 1054 `FATAL: sorry, too many clients already`, но прод-приложение за тот же период не залогировало ни `QueuePool`, ни `OperationalError`. Либо отказы получал не сервис (api-под, миграции, repmgr), либо исключения были проглочены — и тогда прод молча терял сообщения. Проверить при работе над commit-семантикой.

## Phase 2 — параллелизм (детали — `docs/scaling-phase-2.md`)

### AI-SCALE-P2-1 — решить инвариант порядка и ключ партиционирования (M, decision)
- **Что:** зафиксировать инвариант (по инстансу/пулу/заказу) и ключ; подтвердить по данным, что `order_resource_id` всегда под одним ключом и ресурс не мигрирует между значениями ключа.
- **Зачем:** блокирует весь дизайн Phase 2; неверный ключ → out-of-order на уровне бизнес-сущности.
- **Acceptance:** документированное решение + анализ распределения ключей (нет доминирующего hot-пула).

### AI-SCALE-P2-2 — producer-side: ключи + партиции (M/L, decision+impl, кросс-команда)
- **Что:** Вариант A — коллекторы ставят `key=identifier` + N партиций; Вариант B — внутренний re-key слой (consume→republish в keyed-топик).
- **Зачем:** партиционирование определяется продюсером; топики производят коллекторы.
- **Acceptance:** согласован путь A/B; для наших топиков (`statistic-recovery`, retry) ключ ставим сами.
- **Зависит от:** AI-SCALE-P2-1.

### AI-SCALE-P2-3 — увеличить партиции (S, migration/ops)
- **Что:** поднять число партиций (или версионированные топики `*.v2`), запас под целевой ×рост.
- **Зачем:** снять потолок №1.
- **Acceptance:** N партиций; план перехода без длительного разрыва порядка; **помнить: необратимо** (уменьшить нельзя).
- **Зависит от:** AI-SCALE-P2-2.

### AI-SCALE-P2-4 — consumer scaling config (S, impl)
- **Что:** `replicas ≤ partitions`, `max_workers=1` на партицию (сериализация на партицию), `Recreate → RollingUpdate`.
- **Acceptance:** партиции равномерно распределены по подам; порядок на партицию сохранён.
- **Зависит от:** AI-SCALE-P2-3, Phase 1.

### AI-SCALE-P2-5 — KEDA автоскейл по лагу (S, impl)
- **Что:** `ScaledObject` (kafka scaler) по consumer-лагу, `maxReplicaCount ≤ partitions`.
- **Acceptance:** поды масштабируются по лагу; не превышают число партиций.
- **Зависит от:** AI-SCALE-P0-4, AI-SCALE-P2-3.

### AI-SCALE-P2-6 — выбор пулера под N подов (M, decision)
- **Что:** решить, чем мультиплексировать коннекты при N подах: тюненный pgpool (transaction-pooling) / отдельный PgBouncer в transaction mode / без пулера с уменьшенным per-pod пулом. Проверить, что нет опоры на session state (session-scoped advisory-локи, `SET`, temp tables) — сейчас используются только xact-scoped, это надо сохранить.
- **Зачем:** без пулера `N × (pool_size + max_overflow)` упирается в `max_connections`, а много idle backend-процессов в Postgres дороже, чем idle-клиентов в пулере. При этом pgpool совмещает пулинг с маршрутизацией запросов — именно оттуда риск AI-SCALE-P0-8; PgBouncer делает только пулинг и локи не ломает, но не даёт failover.
- **Учесть:** прод сидит на pgpool из чарта `asset-inventory-db-postgresql-ha` — это же единственный источник failover для 2 нод. Отказ от pgpool = failover надо решать на уровне сервиса/оператора.
- **Acceptance:** решение зафиксировано с обоснованием; нагрузочный прогон на выбранной схеме без ошибок PS и без исчерпания соединений.
- **Зависит от:** AI-SCALE-P0-9 (базовый бюджет и `statement_cache_size` уже закрыты там), AI-SCALE-P2-7 (цифры прогона).

### AI-SCALE-P2-7 — нагрузочный стенд / реплей (M, impl)
- **Что:** воспроизведение реального трафика ×N для проверки дрейна лага и потолков.
- **Acceptance:** прогон ×N; собраны метрики лага/лока/пула/p95; зафиксирован следующий bottleneck.

### AI-SCALE-P2-8 — (опц.) `max_workers > 1` + tie-breaker (S, impl)
- **Что:** рамп `2→4→8` на тяжёлом источнике; при равном `collect_time` — вторичный ключ (offset) в guard, иначе держать `max_workers=1`/партиция.
- **Зависит от:** AI-SCALE-P2-7, Phase 1.

- **Зависит от:** AI-SCALE-P3-1.

### AI-SCALE-P3-3 — ревайвор в событийный деплой + дебаунс (M, impl)
- **Что:** заменить inline `create_task` (`order.py:120–133`) на `broker.publish(key=identifier)`; отдельный revivor-консьюмер со своим пулом; дебаунс по identifier (keyed-топик/Redis).
- **Зачем:** ревайвор не должен делить event loop/пул с live ingestion (урок инцидента).
- **Acceptance:** ингест не страдает от ревайвора; повторные запросы по одному identifier схлопываются; inline-путь удалён.
- **Зависит от:** Phase 1 (ревайвор под локом), AI-SCALE-P3-2.

### AI-SCALE-P3-4 — удалить `_AsyncSharedExclusiveLock` + паузу консьюмеров (S, impl)
- **Что:** убрать lock/пауза-механику из `main.py` (см. phase-3 §3); recovery-хендлер работает как обычный (запись через advisory-лок).
- **Зачем:** после Phase 1 + изоляции ревайвора механизм избыточен и сам был источником инцидентов.
- **Зависит от:** AI-SCALE-P3-3.

### AI-SCALE-P3-5 — read-реплики для read-only (M, impl)
- **Что:** `POSTGRES_READ_HOST` + второй движок/`read_session_factory`; роутить **только** read-only (отчёты, recovery/revivor-сканы, API). ⚠️ Горячий путь ingestion — на primary.
- **Зачем:** разгрузить primary по чтению без риска read-after-write на ингесте.
- **Acceptance:** read-only пути ходят на реплику; `order_lookup`/гидрация остаются на primary.

### AI-SCALE-P3-6 — тайм-партиционирование `*_allocate_resource` (L, migration)
- **Что:** declarative RANGE-партиционирование по `start_date`/`created_at` (pg_partman/вручную); онлайн-миграция большой таблицы.
- **Зачем:** append-only история растёт неограниченно.
- **Acceptance:** запись/чтение идут по партициям; план онлайн-миграции отрепетирован на тесте; отдельный проект с бэкапом.

### AI-SCALE-P3-7 — ретеншн/архивация + autovacuum (M, ops)
- **Что:** `DETACH`/архив старых партиций по политике; тюнинг autovacuum под high-write.
- **Зависит от:** AI-SCALE-P3-6.
