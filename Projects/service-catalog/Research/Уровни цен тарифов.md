# Уровни цен тарифов

#project #research

> [!info] Статус
> Реализовано 2026-09-12. Хранилище, XLSX round-trip и защищённый импорт находятся
> в коде; перенос согласования на уровни остаётся отдельным этапом.

Связанные заметки: [[Overview]], [[Architecture]], [[API]].

## Зачем

В Bitrix уже действует матрица согласования цен, а Ordering пока повторно
запрашивает согласование по старой логике минимальной отпускной цены.
Первый этап — создать в классификаторе хранилище уровней и однократно
загрузить согласованные значения из «Матрица скидок_v5.xlsx». Сама матрица является источником
значений, но не форматом импортного API: бизнес переносит нужные цены в Excel-выгрузку
классификатора и загружает её обратно.

В этот этап входят защищённый API импорта XLSX и добавление уровней в существующую
Excel-выгрузку классификатора для сценария «выгрузить → отредактировать → загрузить». Не входят
UI, API чтения и редактирования отдельных уровней, новая логика Ordering, Bitrix и Comet.

## Исходные данные и бизнес-правила

- В файле описаны 566 тарифов для 57 услуг.
- Актуальная матрица содержит три ценовых уровня. Четвёртая строка на листе
  согласования — не дополнительный ценовой уровень. Цена без скидки доступна
  без согласования.
- `New` — ценовой порог уровня. В хранилище записывается его абсолютная цена.
- `Возможная скидка` для хранения и выбора логики согласования не нужна.
- Уровни накапливаются: цена активирует все уровни, для которых цена сделки не выше
  порога. Например, при порогах 900, 800 и 700 цена 750 активирует уровни 1 и 2,
  а цена 650 — уровни 1, 2 и 3.
- Уровни согласуют: Pre-sale; руководитель Pre-sale; коммерческий/финансовый
  уровень. Роли и матрица согласования пока не хранятся в service-catalog.
- Сравнивать цену сделки нужно с абсолютной ценой. Процент скидки производен от GPL
  и может измениться при изменении GPL.

## Текущая модель

`classifier.models.tariff.TariffElement` хранит:

- `price` — GPL;
- `cost_price` — минимальную отпускную цену;
- `beeline_price`;
- вычисляемый `max_discount`.

`Tariff` ссылается на `TariffElement` обычным `ForeignKey`, поэтому один элемент тарификации
может быть связан с несколькими тарифами. Поэтому новые уровни нельзя безопасно
считать общими свойствами `TariffElement`.

Связанные участки кода:

- `backend/classifier/models/tariff.py` — `TariffElement`, `Tariff`, `update_price_code`;
- `backend/classifier/serializers/tariff_serializer.py` — создание/обновление тарифов и `is_code_valid`;
- `backend/classifier/services/draft_publication.py` — расчёт `price_code` при публикации черновика;
- `backend/classifier/models/__init__.py` — явная регистрация моделей в changelog-сигналах;
- `backend/changelog/signals/changes_signals.py` — создание журнала, сброс кэша и запуск
  `update_product_cache` после `save`.

## Решение по хранению

Добавить отдельную модель `TariffPriceLevel` со ссылкой на `Tariff`, а не колонки в
`TariffElement`:

| Поле | Назначение |
|---|---|
| `tariff` | `ForeignKey` на `Tariff`, `on_delete=CASCADE`, `related_name='price_levels'` |
| `level` | Номер уровня, положительное целое |
| `price` | Абсолютный ценовой порог из колонки `New`, `Decimal(10, 2)` |

Отдельная валюта в `TariffPriceLevel` не хранится. Порог использует
`Tariff.element.currency`; конвертация валют при импорте не выполняется.

Ограничения:

- `UniqueConstraint(tariff, level)`;
- `level > 0`;
- `price > 0`.

С ростом номера уровня скидка увеличивается, а пороговая цена уменьшается. Это
правило проверяется при импорте, но в самом service-catalog не реализуется выбор согласующих.
Какие уровни активирует цена сделки, позже определяет потребитель данных.

Схема не ограничивает число уровней тремя. Текущая разовая загрузка ожидает
уровни 1–3, но последующая смена матрицы не потребует миграции схемы. Проценты скидки и
роли согласующих на этом этапе не хранятся.

Уровни относятся к конкретной ценовой версии `Tariff`. При создании новой версии или
черновика они не копируются: новая версия означает новую GPL и требует заново рассчитанных
порогов. Поэтому отсутствие уровней у нового тарифа допустимо.

Модель должна наследовать `ChangeLogMixin` и быть добавлена в список моделей в
`classifier/models/__init__.py`: одного наследования миксина недостаточно для подключения
сигналов.

## Импорт уровней через API

Создать защищённый аутентификацией `POST`-эндпоинт, принимающий XLSX как
`multipart/form-data`. Management-команда не нужна. Автором изменений в changelog является
`request.user`.

Эндпоинт принимает только `.xlsx`. Проверяются расширение и фактическая возможность открыть
файл как OOXML-книгу; `.xls`, `.csv`, повреждённые и только переименованные файлы возвращают
HTTP `400` без изменений БД.

Максимальный размер файла — 10 МБ. Превышение лимита возвращает HTTP `400` до разбора книги и
не меняет БД.

Дополнительно ограничены суммарный распакованный размер OOXML-архива — 100 МБ — и количество
строк данных на первом листе — 10 000. Превышение любого лимита является фатальной ошибкой
файла и возвращает HTTP `400`.

На текущем этапе эндпоинт доступен любому аутентифицированному пользователю через
`IsAuthenticated`. Во вьюхе нужно оставить TODO с причиной: определить и добавить отдельные
права на импорт; возможный будущий вариант — allowlist разрешённых email. Само ограничение по
правам или email в этот тикет не входит.

```http
POST /api/tariff-price-levels/import/
Content-Type: multipart/form-data

file=@tariff-price-levels.xlsx
```

Импорт реализуется отдельной ручкой. Существующий `/api/excel/` остаётся ручкой выгрузки и не
принимает файлы; в нём меняется только состав экспортируемых колонок.

Предлагаемый бизнесу формат — одна строка на тариф:

| Составной код | Услуга | Элемент услуги | Тариф | GPL (необязательно) | Цена уровня 1 | Цена уровня 2 | Цена уровня 3 |
|---|---|---|---|---:|---:|---:|---:|

Составной код является обязательным и единственным идентификатором тарифа. Текстовые названия
сохраняются в файле только для читаемости и понятного отчёта; импортер их не сверяет с БД.
Если код пуст,
некорректен, не найден или соответствует нескольким тарифам, строка считается ошибочной.
Fallback-сопоставление по названиям не выполняется: без однозначно найденного кода неизвестно,
к какому тарифу добавлять уровни.

Файл может быть получен из общей Excel-выгрузки классификатора и содержать дополнительные
колонки. Импортер читает только составной код и цены уровней; GPL, названия и остальные поля
необязательны для импорта и игнорируются.

API поддерживает только этот round-trip формат. Отдельный адаптер для исходной структуры
«Матрица скидок_v5.xlsx» не реализуется.

### Выгрузка

Существующий `/api/excel/` должен добавлять в строку тарифа колонки `Цена уровня 1`,
`Цена уровня 2` и `Цена уровня 3`. Отсутствующий уровень выгружается пустой ячейкой. Запрос
уровней нужно выполнить без N+1, предварительно загрузив `price_levels` для queryset тарифов.
Полученный XLSX должен без преобразований приниматься API импорта.

В выгрузке три колонки уровней располагаются сразу после существующей `Базовая цена` (GPL),
перед остальными ценовыми и служебными полями.

Формат текущих API содержит строго три колонки уровней и не формирует их динамически по данным
БД. Сама модель по-прежнему не ограничивает возможное число уровней.

Заголовки `Цена уровня 1`, `Цена уровня 2` и `Цена уровня 3` обязательны в импортируемом файле,
даже если все значения некоторого уровня пусты. Отсутствие любого из этих заголовков является
фатальной структурной ошибкой файла; пустые значения обрабатываются построчно.

Обязательные заголовки перед сравнением очищаются через `strip` и сопоставляются без учёта
регистра. Например, `составной код` и `Составной код` обозначают одну колонку. Если после такой
нормализации в файле обнаруживаются дубли обязательного заголовка, файл отклоняется как
структурно неоднозначный.

Колонки вида `Цена уровня N`, где `N` не входит в `1–3`, также отклоняются как структурная
ошибка: текущий контракт импорта содержит строго три уровня.

Колонки `составной код` и `Цена уровня 1–3` являются системными для round-trip и всегда
включаются в файл, даже если пользователь скрыл их в настройках таблицы.

Алгоритм:

1. Читать первый лист книги независимо от его названия; остальные листы игнорировать. Проверить
   обязательные заголовки составного кода и уровней, а также наличие кэшированных значений формул.
   Заголовки нормализовать через `strip` и регистр; дубли после нормализации считать фатальной
   ошибкой. Неизвестные и необязательные колонки игнорировать. Читать книгу
   в режимах `data_only=True` и `data_only=False`, чтобы отличить пустую ячейку от формулы без
   сохранённого результата. Формула с сохранённым числовым результатом допустима; формула без
   результата делает ошибочной только содержащую её строку.
2. Пропустить строки-заголовки категорий, в которых нет тарифа.
3. Нормализовать только пробелы: trim, NBSP и повторные пробелы. Не применять нечёткое
   сопоставление.
4. Проверить обязательный полный составной код, включая `price_code`, и сопоставить по нему
   ровно один тариф. Уровни менять только у неудалённых, неархивных и нечерновых тарифов.
   Существующий архивный тариф или черновик с таким кодом не изменять и учитывать в
   `skipped_non_importable_rows`; если с тем же кодом есть ровно один активный тариф, архивные
   и черновые совпадения не делают его неоднозначным. Наличие интервала действия или
   доступности услуги не считать неявным условием импорта. Названия услуги, элемента и тарифа
   использовать только для отображения в отчёте. Fallback и дополнительную проверку по названиям
   не выполнять. Рядом с фильтром оставить WHY-комментарий: архивные тарифы больше не продаются,
   поэтому их уровни не изменяются.
5. Для пустого/некорректного кода, нуля или нескольких совпадений не менять БД, а добавить
   строку в отчёт. Ошибка отдельной строки не отменяет загрузку остальных строк.
6. Перед разбором чисел применить `strip`. Пустая ячейка или строка, оставшаяся пустой после
   `strip`, означает отсутствие конкретного уровня: этот уровень не создавать, остальные
   заполненные уровни строки можно загрузить. Если пусты все уровни, строку пропустить без
   ошибки. В непустой строковой цене удалить обычные пробелы и NBSP, а десятичную запятую
   заменить точкой; затем разбирать через `Decimal`, не через `float`. Валютные символы и другие
   посторонние знаки не удалять. Значение с более чем двумя знаками после запятой не округлять,
   а считать ошибкой. Ноль, отрицательное или не приводимое к `Decimal` значение делает всю строку невалидной и добавляет её в отчёт
   ошибок для последующей обработки. GPL из файла не сравнивать и не обновлять: она не участвует
   в сопоставлении или валидации импорта. Для верхней границы использовать актуальную GPL из БД.
   Непоследовательный набор уровней допустим: например, при заполненных уровнях 1 и 3 пустой
   уровень 2 не создаётся и не делает строку ошибочной.
7. Проверить дубли составного кода в файле. Все строки с повторяющимся кодом отклонить как
   `duplicate_tariff_code`, не выбирая первую или последнюю. Проверить положительность порогов и
   строгое убывание абсолютной цены `New` при росте номера уровня. Каждый переданный порог должен
   быть не выше текущей GPL из БД. При частичном обновлении порядок проверять в итоговом наборе
   для пар, где хотя бы один уровень передан в файле; ранее существовавшие нарушения только между
   нетронутыми уровнями не блокируют строку. Равные, возрастающие или превышающие GPL переданные
   пороги делают всю строку ошибочной. Колонку `Возможная скидка` не загружать.
8. Создать или обновить уровень по ключу `(tariff, level)` только при различии значений.
   Отсутствующие в файле уровни не удалять.
9. Фатальные структурные ошибки книги — например, отсутствие первого листа или обязательных колонок —
   отменяют всю загрузку. Валидные строки записать в `transaction.atomic()` одним набором;
   строки с ошибками в него не включать.
10. Перед сравнением и записью заблокировать затронутые тарифы через `select_for_update()` в
    стабильном порядке. Параллельные загрузки применяются последовательно; последняя
    обработанная загрузка побеждает, а каждое фактическое изменение попадает в changelog.
11. Повторный запуск с тем же файлом не создаёт ни дублей, ни новых записей журнала.

Ответ API должен показывать хотя бы:

- число прочитанных, успешно загруженных, ошибочных и пустых строк;
- число пропущенных архивных тарифов и черновиков;
- созданные, обновлённые и неизменившиеся уровни;
- ненайденные и неоднозначные тарифы с номером строки и составным кодом;
- ошибки чисел, формул, дубли и нарушения порядка порогов;
- неизменившиеся уровни из заполненных ячеек.

Если часть строк загружена, а часть отклонена, API возвращает HTTP `200` со статусом
`partial_success`. Ошибки возвращаются структурированным массивом, как минимум с номером строки,
составным кодом, полем, исходным значением, машинным кодом и понятным сообщением. Ожидается, что
таких ошибок будет мало и фронт позволит пользователю обработать каждую через меню.

Статусы ответа для корректно разобранного файла:

- `success` — все непустые строки загружены;
- `partial_success` — часть строк загружена, часть отклонена;
- `validation_failed` — ни одна строка не загружена из-за построчных ошибок.

Если все строки пропущены из-за пустых уровней и построчных ошибок нет, ответ имеет статус
`success`, `loaded_rows=0` и количество `skipped_empty_rows`.

Все три результата возвращаются с HTTP `200`. HTTP `400` используется только для ошибки самого
файла: это не XLSX, книгу нельзя прочитать, нет первого листа или обязательных колонок.

Эндпоинт не запрашивает исправления интерактивно. Уточнение корректных значений у пользователя
и повторная загрузка исправленного файла в этот тикет не входят.

## Changelog при массовой загрузке

Обычный `save()` на каждый уровень вызовет changelog-сигналы, а затем сброс всего кэша,
фоновую задачу обновления продуктов и уведомления на каждую запись журнала.

Для разовой загрузки нужен массовый путь:

- `bulk_create`/`bulk_update` уровней;
- одна явная запись `ChangeLog` от имени `request.user` на каждый фактически изменившийся
  тариф; внутри записи агрегируются прежние и новые значения всех его уровней;
- записи импорта не запускают стандартную массовую рассылку `Notify`;
- один сброс кэша после успешного коммита, только если уровни фактически изменились;
- повторный импорт без изменений не добавляет записей в журнал.

Это сохраняет журнал изменений, но не создаёт массовую рассылку и тысячи побочных вызовов
сигналов.

## `price_code` и старые цены

Уровни цен не участвуют в генерации `price_code`: они не меняют товарный состав тарифа и
не должны менять составной код, по которому Ordering сопоставляет тарифы.

API импорта не должен изменять `price`, `cost_price`, `beeline_price`, `max_discount` и `price_code`.
Старые поля продолжают работать до отдельного переезда согласования.

`Tariff.update_price_code()` сравнивает список изменённых полей `TariffElement` на точное равенство
`['id', 'price']` или `['id', 'price', 'max_discount']`. Новые уровни находятся в отдельной модели,
поэтому список полей `TariffElement` не расширяется и описанная в исходной постановке регрессия
не возникает. Метод в этом тикете не меняется; отсутствие влияния импорта на `price_code` и
`concated_code` закрепляется тестами.

## Ошибочные строки

В матрице есть 39 тарифов с ненулевой единовременной ценой и нулями в ценах уровней.
Ноль обрабатывается так же, как любое другое непустое невалидное значение: строка получает
ошибку `non_positive_price`, уровни для неё не меняются, а загрузка остальных валидных строк
продолжается. Отдельного статуса для этих 39 тарифов нет.

## План реализации

1. Добавить `TariffPriceLevel`, ограничения БД, миграцию и changelog-регистрацию.
2. Реализовать парсер книги и полную предварительную валидацию без записи в БД.
3. Добавить цены уровней в существующую `/api/excel/` выгрузку без N+1.
4. Реализовать защищённый `IsAuthenticated` multipart `POST` API с идемпотентной
   транзакционной записью, changelog от имени `request.user` и отчётом в ответе. Во вьюхе
   оставить TODO о будущем отдельном permission/allowlist email.
5. Добавить тесты модели, Excel round-trip, API импорта, прав доступа, changelog и регрессий
   `price_code`.
6. Запустить тесты `classifier`, полный test suite и `qa`.
7. На копии продовых данных выполнить dry-run, разобрать все несопоставленные строки и только
   после этого запустить запись.

## Проверки

Минимальный набор:

- миграция применяется к пустой и к актуальной БД;
- ограничения модели отклоняют дубль уровня, нулевой и отрицательный порог;
- импорт отклоняет строку с равными или возрастающими ценами заполненных уровней;
- импорт отклоняет строку, если хотя бы один заполненный порог превышает актуальную GPL из БД;
- уровни не имеют отдельной валюты и используют валюту связанного `TariffElement`;
- API отклоняет неаутентифицированный запрос;
- API разрешает импорт любому аутентифицированному пользователю;
- Excel-выгрузка содержит составной код и цены уровней, а полученный файл принимается импортом;
- исходная структура «Матрица скидок_v5.xlsx» напрямую не принимается;
- колонки уровней расположены сразу после `Базовая цена`;
- обязательные round-trip колонки не исчезают из-за пользовательских настроек таблицы;
- отсутствие любого из трёх обязательных заголовков отклоняет файл до записи в БД;
- регистр и внешние пробелы заголовков не влияют на импорт, но нормализованный дубль заголовка
  отклоняет файл;
- частично успешный импорт возвращает HTTP `200`, статус `partial_success`, корректные счётчики
  и структурированный список ошибок;
- полностью невалидный набор строк возвращает HTTP `200` и `validation_failed`, а структурно
  некорректный файл — HTTP `400` без изменений БД;
- `.xls`, `.csv`, повреждённый или только переименованный в `.xlsx` файл возвращает HTTP `400`;
- XLSX размером более 10 МБ отклоняется до разбора и записи;
- файл только с пустыми уровнями возвращает `success`, ноль загрузок и корректный счётчик
  `skipped_empty_rows`;
- API пропускает заголовки, однозначно сопоставляет тарифы, загружает валидные строки и
  отчитывается о каждой незагруженной строке;
- все строки с повторяющимся составным кодом отклоняются независимо от их порядка в файле;
- код архивного, удалённого или чернового тарифа не принимается и возвращается как ошибка строки;
- пустая ячейка уровня не создаёт этот уровень и не мешает загрузке остальных уровней строки;
- заполненный уровень после пустого допустим и загружается;
- строка со всеми пустыми уровнями пропускается без ошибки, а непустое невалидное значение
  добавляет всю строку в отчёт ошибок;
- строковые цены с пробелами/NBSP и десятичной запятой принимаются, а значения с валютными
  символами отклоняются;
- значения с более чем двумя знаками после запятой отклоняются без округления;
- формула с кэшированным числом принимается, а формула без сохранённого результата отклоняет
  только свою строку;
- первый запрос создаёт ожидаемые уровни и по одной записи changelog с автором `request.user`
  на каждый изменившийся тариф;
- импорт не отправляет уведомление на каждую запись changelog;
- второй запрос с тем же файлом не меняет БД и журнал;
- параллельные запросы для одного тарифа выполняются последовательно без потерянного обновления;
- изменившиеся ячейки обновляют только нужные уровни и пишут одну агрегированную запись на тариф;
- расхождение GPL между файлом и БД игнорируется, уровни загружаются, а GPL в БД не изменяется;
- `price`, `cost_price`, `beeline_price`, `max_discount`, `price_code` и `concated_code` до и после импорта не
  изменяются;
- обновление только GPL по-прежнему корректно инкрементирует `price_code`, а изменение уровней его
  не меняет;
- создание и публикация новой ценовой версии не копируют старые уровни;
- публикация черновика и обычные редактирования тарифа не получают регрессий.

## Валидация плана

План независимо проверен Claude Code 2.1.267, Kimi Code 0.40.1 и Codex. Общий вывод:
отдельная дочерняя модель лучше колонок в `TariffElement`. После уточнения бизнес-правила
на каждый уровень хранится один абсолютный ценовой порог из `New`. В итоговый план также включены замечания о
транзакции, кэшированных значениях Excel-формул, неоднозначных совпадениях, тестах changelog и
регрессиях ценового кода.
